# D31: IaC & Container Security

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether Dockerfiles / Terraform / Kubernetes config follow security best practices.

## Applies to
Infrastructure and container manifests in any repository, whatever its programming language:

- container build files (Dockerfile and Containerfile, including named variants such as `Dockerfile.prod` or `Dockerfile-arm`);
- Docker Compose files;
- Terraform;
- Kubernetes manifests, including Helm charts and Kustomize bases and overlays;
- AWS CloudFormation, Azure Resource Manager (ARM) templates and Bicep;
- Ansible playbooks;
- edge-platform deployment descriptors, for example a Cloudflare Workers configuration file.

## Population
This dimension reads the manifests listed under Applies to. It does not read production code. Most of these manifests are build scripts or configuration markup, and [production-code.md](../production-code.md) leaves those out of production code. This dimension reads no other build script or configuration file. The exclusions below belong to this dimension.

A manifest is in scope when it describes infrastructure or containers that the project itself builds, runs or deploys. These manifests are **out of scope**:

- **Tests, fixtures and samples:** manifests that are test input, expected test output or example material (for example a Dockerfile in a test-fixture folder).
- **Documentation:** manifests inside documentation, for example a sample Kubernetes file in a tutorial.
- **Vendored code:** manifests inside third-party code copied into the repository, and modules a tool downloads into a cache.
- **Build output and tool state:** as [production-code.md](../production-code.md) defines them.
- **Configurations that cannot be applied:** a Terraform directory whose files declare the same resource more than once, so the directory cannot form one module (for example one file per answer option in a quiz).

Development-environment manifests are in scope but count at reduced severity (see Thresholds). A development-environment manifest sets up a local developer environment that is never deployed, for example a dev-container image or a development override Compose file.

## Unit and denominator
**Unit: a misconfiguration.** A misconfiguration is one place in an in-scope manifest that fails a recognised container or infrastructure security practice. It sits in a file the repository tracks. Public IaC security check catalogues state many of these practices, for example the checks of a public IaC security scanner. The practices listed under Severity are also part of the unit, whether or not a catalogue states them. Informational results are not counted.

**Severity.** Each misconfiguration is critical, high, medium or low. A practice that a public catalogue states takes that catalogue's severity. If the catalogue does not rate it, it is medium. The practices below take the severity given here:

- **High:**
  - the container runs as root;
  - a script, binary or archive is fetched during the build and then run, unpacked into the image or put on its path, with no checksum or signature check;
  - a signing key or other trust anchor is fetched without verification;
  - a fetch turns off certificate checking or uses an unauthenticated channel;
  - the build creates private key material inside the image;
  - the base image is past its end of life;
  - a Compose service mounts the container runtime's control socket;
  - a Compose service joins a host namespace (network, process or IPC) or runs privileged;
  - a Compose service pulls an image with no tag or with `latest`;
  - a workload runs privileged;
  - a Kubernetes Secret commits its secret values;
  - an edge-platform descriptor binds a credential to a plaintext value.
- **Medium:**
  - a base image is pinned by a movable tag rather than a digest;
  - a Compose service pulls an image by a movable version tag;
  - a toolchain or package is installed at no fixed version;
  - a repository is cloned at a movable reference;
  - an image reference has a tag that is an unfilled placeholder;
  - the whole build context is copied in with no ignore file;
  - a build tool is replaced by a script that does nothing and succeeds;
  - git's repository-ownership check is turned off;
  - the interpreter's guard against installing into the system packages is turned off;
  - a path is handed to a service account and then made writable by everyone;
  - a setuid permission is granted;
  - a browser's sandbox is turned off in its launcher;
  - a workload mounts its service-account token by default;
  - a persistent volume is backed by a host path;
  - an Ingress serves without TLS (cleartext ingress).
- **Low:** a service image declares no health check.

Each failed practice counts once, by these rules:

- **One fact, one count.** When two checks or catalogues report the same fact at the same place, it counts once. When overlapping checks report different facets of one missing setting, they count as one misconfiguration.
- **The highest severity wins.** When several checks report one fact, one setting's facets or one copied resource, and rate it differently, the one misconfiguration that counts takes the highest of their severities.
- **One resource, one count.** A resource copied unchanged into several files counts once for each practice it fails. Two resources are the same when they have the same kind, namespace and name.
- **One namespace, one count.** A practice that belongs to a whole namespace (for example a resource quota or a limit range) and that no in-scope manifest satisfies counts once for each namespace, at the highest severity reported. It does not count once for each manifest in that namespace. A manifest belongs to the namespace it names. If it names none, it belongs to the namespace its deployment unit applies (for example a Kustomize base's namespace). Manifests that no such setting covers share one namespace for each deployment unit, or one for the whole repository when they belong to no deployment unit.
- **The manifest set decides.** A practice is not failed when another in-scope manifest already satisfies it. For example, a container inherits a pod-level security context, a namespace holds its own resource quota or limit range, a namespace enforces a restrictive pod security level, or a service account turns off token mounting.
- **Values as deployed.** A template is not judged on a setting whose value is supplied only at deploy time, for example a Helm value, a placeholder or an overlay's image override. A Terraform input is judged at its declared default value. A patch fragment is judged only on the fields it sets. Generated overlay output does not count a failure that its hand-written source already counts.

**Denominator:** none. The score uses the total weighted count of misconfigurations across the repository's in-scope manifests. It does not divide by the number of manifests or lines.

## Thresholds
- **Severity weights:** critical 10, high 5, medium 1.5, low 0.4. Informational 0.
- **Development environments:** in a development-environment manifest, a critical, high or medium misconfiguration counts as low.

## Score
Let W = 10 × critical + 5 × high + 1.5 × medium + 0.4 × low, counted over the in-scope misconfigurations.

Score = clamp(10 − W / 15, 0, 10)

- A score of 10 means no misconfiguration was found in any in-scope manifest.
- The score falls by 1 for every 15 weighted points.
- It reaches 0 at W = 150. For example, 15 critical, 30 high, 100 medium or 375 low misconfigurations each give W = 150.

## Not measured when
The repository holds no in-scope infrastructure or container manifest. The dimension is then not applicable and is left out of the lens. It does not score 10. A repository whose only manifests are out of scope (for example only test fixtures, documentation samples or vendored modules) is not measured.

## What the result is not
- It is not the security of the deployed system. It reads committed manifests only. It does not see the live cloud account, runtime settings, or drift between the repository and what is deployed.
- It is not proof of correct configuration. It covers only the practices that are checked. A weakness that no checked practice describes is not counted.
- It is not a vulnerability scan of images or dependencies. Known vulnerabilities in packages belong to other dimensions.
- It does not reward hardening beyond the checked practices, for example network egress policies.
- It is not scaled to the size of the estate. A large estate with more misconfigurations in total scores lower than a small estate with fewer, even when the large estate has fewer per file.

## Pending re-definition

- **Normaliser:** 15 weighted points per score point.
- **Severity weights:** 10, 5, 1.5 and 0.4 for critical, high, medium and low.

- **Development-environment cap:** in development-environment manifests, critical, high and medium are lowered to low.
