# M2: Architecture documentation

**Lens:** maturity · **Scored:** yes

## Property
Whether key decisions (ADRs) and the high-level shape (C4/diagrams) are written down.

## Applies to
Any language. The dimension reads the repository's documents, not its code. These are in scope:

- documentation in any prose or page markup (for example Markdown, MDX, reStructuredText, AsciiDoc, plain text, HTML);
- diagram sources (for example C4 or Structurizr models, PlantUML, Mermaid, Graphviz, D2);
- drawn diagrams (for example SVG, PNG, draw.io, Excalidraw);
- guided walkthroughs of the codebase that a developer's editor can replay (for example a committed code tour).

## Population
The population is the repository's own documentation about itself. This documentation is not production code, so [production-code.md](../production-code.md) does not decide what is in scope. These are out of scope:

- **Tests and test inputs:** for example a diagram or numbered document that a test suite reads as a fixture or compares against.
- **Build output and tool state:** for example installed dependency folders, compiled output, and editor or tool folders.
- **Project plumbing:** for example issue and pull-request templates and workflow definitions.
- **Third-party material:** for example published standards or protocol specifications reprinted verbatim.

Being numbered or filed like a decision record does not make a document one. Each of the following counts only when it has a decision record's shape (see Unit):

- dated posts and announcements, press and newsletters;
- numbered manual or tutorial chapters;
- research notes, dev journals and work logs;
- UI mockups and wireframes;
- runbooks and playbooks;
- proposals that ask for a change but record no decision;
- the landing or index page of a decision log.

## Unit and denominator
The dimension reads three facts about the repository. Each one is either present or absent. There is no denominator.

1. **Decision records.** A decision record is one document per significant decision. It states the decision with its context and consequences. Examples are the Status / Context / Decision / Consequences shape, the MADR shape, and a design document with a problem statement and a weighing of alternatives. A single document titled as a log of design or architecture decisions also counts if it has one section per decision and at least 2 such sections. The number of records does not change the score. What matters is whether any exist and how they are filed:
   - **filed conventionally:** the record is in a folder kept for the decision log (for example `docs/adr/`, `decisions/`, `docs/rfcs/`), or its name is a decision number followed by a title (for example `0007-use-postgres.md` or `ADR-0007.md`);
   - **filed by content only:** the record has a decision record's shape but is filed in neither of those ways. A single consolidated decision log that is not in a folder kept for the decision log counts as filed by content only.
2. **A current architecture diagram.** This is a diagram of the system's parts that still matches the code (see Thresholds). It can be a file in a diagram notation, a diagram embedded in a document, or a drawn diagram of the system's parts.
3. **An architecture document.** This is prose that presents the system's high-level shape. Examples:
   - a document named for the architecture or design (for example `ARCHITECTURE.md` or `design.rst`);
   - a page kept in a folder for the architecture;
   - a docs page whose own title presents it as the architecture;
   - a section in the readme, the docs, or a contributor or agent guide that introduces the architecture or lays out the parts and where they live;
   - a page or folder in the repository that the readme or the docs point to as the architecture;
   - a link from the readme or the docs to an architecture page outside the repository, where the link's own label calls it the architecture (the outside page is not read);
   - a guided walkthrough that visits the system's parts.

## Thresholds
- **Decision records:** at least one record is needed. One record counts the same as many.
- **Diagram matches the code:** each diagram is compared with the repository's units. A unit is a project, package, crate, module, command or built service that the repository declares. A production unit is a unit that is not a test, test-support, sample, example, demo or benchmark unit. This differs from [production-code.md](../production-code.md), which counts samples and examples as production code. Units form a sibling group when they are of one kind and share one parent, or when one service-composition file builds them. A diagram makes a checkable claim only about a sibling group with at least 2 production units, and only if the diagram names at least 2 of them. A diagram is out of date, and does not count, when either of these is true:
  - it names a part that carries the sibling group's shared naming prefix, but that part is not a unit of the repository, is not inside one, and is not a path in the repository;
  - it names at least half of a sibling group's production units but leaves out one or more of them. Units that are not production units never count as left out.

  A diagram that makes no checkable claim counts (for example a context diagram that shows the system as one box). A picture whose text cannot be read (for example a PNG) makes no checkable claim and counts.

## Score
The score is the sum of three parts, capped at 10.

The decision-record part is one value:
- 6 points when at least one decision record is filed conventionally;
- 2 points when decision records exist but none is filed conventionally;
- 0 points when there are no decision records.

These two tiers are never added together.

| Part | Points |
|---|---|
| Decision records (see above) | 6, 2 or 0 |
| A current architecture diagram | 3 |
| An architecture document | 2 |

Examples of resulting scores:

| Decision records | Diagram | Document | Score |
|---|---|---|---|
| Filed conventionally | yes | yes | 10 (11, capped) |
| Filed conventionally | yes | no | 9 |
| Filed conventionally | no | yes | 8 |
| Filed conventionally | no | no | 6 |
| Filed by content only | yes | yes | 7 |
| None | yes | yes | 5 |
| None | no | no | 0 |

If every diagram in the repository is out of date, the repository scores the same as one with no diagram.

## Not measured when
- The repository's tree is not available for the run.
- The repository declares itself a template, kata, sample, demo, teaching example or proof of concept, **and** it has no decision record, no architecture diagram (current or out of date) and no architecture document. A template that has any of these is scored.

## What the result is not
- It is not the number of decisions recorded. 1 record and 124 records score the same.
- It is not the quality of each record. Record quality is a separate dimension.
- Documentation kept outside the repository is not read. It counts only when the repository links to it as the architecture. A low score does not prove that nobody wrote the shape down.
- It does not check that a prose architecture document is correct. Only diagrams are compared with the code.
- It is not a judgement on the architecture itself.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Discoverability weight:** decision records filed by content only earn 2 points instead of 6, even when the docs site's navigation links to them.
- **Where a decision record's shape must appear:** a document that is a decision record only by its content counts only when that shape appears within its first 64 KB. For a single record the shape is its sections. For a decision log it is the log's title and its per-decision sections.
- **Body size:** each of these counts only when it holds at least 120 characters that are not whitespace: a page in an architecture folder, a docs page titled as the architecture, and a page in the repository that the readme or docs point to as the architecture. When the readme or docs point to a folder, the documents in that folder must hold at least 120 such characters together. A link to a page outside the repository has no body check.
- **Located parts:** a section that lays out the parts and where they live, without calling itself the architecture (for example a bare "Structure" or "Design" heading), counts only when it points to at least 2 distinct files or folders that exist in the repository.
- **Named units:** a section headed as the layout of the project, its modules, packages or components counts only when the document names units of code at least 3 times.
- **Repeated mention:** a document that states what its architecture is, without an architecture heading, counts only when it names the architecture at least 2 times.
- **Guided walkthrough:** a walkthrough counts as an architecture document when it has at least 8 steps tied to a file or folder, spread over at least 3 distinct folders.
- **Where a section must start:** a section of a readme, docs page, or contributor or agent guide that introduces the architecture or lays out the parts counts only when it begins within the first 64 KB of that file.
- **Where a title must appear:** a docs page counts as titled as the architecture only when that title appears within its first 16 KB.
- **Diagram size:** a diagram file larger than 2 MB is not compared with the code. It counts just by being present.
