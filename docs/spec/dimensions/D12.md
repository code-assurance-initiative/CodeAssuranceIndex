# D12: Dependency Hygiene

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether dependencies are current, not deprecated, and not bloated. Known vulnerabilities are D30's.

## Applies to
This dimension applies to any language whose code lists third-party packages in a package manager's manifest. Today it reads these package managers: NuGet, npm, Maven, Gradle, sbt, Go modules, RubyGems, Hex (Mix and rebar3), Cargo, Composer, pub, PyPI, SwiftPM with CocoaPods, and the Unity package manager. If no manifest lists a language's dependencies, that language has nothing to measure here.

## Population
- **In scope:** the direct dependencies of production code, as [production-code.md](../production-code.md) defines it. A direct dependency is a package named in a manifest of one of the repository's own projects. Each one is read at the version it resolves to:
  - the version in the committed lockfile, where there is one;
  - otherwise, the version the declaration fixes.

  In rebar3 with no lockfile, an exact version requirement is the resolved version.
- **Also in scope today:**
  - npm: the deprecated signal also counts direct development and optional dependencies. The outdated signal and pinning count production dependencies only.
  - When NuGet scores the repository (with npm), the npm outdated term counts every non-development package that the committed npm lockfiles resolve. This includes transitive packages.
  - Maven and Gradle: the outdated signal counts every artifact in the resolved dependency graph, including transitive artifacts. In Maven, test-scoped artifacts count too.
- **Out of scope:**
  - Other transitive dependencies, meaning packages that only other packages pull in.
  - Other dependencies listed only for development or tests, for example a test project's references.
  - Platform and runtime requirements, for example a required language version, a native extension of the runtime, or a package that ships with the SDK.
  - Packages that no public registry of their ecosystem publishes, for example private or in-house packages and the repository's own workspace packages. These are never charged.
  - Vendored code, which [production-code.md](../production-code.md) already excludes.
- **One package, several declarations:** a package listed in several manifests or projects counts as one dependency.
- **Which package managers count:** today one package manager scores the repository. Where the repository has .NET package projects, NuGet and npm score it together. There is one exception: if NuGet finds no outdated, deprecated or vulnerable package and the repository has no .NET source of its own (C#, Visual Basic or F#), the order under Pending re-definition applies.

## Unit and denominator
The unit is one **dependency**. It can carry these signals:

- **Deprecated:** the publisher has marked the package, or the release it resolves to, as not to be used. Examples are a deprecation, a retirement (Hex), a yank (Cargo, PyPI), an abandonment (Composer) and a discontinuation (pub). Today no deprecated signal is read for RubyGems, Maven Central or SwiftPM, so nothing there is ever charged as deprecated (see the table under Score).
- **Prerelease:** the dependency resolves to a prerelease build, for example `-preview.2` or `-rc.1`. Today only NuGet packages are charged for it.
- **Outdated:** a newer stable release exists. The table under Thresholds says which newer release counts.

A dependency with more than one signal counts once, under its heaviest signal. Deprecated is the heaviest, then prerelease, then outdated.

The second unit is the **pinning defect**. Each of these counts as one defect:
- each direct production dependency taken from a source with no fixed revision, for example a git branch;
- in Go, each direct requirement pinned to an untagged commit that is 1,095 or more days old;
- in Hex (Mix and rebar3), each direct runtime requirement whose version range has no upper bound, for example `>= 1.0`. This includes a rebar3 dependency listed by name with no requirement at all. Optional dependencies are exempt;
- in Go, each module that requires other modules but commits no checksum file (`go.sum`);
- in the other package managers, each direct production dependency that the committed lockfile does not cover;
- each application manifest whose application commits no lockfile;
- each package that production code requires at two major versions at once.

There is no denominator. The counts are absolute.

## Thresholds
- A dependency is outdated when one qualifying newer stable release exists. Being further behind does not cost more. A prerelease never counts as the newer release.
- Which newer release counts:

| Package manager | Outdated when |
|---|---|
| NuGet | a newer stable release exists |
| npm | the registry's latest release is newer than the locked version |
| Go, Maven, Gradle, sbt | a newer release exists (in Go, a new major version is a different module) |
| SwiftPM, CocoaPods | a newer release exists on the same major version |
| Unity | a newer release exists that the project's editor version can install |
| RubyGems, Hex (Mix), Cargo, pub | the lock is behind a newer release that the dependency's own declared range allows (in pub, a bare version is exact and allows nothing newer) |
| rebar3 | as Hex (Mix); in addition, an exact version requirement is outdated when a newer stable release exists |
| Composer | the lock is behind a newer release the declared range allows, or the declared range excludes the newest stable release and the installed version is 3 or more major versions behind it (with or without a lock entry) |
| PyPI | an exact pin is behind the newest stable release (a minimum or a range is never outdated) |

- **Checked package manager:** a package manager counts as checked only when both of these hold:
  - every one of its dependencies got a definite answer from its registry;
  - at least one of them is published on that public registry.

  A package manager whose dependencies are all unpublished is not checked.

## Score
Each term grows linearly with its count, up to a cap. D, P, O and K are the counts of deprecated, prerelease and outdated dependencies and of pinning defects.

- deprecated: `min(0.5·D, 3.0)`
- prerelease: `min(0.25·P, 1.5)`
- outdated: `min(0.05·O, 2.0)`
- pinning: `min(0.25·K, 2.0)`

```
score = clamp(10 − sum of the terms charged, 0, 10)
```

Which terms are charged today depends on the package managers that score the repository:

| Scored set | Terms |
|---|---|
| NuGet (with npm, if present) | deprecated (NuGet and direct npm, counted together), prerelease (NuGet), outdated (NuGet), and a second outdated term for npm: `min(0.05·O_npm, 2.0)` |
| npm, Go, Unity, Hex (Mix), rebar3 | deprecated, outdated, pinning |
| RubyGems, SwiftPM | outdated, pinning |
| Cargo, PyPI, Composer, pub | deprecated, outdated |
| Maven, Gradle, sbt | outdated |

Example: a .NET repository has 2 deprecated, 1 prerelease and 30 outdated NuGet packages, plus 50 outdated npm packages. It scores 10 − 1.0 − 0.25 − 1.5 − 2.0 = 5.25.

A score of 10 means no charged signal and no pinning defect.

## Not measured when
- Production code lists no dependency in any manifest that is read.
- In a repository with .NET package projects and .NET source of its own (C#, Visual Basic or F#), the dimension is not measured when any of these holds:
  - The NuGet registry could not be reached, or the NuGet dependencies could not be resolved and read.
  - The only NuGet declarations are package lists that pin exact versions, and one of these is true: any of those declarations got no answer from the registry, or there are more of them than the limit under Pending re-definition. In other .NET repositories, exact-version declarations beyond that limit are not counted.
  - No NuGet package was found outdated, deprecated or vulnerable, and C# and Visual Basic together hold less than half of the repository's production lines (../production-code.md).
- A repository with .NET package projects but no .NET source of its own is scored as a NuGet repository when NuGet finds an outdated, deprecated or vulnerable package. Otherwise it is scored as a repository without .NET projects.
- Outside .NET, it is not measured when no package manager is checked, as Thresholds defines it. When a package manager is not checked, the next one in the order is tried instead.
- Maven is not checked when its dependency graph could be resolved only in part. A repository with more Maven builds than the cap under Pending re-definition counts as resolved only in part. If the graph cannot be resolved at all, the versions the poms declare are graded instead. This is done only when every pom can be read and every direct non-test dependency states its version in the repository's own poms. Otherwise Maven is not checked.
- Cargo and pub without a lockfile are not checked when their dependency graph is larger than the cap under Pending re-definition.
- In a .NET repository, an npm registry that cannot be reached does not stop the score. The npm outdated term is then 0.

## What the result is not
- It does not cover known vulnerabilities. Those belong to D30.
- It does not cover bloat. Today's score does not count unused, duplicated or excess dependencies, even though the property names them.
- It does not judge whether a package is maintained. Release age is not a maintenance status.
- It does not see copied-in code that no manifest lists.
- It can change over time. When a registry publishes a new release, the same commit can score lower.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **One package manager scores the repository.** Where the repository has .NET package projects, NuGet and npm score it together, and no other package manager is charged. There is one exception: if NuGet finds no outdated, deprecated or vulnerable package and the repository has no .NET source of its own (C#, Visual Basic or F#), the order below applies. In that order, the first package manager that is checked scores the repository alone: SwiftPM (with CocoaPods), Hex (Mix), rebar3, Go, RubyGems, Unity, Maven, Gradle, sbt, Cargo, Composer, pub, PyPI, npm. Package managers from sbt onwards are skipped when an earlier one lists dependencies, even if that earlier one is not checked. SwiftPM and rebar3 do not cause this skip.
- **At least one published dependency:** a package manager whose dependencies are all unpublished is not checked and does not score the repository.
- **NuGet declarations checked:** at most 400 exact-version declarations are checked against the registry. If the only NuGet declarations are exact-pin package lists and there are more than 400, the repository is not measured. Otherwise, declarations beyond 400 are not counted.
- **Maven builds read:** at most 4 separate Maven builds. A repository with more counts as resolved only in part, so Maven does not score it.
- **Unity dependencies read:** at most 100 direct registry dependencies per project.
- **Cargo and pub without a lockfile:** a dependency graph of more than 1,500 packages cannot be read, so the package manager is not checked.
- **Separate npm outdated cap.** When NuGet scores the repository, outdated npm packages have their own cap of 2.0, beside NuGet's cap of 2.0. Outdated can therefore cost up to 4.0 there.
- **Terms per scored set.** Which of the four terms each package manager is charged, as the table under Score gives.
- **.NET majority share:** half of the repository's production lines in C# and Visual Basic together. Below it, a .NET repository with no NuGet finding is not measured.
- **Stale untagged pin in Go:** 1,095 days.
- **Far behind in Composer:** 3 major versions.
