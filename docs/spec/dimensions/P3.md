# P3: Security & performance tooling

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether SAST, secret/dependency scanning and performance benchmarking are wired in (presence, not runtime).

## Applies to
Any language. This dimension reads how the repository is set up, not its source code. It reads:

- pipeline definitions;
- project and package manifests;
- analyzer and update-bot configuration files;
- benchmark and fuzz targets;
- the hosting platform's settings for the analysed commit (for example, code scanning or secret scanning switched on in the repository's settings).

## Population
The whole repository at the analysed commit. Most dimensions read only production code as [production-code.md](../production-code.md) defines it. This one does not:

- Benchmark projects and fuzz targets count here, even though they are not production code.
- Pipeline files, build files and tool configuration files count here, even though they are not production code.
- These files count only when they belong to the repository itself. Configuration inside vendored code (for example, an installed dependency folder) is left out.
- Text in a comment configures nothing and does not count.
- A command that only deletes a tool does not count (for example, clearing a tool cache to free disk space).

## Unit and denominator
The unit is the repository. There is no denominator. Each component below is either present or absent:

1. **Static analysis (SAST):** a tool that analyses the project's own code or infrastructure definitions without running it. Examples: a security scanner, a language's standard static analyzer, a compiler's built-in analyzers, or an infrastructure-as-code scanner.
2. **Secret scanning:** a scan for committed credentials. It counts when it runs in the pipeline or is switched on in the hosting platform's settings.
3. **Dependency scanning:** either of these:
   - automation that keeps dependencies current: an update bot whose configuration schedules at least one update;
   - a pipeline check that reviews each change's dependencies against known advisories.

   An update-bot configuration that schedules nothing, or that switches the bot off, does not count.
4. **Benchmarks:** performance benchmarks in the ecosystem's own form. Examples: a benchmark project, a benchmarks folder, a benchmark harness dependency, or benchmark functions in the language's standard test framework.
5. **Fuzzing:** fuzz targets in the repository, or a fuzzer run in the pipeline.

**Combined scan.** This is one product that, in a single run, scans the whole repository for all three: flaws in the code, committed secrets and vulnerable dependencies. It is present when its results are committed to the repository or when the pipeline runs it.

- A combined scan never counts under components 1 to 3. It earns only the "Combined scan only" column under Score, for each of the three, even when the pipeline runs it on every change.
- Full points for a component need a tool that meets that component's own definition and that the repository runs or configures for that purpose.
- A component that has such a tool earns that tool's points. The combined scan adds nothing to that component.
- Why it earns only partial credit: the combined scan is treated as a report read after the fact, not as a check for each component that can fail a change.

## Thresholds
Static analysis has three tiers.

**Gating.** Any of these holds:

- A dedicated analysis tool runs in the pipeline on at least one trigger that comes before a merge. Such triggers are a proposed change (for example, a pull request), a merge queue, a reusable call, or a push that is not limited to certain branches. Code scanning that the hosting platform itself runs on proposed changes also counts.
- A dedicated analyzer is part of the project's own build, so it runs wherever the project is built, with or without a pipeline. Examples: an analyzer package the project references, or a build target that runs the analyzer and that the project's check target requires.
- The project's own settings make the compiler's built-in analysis strict. Strict means one of:
  - the full rule set is on (for example, .NET's analysis mode "All");
  - the built-in analyzers are switched on in the project's settings and warnings are treated as errors.

**Advisory.** Analysis exists but cannot fail a change. Any of these holds:

- The project's own settings switch the built-in analyzers on, or give them an analysis level or mode, but below the strict level (warnings only).
- A static analyzer is declared as a development dependency, or its own configuration file is present, but neither the build nor the pipeline runs it.
- A dedicated tool runs in the pipeline only on triggers that do not come before a merge (for example, a schedule, a manual start, or a push limited to certain branches), and nothing else in the repository earns gating.

Two cases earn nothing:

- A toolchain default that the project's settings do not set.
- Built-in analyzers that the project's settings explicitly switch off. For example, in .NET: an analysis level or mode of "none", or the built-in analyzers disabled.

**Combined scan only.** Neither tier above applies, but a combined scan is present.

Secret scanning is present, absent or unknown:

- **Unknown** applies only when all of these hold:
  - the repository's host offers a secret-scanning setting, and that setting could not be read;
  - no secret scanner runs in the pipeline;
  - there is no combined scan.
- **Absent** applies when no secret scanner runs in the pipeline, there is no combined scan, and one of these holds:
  - the repository has no known host;
  - its host has no secret-scanning setting;
  - the host reports the setting as off.

## Score
Points per component:

| Component | Full | Combined scan only | Otherwise |
|---|---|---|---|
| Static analysis | 4 (gating), 3 (advisory) | 2 | 0 |
| Secret scanning | 3 | 1.5 | 0 |
| Dependency scanning | 3 | 1.5 | 0 |
| Benchmarks (bonus) | 1 | (no partial) | 0 |
| Fuzzing (bonus) | 1 | (no partial) | 0 |

- **Score** = static analysis + secret scanning + dependency scanning + benchmarks + fuzzing, clamped to 0-10.
- **Unknown secret scanning** is left out rather than counted as absent: score = (static analysis + dependency scanning) × 10/7 + benchmarks + fuzzing, clamped to 0-10. Absent secret scanning scores 0, and the sum is not rescaled.
- **Missing benchmarks or fuzzing never lower the score.** They can only add to it.

These are reported but do not change the score:

- a dependency bot that watches only some of the repository's ecosystems;
- a secret scan that does not gate merges;
- a built-in dependency audit that is switched off.

## Not measured when
- **Templates and examples.** The repository declares itself a template, kata, sample, demo, tutorial or similar: code meant to be read or copied, not run as a product. It is not measured when it has none of these:
  - static analysis at the gating or advisory tier;
  - secret scanning;
  - dependency scanning;
  - benchmarks.

  A combined scan and fuzzing do not count for this test. A template with any of the four is scored.
- **Unreadable tree.** The repository's files cannot be read.

## What the result is not
- **Not about findings.** It does not say whether the tools find anything, whether findings get fixed, or whether the tools run successfully.
- **Not dynamic testing.** It is not runtime security testing of a running application. Fuzzing is only a bonus.
- **Not a full coverage check.** It does not check that a tool covers every language or every dependency ecosystem in the repository.
- **Not a measure of performance or security.** A 10 means the tooling is wired in, not that the code is fast or secure.
