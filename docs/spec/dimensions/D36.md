# D36: Supply-chain Provenance & Signing

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether the build pipeline, including the configuration that publishes its releases, provides supply-chain integrity: generated provenance or attestation (a record, often signed, of how and from what an artifact was built), signed artifacts, an SBOM (software bill of materials, a machine-readable list of the components in an artifact), and build actions the pipeline reuses (for example CI actions or included templates) pinned to an immutable reference, such as a full commit hash or digest, rather than a movable tag or branch. Presence of the configuration, not a runtime guarantee.

## Applies to
Any language. The dimension reads build and release configuration, not production code:

- the repository's CI or build pipeline configuration, in any CI system;
- the scripts and the repository's own composite actions that the pipeline runs;
- build manifests (for example Maven, Gradle or sbt build files);
- release tool configuration (for example a GoReleaser manifest) and release task runners (for example a Makefile or Justfile release target). These count only when the pipeline, a script it runs, or the release task runner actually runs the tool;
- the repository's own release automation;
- SBOM files committed to the repository.

## Population
- **In scope:** the active lines of the files listed under Applies to. A line that is commented out does not count.
- **Every workflow is read for all four controls.** This includes a workflow whose only deployment is the project's documentation site.
- The definitions in [production-code.md](../production-code.md) do not apply. This dimension does not read production code.

## Unit and denominator
The unit is a supply-chain control. The repository either has it or does not:

1. **Provenance:** the pipeline generates a provenance or build attestation for what it releases. Examples: a provenance or attestation step, a registry publish with provenance turned on, trusted publishing that attests on publish, an image build that attaches a provenance attestation, a reusable builder asked to attest, or a step that handles provenance files the build produced. A flag or input that turns provenance off does not count.
2. **Signing:** the pipeline signs what it releases. Any signing act counts, for example:
   - a signature tool (sigstore-family, GPG detached signatures, platform code signing, package signing);
   - a hosted signing service;
   - a signing key or keystore given to the pipeline;
   - a build-manifest signer;
   - signing done by the release tool, the release task runner or the release automation;
   - a keyless attestation bound to the artifact's digest, including trusted publishing and a registry publish with provenance turned on.

   Two cases do not count: an Android signing setup that uses only the SDK's debug key, and importing or verifying someone else's key.
3. **SBOM:** an SBOM is generated or committed. Examples: a generator run by the pipeline or its scripts, an SBOM generator declared in a build manifest or in a release tool configuration that runs, an image build that attaches an SBOM attestation, an SBOM the pipeline publishes as a build artifact, or an SBOM file committed to the repository. A disabled SBOM input does not count.
4. **Pinned actions:** every reused action that the pipeline configuration references by `uses:` is pinned to an immutable reference. A reused action is a remote action, a reusable workflow from another repository, or a container action. GitHub Actions and compatible forges use this syntax. Only the CI configuration files are read for this control.

**npm-only evidence rule.** npm's own registry evidence is npm trusted publishing or a publish with npm provenance turned on. It covers only the npm package. Sometimes it is the only evidence of provenance or signing while the pipeline also publishes an artifact somewhere else, for example a package on another registry or a container image. In that case, that control is not present. Only npm's own evidence is set aside under this rule. All other evidence still counts, including PyPI trusted publishing, a sigstore-family or GPG signature, and a forge attestation.

**Denominator:** 3 (provenance, signing, SBOM), plus 1 when the pipeline configuration contains at least one `uses:` reference to a reused action.

## Thresholds
- **Immutable reference:** a full 40-character hexadecimal commit hash, or a container digest of the form `sha256:` followed by 64 hexadecimal characters. Anything else counts as movable. Examples: a version tag such as `v4`, a branch such as `main`, or a container image with only a tag or with no tag.
- **Pinned actions present:** every `uses:` reference is immutable. One movable reference means the control is absent.
- An action referenced by a local path in the same repository has no reference to pin. It is not counted.
- Each control is worth an equal share. Nothing else is weighted.

## Score
`score = 10 × present / denominator`, where `present` is the number of controls present.

- With a denominator of 3, the possible scores are 0, 3.33, 6.67 and 10.
- With a denominator of 4, the possible scores are 0, 2.5, 5, 7.5 and 10.

A 10 means the pipeline generates provenance, signs artifacts and produces an SBOM. If it uses reused actions, it also pins every one of them. A 0 means a releasing pipeline has none of these controls.

## Not measured when
- The repository has no CI pipeline configuration (a pipeline definition for a CI system). Build manifests, release tool configuration and task runners alone do not make the dimension apply.
- The repository is a project template that scaffolds new projects. It releases no artifact of its own.
- The pipeline publishes no artifact and neither signs nor attests anything. Publishing an artifact means a package publish, a container push, or a release with downloadable files. Deploying the service itself is not publishing an artifact. A workflow whose only deployment is the project's documentation site is not publishing an artifact either, although it is still read for all four controls.
- The release clearly produces no artifact. For example: a library is tagged for a module proxy, its release tool builds nothing, no other pipeline ships anything, and nothing is signed or attested.

In the last two cases the dimension is not scored, even when it reports findings about the pipeline.

## What the result is not
- It does not guarantee anything at runtime. It reads configuration. It cannot confirm that the build platform actually produces or verifies the attestation (for example a SLSA level 2 or 3 build). Compliance controls should treat it as supporting evidence, not proof.
- It does not check signatures, the contents of an SBOM, or whether provenance is correct.
- It does not cover the integrity of all the pipeline's inputs. Examples are unverified downloads, moving dependency references, mutable container pulls, workflow token scope and branch protection. These are reported elsewhere or not scored, and none of them affects this score.
- In other CI systems, today's pinned-actions control does not include pinning of included templates. In those systems the denominator is 3.
- It does not score how much of a release is covered. One signing act anywhere on the release path counts as signing.
