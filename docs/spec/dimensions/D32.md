# D32: Data Compliance (PII/GDPR)

**Lens:** securityCompliance · **Scored:** yes

## Property
Likely personal-data (PII / GDPR) handling concerns — logging or storing data without safeguards.

## Applies to
- **Personal data written to a log or console:** C#, F#, Visual Basic .NET, Java, Kotlin, Scala, Python, JavaScript, TypeScript, Go, Ruby, PHP, Swift, Rust, Dart, Elixir and Erlang.
- **Whole object written to a log:** C# only.
- **Personal data placed in a URL:** the same languages as log and console sites.
- **Personal data written to browser storage:** JavaScript and TypeScript.

This dimension does not read other languages, web markup (HTML) or styles (CSS).

## Population
This dimension reads production code as [production-code.md](../production-code.md) defines it, in the languages above. It also leaves out:

- **Examples, samples and demonstrations:** for example a `samples` project or an example application shipped beside the product.
- **Database migrations:** code that changes a database schema or moves its data from one version to the next.

## Unit and denominator
**Unit: a leak site.** A leak site is one place in the code where a personal-data value crosses one of these boundaries:

1. **Log or console:** the value is passed to a call that writes a log entry or console output. For example a logger's level method, `print`, `println`, `Console.WriteLine`, `NSLog`, a Rust logging macro, or a logging method the code itself declares.
2. **Whole object in a log (C# only):** a log call writes out every public member of an object, and one of those members holds personal data (for example a structured-log template hole that serialises the object). Each such hole is its own leak site.
3. **URL:** the value is placed in a URL's query string as a parameter named for personal data (for example `?email=…`, `&phone=…`, `?ssn=…`).
4. **Browser storage:** the value is written to `localStorage` or `sessionStorage`. This happens in one of two ways: under a key that names personal data, or as a value that holds contact data (for example a list of e-mail addresses or recipients).

**Personal data** is a value about an identifiable person. It falls into two categories:

- **Sensitive:** special-category data and direct identifiers. For example national identity numbers (social security, CPR), passport and driving-licence numbers, payment card numbers, bank account numbers and IBANs, biometric data, health and medical records, and medical diagnoses.
- **Ordinary:** other personal identifiers. For example e-mail addresses, phone and mobile numbers, dates of birth, home, postal, street and billing addresses, first names, last names and surnames, and tax identifiers.

These are not personal data:

- a hashed, masked, redacted, encrypted or pseudonymised form of the value;
- a fact about the value, for example a flag (`hasEmail`), a count, a length, a domain or a verification state;
- a literal word or small number in a URL parameter (for example `?email=true`);
- the name of a field written as prose in a message, when the field's value is not itself written.

**Counting at one place.** At one place in the code, each kind of leak site in the weight table counts at most once. Different kinds count separately. One log call that writes both a sensitive and an ordinary value counts 5 + 1.5 = 6.5. In C#, if that call also writes out a whole object holding personal data, each such hole adds 1.5. One browser-storage write that both uses a key naming personal data and stores contact data counts 1.5 + 1.5.

**Denominator:** none. The score comes from the weighted number of leak sites in the repository. Repository size does not change it.

## Thresholds
Each leak site carries a weight:

| Leak site | Weight |
|---|---|
| Sensitive personal data passed directly as a value to a log or console | 5 |
| Ordinary personal data passed directly as a value to a log or console | 1.5 |
| Personal data of either category in a whole object written to a log (C#, per hole) | 1.5 |
| Personal data of either category placed in a URL | 1.5 |
| Browser storage written under a key that names personal data | 1.5 |
| Contact data written as a value to browser storage | 1.5 |

The weight of 5 applies only when the sensitive value itself is passed to the log or console call. A whole object written to a log weighs 1.5 even when one of its members holds sensitive data.

W is the sum of the weights of all leak sites in the population.

## Score
score = 10 × 0.5^(W / 10), rounded to 2 decimals.

The score halves for every 10 points of W. Examples:

- one ordinary leak site gives 9.01;
- one sensitive leak site gives 7.07;
- one log call writing both a sensitive and an ordinary value (W = 6.5) gives 6.37;
- two sensitive leak sites give 5.00;
- four sensitive leak sites give 2.50.

The score falls toward 0 as W grows. It rounds to 0.00 once W is about 110 or more (for example 22 sensitive leak sites).

## Not measured when
- **No leak site is found.** A clean result is not scored and is not a 10. Finding no leak sites does not show that a repository handles personal data well.
- **No production code in an applicable language.** The repository has no production code in any language listed under Applies to.

## What the result is not
- **Not a GDPR compliance verdict.** It does not check lawful basis, consent, retention periods, erasure, data subject rights or encryption at rest.
- **Not an inventory of the personal data a repository holds.** A repository can hold a lot of personal data and never send it across these boundaries. That is not measured.
- **Not a runtime data-flow trace.** A value is recognised as personal data by how the code names it, so:
  - personal data under a neutral name is missed;
  - non-personal data named like personal data (for example a card number in a card game) can be counted.
- **Not a count of every leak path.** Personal data sent to files, databases, analytics services, error reporters or third-party APIs is not counted. Whole objects written to logs are counted only in C#.
- **Not reached by every file.** Code that cannot be read as its language is not counted. A leak site missed there is not a clean result.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them. A later decision under decision 0013 will replace each with a threshold on the property.

- **Half-score point:** W = 10 gives a score of 5 (the 10 in the curve).
- **Whole objects in C# logs, file cap:** whole objects written to a log are read only in the first 20,000 C# files, and only in files of at most 1,000,000 bytes. Leak sites of this kind in other C# files are not counted.
