# D26: Project Cohesion

**Lens:** architecture · **Scored:** yes

## Property
Whether each project is a focused, coherent unit rather than an oversized grab-bag.

## Applies to
This dimension applies to any language whose code is organised into projects. A project is a unit that the repository's own build declares as one thing it builds or ships. Some examples: a .NET project, a Maven or Gradle module, an npm, Deno or JSR package, a Go module, a Cargo crate, a Python, Composer, Bundler, Mix, SwiftPM or pub package, or an Xcode target spec. A repository that declares no build at all is one project.

Two things depend on the language:

- **Spread.** In C# and Visual Basic .NET, a project's spread is the number of namespaces that its counted types declare. In every other language it is the number of directories that hold its counted types.
- **Counted types.** In every language, a counted type is one the language exposes beyond the file or package that declares it. Examples are a `public` class in C# or Java, a Rust `pub` type, or a Go exported (capitalised) type. In Swift, Kotlin and F#, an `internal` type also counts, and so does a Swift `package` type, because in those languages `internal` means visible across the whole module. In C# and Visual Basic .NET only `public` types count. `internal` (`Friend`) types do not.

## Population
A project's figures are read over its production code, as [production-code.md](../production-code.md) defines it. Each production file belongs to the nearest project that encloses it. A project that builds for several target frameworks or platforms counts once.

Which projects are in the population depends on the language:

- **C# and Visual Basic .NET:** every project the repository declares. This includes a project with no production code, for example a test project. Such a project is never flagged, so it costs 0.
- **Every other language:** every declared project that holds production lines or counted types. A project with neither, for example a test-only package, is not in the population.

This dimension differs from [production-code.md](../production-code.md) in these ways:

- Types declared in generated files count toward neither the type count nor the spread.
- In the one-project case (see Score), a test, sample, benchmark or tooling project is not graded. This applies even though samples and the authors' own tools are otherwise production code.

## Unit and denominator
Each project has three figures:

- **Lines:** its production lines, as [production-code.md](../production-code.md) counts them.
- **Types:** its counted types (see Applies to). A type is a named class, interface, struct, record or enum, or the language's equivalent, declared at namespace, package or module level. This includes a type declared in a single-file component (for example a Vue or Svelte file). A type split over several files (for example a C# partial class) counts once.
- **Spread:** its namespaces or directories (see Applies to).

A project is **flagged** when it goes past its bounds (see Thresholds). Its **overshoot** is the largest of three ratios: lines ÷ 6,000, types ÷ 120 and spread ÷ 10.

The denominator is the number of projects in the population (see Population). In C# and Visual Basic .NET this includes projects with no production code. In other languages it does not.

**One project.** When the population is exactly one project, the figure used is its **separable share** instead. That is the share of its types that sit in parts that reach the rest of the project only through its shared core (see Pending re-definition). For the separable share, a type is every named type that the project declares in its own non-generated production source, whatever its visibility. A type split over several files counts once. Every share and count in the separable-share rules counts these types.

## Thresholds
- **Lines bound:** 6,000 production lines.
- **Types bound:** 120 counted types.
- **Spread bound:** 10 namespaces or directories.
- A figure is over its bound when it is strictly greater than the bound.
- **Flag:** a project is flagged when at least 2 of its 3 figures are over their bounds and it has more than 0 production lines.
- **Line floor (spread counted by directory):** outside C# and Visual Basic .NET, a project is flagged only if it also has at least 0.75 × 6,000 = 4,500 production lines. A project whose spread is its declared namespaces has no floor.

## Score
**Two or more projects.** Each flagged project costs

  penalty = 1 + clamp(log2(overshoot), 0, 1)

A project just over its bounds costs 1. The cost rises to 2 for a project at twice its worst bound or more. A project that is not flagged costs 0.

  score = clamp(10 − 10 × (Σ penalty ÷ number of projects), 0, 10)

**Exactly one project.**

- Within the bounds (not flagged): not measured (see below).
- Flagged: score = clamp(10 × (1 − separable share), 0, 10). A flagged project with no separable part scores 10, whatever its size.

## Not measured when
- The repository has no production code.
- The repository has C# or Visual Basic .NET production code, but no .NET project it declares holds that code.
- Too little of the production code belongs to a project. A language is covered when at least half of its production lines sit in files that belong to a project. The dimension is not measured when the covered languages hold less than half of the repository's production lines. Files of example or sample projects are left out of both counts.
- The repository is one project within the bounds. One project of that size gives cohesion nothing to grade.
- The repository is one project, and that project is a test, sample, benchmark or tooling project.
- The repository is one flagged project, and the references between its parts cannot be read. Its size alone gives no verdict.

## What the result is not
- It is not a direct reading of conceptual coherence. With two or more projects it reads size and spread. A small project that mixes unrelated concerns is not flagged.
- It is not a request to split. A large project whose parts reference each other is one coherent unit.
- It does not judge whether a split is possible. Splitting a published package can break its consumers.
- It says nothing about cohesion inside a type or a file (see D6).

## Pending re-definition
These are parameters of the existing reading's model, and today's score depends on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Overshoot curve:** log2 of the worst ratio, capped at an extra cost of 1, so the most one project can cost is 2.
- **Line floor:** 0.75 of the lines bound. It applies only where spread is counted by directory.
- **Coverage bar:** half of a language's lines must belong to projects for the language to be covered, and the covered languages must hold half of all production lines.
- **Parts of one project (separable share):**
  - **Root:** in C# and Visual Basic .NET, the root is the longest dotted namespace prefix that holds at least 90 % of the types, in it or below it. In other languages, it is the deepest directory that holds at least 90 % of the types, in it or below it. Each type is counted once, at the directory of the file that declares it.
  - **Part:** a part is the first namespace segment (or directory) below the root. Types in the root itself, or outside it, form the root part. A root-namespace type declared inside a part's own folder belongs to that part. That folder is the nearest folder named like the part that holds all of the part's files.
  - **References:** a reference is every place in the project's own source that names one of its own types, counted once per occurrence. A type naming itself does not count. Outside .NET, references are the import statements and name references from one of the project's files to another of its files.
  - **References touching a part:** every reference that starts in the part or names a type in it. This includes references between the part's own types.
  - **Shared core:** the root part, plus every part that is referenced at least 3 times as often as it references other parts (in ≥ 3 × max(out, 1)).
  - **Concentration:** if the largest part holds at least 75 % of the types, the separable share is 0.
  - **Separable part:** a part that meets all of these conditions:
    - It is not in the shared core.
    - It has at least 5 types and at most 25 % of the project's types.
    - It spans at least 3 files.
    - It has at least 1 reference touching it for each type it holds.
    - At most 15 % of the references touching it run between it and a part that is not in the shared core.
    - It is not both referenced by the rest of the project and referencing the rest.
    - It is not named for a framework role. Role names, compared ignoring case: Abstractions, Admin, Api, Apis, Areas, Attributes, Commands, Common, Components, Constants, Contracts, Controllers, Converters, Core, Data, Drivers, Dto, Dtos, Endpoints, Entities, Enums, Exceptions, Extensions, Factories, Filters, GraphQL, Handlers, Helpers, Hubs, Infrastructure, Interfaces, Mappers, Mapping, Mappings, Middleware, Middlewares, Migrations, Models, Pages, Properties, Queries, Repositories, Requests, Resources, Responses, Services, Shared, Tools, Utilities, Utils, Validation, Validators, ViewComponents, ViewModels, Views.
  - **Separable share:** the types in all separable parts ÷ all the project's types.
