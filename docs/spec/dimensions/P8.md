# P8: Schema migrations

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether database schema changes in production code and configuration go through versioned migrations (a committed, ordered history of schema changes) rather than being created or altered automatically from the application's entity or model definitions (for example EF Core EnsureCreated, GORM AutoMigrate, SQLAlchemy create_all, TypeORM synchronize set to true, Hibernate ddl-auto set to create or update). Test code, for example a fixture that creates a throwaway database, is excluded. A positive result means production schema changes are recorded as versioned migrations and not created automatically; it is not proof that the migrations are applied or match the live schema.

## Applies to
Any language whose application code owns a relational database schema, whether through an ORM, a migration tool or SQL it runs itself. The dimension also reads the files that decide how the application treats its database:

- application configuration (for example a framework's properties or YAML settings)
- the migration files themselves (SQL or code)
- the scripts that start or deploy the application (for example a container entrypoint, a Procfile, a compose file, a package's start or build script, or a deployment pipeline step)

## Population
Production code as [production-code.md](../production-code.md) defines it, with these differences:

- **Also read:** the repository's production configuration files, its migration history files in any format, and the scripts that build, start or deploy the application, including deployment pipeline definitions. A migration history counts wherever the repository keeps it. That includes a migration template the product ships to the applications that use it.
- **Left out, beyond [production-code.md](../production-code.md):**
  - Examples, samples, demonstrations and getting-started programs. Their schema belongs to the program they demonstrate.
  - Starter or scaffold templates that a generator copies into other repositories.
  - Configuration for an environment that is not production (for example a development, local or test profile).
  - A plug-in's own tables, when the product beside it has a versioned history.
  - A local store kept in the end user's own directories (for example a desktop tool's per-user database file).
  - Database libraries declared only for development or tests.
- Tests and test support stay out, as [production-code.md](../production-code.md) says. A test that builds a throwaway schema from the model is the intended use.

## Unit and denominator
The unit is the repository. Two things are read from its population:

- **Versioned history:** a committed, ordered set of schema changes. It is applied by a migration tool, or by the application's own runner when that runner records which changes it has applied. For example: numbered SQL migration files; a Flyway, Liquibase, Alembic, Django, Rails, Prisma, TypeORM, Knex, Sequelize, golang-migrate, goose, Diesel, sqlx, DbUp, FluentMigrator or EF Core migrations history; or a deploy step that applies such a history. Schema statements inside the history are part of the history. They are not auto-create sites. A runner's own table that records which changes it applied is not a site either.
- **Auto-create site:** a place in the population where the running or deploying application creates or alters the schema outside any versioned history. Each call, setting or statement counts as one site. For example:
  - a call or setting that builds the schema from entity or model definitions (the examples in the property)
  - a deploy or start step that generates migrations on the spot or pushes the model straight to the database (for example `makemigrations` or `prisma db push` at deploy)
  - a `CREATE TABLE` statement that the application itself executes at runtime

  A call or setting of an ORM or migration library counts as a site only when the repository uses that library in production, not when the library is declared only for development or tests. A schema statement that the application runs itself is always a site, with or without a library.

There is no denominator. The score depends only on two facts: whether at least one versioned history exists, and whether at least one auto-create site exists.

## Thresholds
- A single auto-create site is enough for auto-create to count.
- A single migration is enough for a versioned history to count.

## Score
| Repository state | Score |
|---|---|
| A versioned history and no auto-create site | 10 |
| One or more auto-create sites, with or without a versioned history | 3 |

No other score is possible. The number of sites does not change the score.

## Not measured when
- **Not applicable:** the repository has no database schema of its own. This covers two cases:
  - Nothing declares an ORM or a migration tool, and nothing creates a schema automatically.
  - An ORM is declared, but the repository defines no table or model of its own and has neither a history nor an auto-create site (for example a client library, or a tool that only queries a database someone else owns).
- **Not measured:** the repository uses an ORM and defines a schema, but has neither a versioned history nor an auto-create site. The schema may be managed from outside the repository, so the dimension gives no score rather than a low one.
- **Not measured:** the engine cannot read the repository's languages for this dimension.

## What the result is not
- It is not proof that the migrations are applied or complete, or that they match the live database schema.
- It does not judge the quality of individual migrations (for example whether a migration can be reversed, or is safe on large tables).
- It is not a count. A repository with one auto-create site scores the same as one with many.
- A score of 3 when a history is present means the schema has two paths. It does not mean the history is missing.
