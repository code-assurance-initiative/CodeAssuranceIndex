# C2: Access Controls

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether access is authorized by default — a framework authorization attribute/decorator or policy, or imperative guard methods (throw-on-violation) called from handlers.

## Applies to
Code that serves requests to callers other than itself, in C#, Java, JavaScript, TypeScript, Python, PHP, Ruby, Dart, Rust and Elixir. It also covers SQL table definitions when the repository creates tables that a hosted database serves straight to clients over an API (for example Supabase tables in the `public` schema).

## Population
Production code as [production-code.md](../production-code.md) defines it, with these differences:

- **In scope:** the repository's request surface. This is every endpoint, route, request handler or service operation the code serves, plus all authorization the code declares or performs.
- **Server-side templates** count as production code for this dimension. An authorization marker written in a view or page counts (for example `@attribute [Authorize]` in a Razor page).
- **Out of scope:** client-side route guards in a browser or mobile application, because they hide a page but authorize nothing. Calls the code makes to other services are also out of scope (for example an HTTP or REST client).

## Unit and denominator
The score uses these counts and facts, taken over the whole repository. Nothing is divided per file.

- **Declared guard:** a place where the code marks an endpoint, a group of endpoints or a whole controller as needing an authorized caller. Examples: an `[Authorize]` attribute, `RequireAuthorization` on a route or group, `[PrincipalPermission]`, a route guard or auth decorator, an authentication middleware on a route, or a served database table with row-level security turned on. Each place counts once.
- **Opt-out:** a place where the code marks something as open to anonymous callers. Examples: `[AllowAnonymous]`, a public-route marker, or a served table without row-level security. Each place counts once.
- **Imperative guard call:** a call from a handler to a guard that refuses an unauthorized caller, either by throwing or by returning a refusal such as 401 or 403. The guard can be a method the repository defines or a refusal written inline. Each call site counts once.
- **Default deny:** the code refuses every request that does not explicitly opt out. Examples: an authentication middleware in front of every route, or a fallback authorization policy.
- **Every route guarded:** every route the code serves is reached by at least one guard. The guard can sit on the route, on its router or group, or on the whole application.
- **Named rules:** the access rules are declared once by name and checked where access is decided. Examples: named policies, roles or claims registered with the framework, policy classes, abilities, or permission enums.
- **Authentication configured:** the program registers an authentication scheme or the framework's authorization services.
- **Open by omission:** at least one of these holds:
  - an endpoint lacks the guard its siblings carry;
  - an authorization check does not decide the response (nobody reads its result, or a write happens before the check);
  - an anonymous opt-out covers a whole controller or page whose endpoints change state;
  - a served table has no row-level security.

## Thresholds
- **Declared:** at least 1 declared guard.
- **Sufficient imperative enforcement:** at least 3 imperative guard calls, or every route guarded.
- **Every route guarded:** at least 2 routes, and all of them reached by a guard.
- **Any authorization:** declared, sufficient imperative enforcement, default deny, named rules, or at least 1 imperative guard call.
- **Balanced:** the number of opt-outs is at most the number of declared guards.

## Score
The score is the sum of three components and runs from 0 to 10.

- **Core (5):**
  - 5 if the code is declared, has default deny, or has every route guarded.
  - Otherwise min(imperative guard calls, 3) / 3 × 5. So 1, 2 and 3 calls earn 1.67, 3.33 and 5.
- **Named rules (3):** 3 if named rules are present, otherwise 0.
- **Balance (2):** 2 only when there is any authorization, nothing is open by omission, and one of these holds:
  - if declared: the code is balanced, or a fallback deny policy is in place;
  - if not declared: sufficient imperative enforcement, or default deny.

  Otherwise 0.

**Rescaling:** in C# only, the named-rules component does not apply when the code is declared but has neither authentication configured nor named rules. In that case the score is (core + balance) × 10/7.

A request surface with no authorization scores 0.

## Not measured when
- The code serves no requests, whatever authorization code it contains. Examples are a library, including one that ships authorization attributes or guards, and a command-line tool.
- The repository is a project template that contains no authorization.
- The code is a client whose data a hosted backend serves, and the repository contains none of that backend's access rules. The backend's configuration decides access, so the dimension is not assessed.

## What the result is not
- It does not prove that every endpoint is protected. Opt-outs are only weighed against the total number of declared guards.
- It does not check that the rules themselves are right, for example whether a given role should have a given right.
- It does not measure authentication strength, session handling or record ownership.
- It says nothing about protection outside the repository, for example a gateway, a reverse proxy or a hosted backend's settings.
