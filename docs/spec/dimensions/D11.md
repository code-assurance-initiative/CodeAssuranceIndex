# D11: Test Reliability

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether the tests pass reliably, with no flakiness.

## Applies to
Any language that has a test suite that can be run. This dimension reads how the tests behave when they run. It does not read what the test code looks like. The language matters only because it decides which test suites the repository has.

## Population
- **In scope:** every test in the repository's own test suites, in every language and every kind of suite (for example unit, integration, behaviour-driven and end-to-end suites). [production-code.md](../production-code.md) defines tests and test support. On this page they are what is measured, not what is left out.
- **Tests behind a build setting:** tests that compile only under a build setting that is off by default (for example a conditional-compilation symbol) are part of the suite. They are run with that setting on.
- **Out of scope:**
  - tests inside code that [production-code.md](../production-code.md) excludes for another reason: generated code, vendored or copied-in third-party code, and build output.
  - tests the suite itself does not run, for example a test its framework marks as skipped or ignored. A skipped test has no outcome, so it cannot be flaky.
  - code that is not a test. Production code is not read.
- **Parts of the suite:** a suite has parts, for example a language's unit tests, its integration tests, or one test project or package. A part is compared when all of its runs finished and together they reported at least one test. A part whose runs did not all finish, or that reported no test, is not compared.
- **What the compared parts decide:** they decide only whether a score is published and which parts the result says it covers. They do not limit F (see Unit and denominator). A part that was not compared does not withhold the score by itself, unless it leaves a language named under Not measured when with no compared part.

## Unit and denominator
- **Run:** one complete run of one part of the suite at the analysed commit, in one environment, with nothing changed between runs.
- **Test:** one test case as the repository's test framework reports it (for example one test method, one `it` block or one test function). A test belongs to its test project or package, so two tests with the same name in different projects are two tests.
- **Flaky test (the unit):** a test that passes in at least one run and fails in at least one other run of the same code.
  - A test that fails in every run is broken, not flaky. It is not counted.
  - A test that passes in every run is not counted.
  - A test seen both passing and failing is flaky even when its part's runs did not all finish.
- **Count:** F is the number of distinct tests seen both passing and failing in any part that ran, whether or not that part's runs all finished. F is summed over all languages and all kinds of suite. A part that was not compared still adds its flaky tests to F.
- **Denominator:** none. F is an absolute count. It is not divided by the number of tests.

## Thresholds
- **Runs:** each part of the suite is run 3 times. With fewer than 2 runs a test can never be seen both passing and failing, so 2 is the minimum.
- **Flaky:** at least 1 passing run and at least 1 failing run of the same test.
- **Compared part:** all of the part's runs finished, and together they reported at least 1 test.
- **Material language:** a production language is material when it holds at least 15 % of the repository's production lines, counted as [production-code.md](../production-code.md) defines them. C and C++ count together as one language.

## Score
```
score = clamp(10 − 2 × F, 0, 10)
```
| F (flaky tests) | Score |
|---|---|
| 0 | 10 |
| 1 | 8 |
| 2 | 6 |
| 3 | 4 |
| 4 | 2 |
| 5 or more | 0 |

When only some parts were compared, the score uses the same formula over every flaky test seen. The result names the parts that were not compared. When no part was compared but at least one flaky test was seen, the score is still given from F, and the result names the parts that were not compared.

## Not measured when
The first four cases apply only when no test was seen both passing and failing. Once a flaky test has been seen, they do not withhold the score.

- The repository has no test suite to run.
- No test ran: the suite could not be built or started. This includes tests behind a build setting that is off by default, when even with that setting on they cannot be built or no test runs.
- The runs finished but reported no tests at all. A suite that ran no tests is not measured, and it does not get a perfect score.
- No part of the suite was compared.

These two cases withhold the score even when flaky tests were seen:

- A material language has a test suite of its own and no part of that suite was compared (it was not run, did not finish, or reported no test). A score for one part of a polyglot product is not published as the score for the whole product.
- The repository has both a test suite for .NET languages (for example C#, F# or Visual Basic .NET) and a JavaScript or TypeScript test suite, and either of the two has no compared part. This holds whatever share of production lines each language has.

When the score is withheld, the flaky tests that were seen are still reported.

A repository can mark some of its own tests as skipped and give flakiness or intermittent failure as the reason. If its suite could not be run, those tests are reported as the repository's own statement. They are not counted, and no score is given.

## What the result is not
- **Not a density.** One flaky test in a suite of ten thousand tests costs as much as one flaky test in a suite of ten.
- **Not a proof of reliability.** Only the runs that were made are observed. A test that fails rarely, or only under conditions those runs did not meet (for example load, time of day, platform or a different test order), stays invisible.
- **Not always the whole suite.** When some parts were not compared, the result says that it does not cover them. Their flaky tests that were seen still count.
- **Not a search for order dependence.** A test whose outcome depends on which tests ran before it counts only when its outcome actually changed between the runs.
- **Not a pass rate.** Tests that fail every time are reported by the test dimensions, not here.
- **Not a judgement of test quality or coverage.** Other dimensions cover those.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Number of runs:** each part of the suite is run 3 times, with a minimum of 2. How many tests can be found flaky depends on this number.
- **Penalty per flaky test:** each flaky test costs 2 points, so 5 flaky tests give a score of 0, whatever the size of the suite.
- **Material language:** when a language holds at least 15 % of production lines and has tests of its own, at least one part of its suite must have been compared for the result to be measured.
- **.NET and JavaScript/TypeScript suites together:** when both exist, each must have a compared part, whatever its share of production lines.
