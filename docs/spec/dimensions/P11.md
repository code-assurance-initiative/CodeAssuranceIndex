# P11: BDD / executable specs

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether behaviour is captured as executable Gherkin specifications (a plus for shared understanding) — only assessed when a BDD framework is present.

## Applies to
Any language that has a BDD framework. The dimension reads two kinds of files:

- **Specification files:** Gherkin feature files (`.feature`), in any spoken language.
- **Project declarations:** the build project or package manifest that holds those files, any shared build settings
  it imports, and the runner configuration that says which specification files a runner loads.

Code-first BDD frameworks also count. In these frameworks, scenarios are written as code in the project's own
language (for example LightBDD or BDDfy in C#).

## Population
This dimension is about tests, so it does not use production code as [production-code.md](../production-code.md) defines it. Tests and test
support are in scope.

- **In scope:** every specification file the repository tracks, and every runner declaration of a BDD framework.
- **Out of scope:** build output and tool state, vendored code (for example an installed dependency folder), files in
  hidden folders, and files the version control ignores rather than tracks.

**The projects that hold a file:** a specification file belongs to the nearest project or package above it, in any
language. It also belongs to any project that names it by path to include it. A file can belong to no project at all
(for example a bare features folder with no manifest above it).

**Runner declarations:** a runner declaration is one place that lists a Gherkin runner as a dependency. That place is
either a project's own manifest or shared build settings. A declaration reaches the project that holds it and, for
shared build settings, every project that imports those settings. A project has a runner when at least one
declaration reaches it.

## Unit and denominator
The unit is one specification file. Each file is in one of four states:

- **Run:** a project it belongs to has a Gherkin runner, and a runner in the repository loads the file.
- **Unattached:** it belongs to at least one project, and none of those projects has a Gherkin runner.
- **Not loaded:** a project it belongs to has a Gherkin runner, but no runner in the repository loads the file.
- **Unowned:** it belongs to no project or package. Such a file is neither unattached nor not loaded. It counts in F
  only.

A runner loads the paths and patterns that its configuration and command lines declare. A runner with no declared
paths loads the paths it loads by default (for example, cucumber-js loads its features folder). A runner that runs
every feature file of its own project (for example Reqnroll or SpecFlow) loads all of that project's specification
files. If a package builds its load list at run time, so the list cannot be read from the code, every file of that
package counts as run.

Two more things are read:

- **Idle runner:** a runner declaration is idle when none of the projects it reaches holds a specification file.
  Idleness is judged once per declaration, not once per project. A runner declared once in shared build settings
  that several projects import is idle only when none of those projects holds a specification file.
- **Code-first specifications:** a project declares a code-first BDD framework. This counts as specifications being
  present, even with no feature file.

The denominator is F, the number of specification files in the population. Every file counts, whatever its state.

## Thresholds
- One unattached specification file is enough to cap the score (see Score).
- One idle runner declaration is enough to cap the score.
- Specifications are present when there is at least 1 specification file or a code-first BDD framework is declared.

## Score
1. **Base score.**
   - The base is **6.0** if there is at least one unattached specification file or at least one idle runner
     declaration.
   - Otherwise the base is **10.0** if specifications are present.
   - Otherwise the base is **6.0**.
2. **Loaded share.** Let U be the number of not-loaded specification files. If U is at least 1, the score is
   min(base, round(10 × (F − U) / F, 1)). The share is rounded to one decimal. An exact midpoint rounds to the
   even digit (9.25 gives 9.2, 9.75 gives 9.8).
3. If U is 0, the score is the base.

A repository whose specifications all run, with no idle runner, scores 10. A BDD framework with no specification
scores 6. The score falls below 6 only when more than 40 % of the specification files are not loaded. It reaches 0
when none of them is loaded.

## Not measured when
The repository has no specification file and no project declares a BDD framework (a Gherkin runner or a code-first
framework). BDD is optional, so a repository without it loses nothing.

## What the result is not
- It is not freshness. One stale specification file that a runner loads gives a 10.
- It is not pass state. It does not check whether scenarios pass, or whether a continuous-integration run executes them.
- It is not quantity or coverage. It does not count scenarios or steps, or check which behaviour they describe.
- It is not the quality of the specification text or of its step definitions.
- A score of 6 does not mean the behaviour is untested. It means at least one of these: a BDD framework is declared
  with no specifications; a specification file belongs only to projects with no Gherkin runner; a runner is declared
  where no specification file is; or about 40 % of the specification files are not loaded.
