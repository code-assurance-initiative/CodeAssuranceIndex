# D34: Knowledge Freshness

**Lens:** maturity · **Scored:** yes

## Property
Whether anyone still has living knowledge of each file, or it has been orphaned — last understood long ago by someone now gone quiet. The sibling of the bus factor: D16 asks who owns it, D34 asks whether anyone still knows it.

## Applies to
Any language. The dimension reads the repository's version-control history and matches it to production code files by
path. It does not depend on any language's syntax.

## Population
The population is the **significant files**. These are production code as [production-code.md](../production-code.md) defines it, with these
differences.

- **sbt and Gradle build definitions are in.** Build definitions of the sbt and Gradle build tools (written in Scala,
  Groovy or Kotlin) are in the population. Every other build script stays out, as [production-code.md](../production-code.md) says.
- **Examples, samples and demonstrations are left out.** This includes the authors' own example, sample, demo,
  proof-of-concept, sandbox and playground code.
- **Scaffolding templates are left out.** This is starter code that a generator in the repository copies out to its
  users, for example a project-creation tool's template folder. A product's own view or email templates stay in.
- **Constant enumerations are left out.** This is a file whose only declarations are enumerations of named constants
  (one or more). Each member is a bare name, optionally set to a literal value. The file has no function, type,
  implementation or module beside the enumerations, and no member computed by logic. A file can be a constant
  enumeration only if it is under a size limit and meets a member count and a member share. These are under Pending
  re-definition. A file that declares named constants in any other form stays in, as [production-code.md](../production-code.md) says.
- **Size floor.** A file is significant when it is at least 2,400 bytes. If no production file reaches 2,400 bytes and
  the repository has 10 or more production files, the floor is waived and every production file is significant.
- **Cap.** The cap is taken first: the 3,000 largest files by size in bytes that meet the size floor. Files that no
  commit read touched, and automation-only files, are then removed from those 3,000. Smaller files do not fill their
  places.
- **History.** A file is in the population only if at least one commit read touched it.
- **Automation-only files** are left out, as [people.md](../people.md) defines them.

The history is read as [people.md](../people.md) defines it: commits, authors, people, machine accounts and dates. A file keeps its
history across renames, so commits made under an earlier name count for the file under its current name.

## Unit and denominator
**Unit: an orphaned file.** This is a significant file whose living knowledge is below the orphan floor, and for which
no rescue applies (see Thresholds).

**Changes that need no understanding.** These touches of a file teach nothing about it:

- a merge (../people.md);
- a pure move or rename of the file;
- an edit that only changes whitespace, tool directives, imports, logging, one identifier's name, a licence header, a
  single value, or a stamp (for example a version or date);
- a comment-only edit, when the same commit makes comment-only edits to 3 or more files (a comment sweep).

**Knowledge a commit gives.** When a commit touches a file, it gives its author this much knowledge of that file:
`decay × focus × size`.

- `decay = 0.5 ^ (age / 182.625)`. Age is the number of days from the commit date to the moment of measurement, and is
  never negative.
- `focus = 1 / √N`, where N is the number of distinct files the commit changed.
- `size = min(1, √(L / 20))`, where L is the larger of the lines the commit added to the file and the lines it deleted
  from it. If the change has no line counts (for example a binary file), `size` is 1.

A commit gives no knowledge of a file in two cases. The first is when its change to that file needs no understanding
(above). The second is a **removal**: the commit adds fewer than 20 lines to the file and deletes at least 20 more
lines than it adds.

**Active people.** Activity is measured from the **reference point**. The reference point is the date of the newest
commit read, when that date is earlier than the moment of measurement and no more than 182.625 days before it.
Otherwise the reference point is the moment of measurement. An identity is **present** when its newest commit anywhere
in the repository is within 182.625 days of the reference point. It is **recently active** when that commit is within
90 days of the reference point.

**Living knowledge of a file:** the sum of the knowledge its present identities hold. Machine accounts hold knowledge
as [people.md](../people.md) says.

**Denominator:** the significant files, each weighted by its role:

- **Domain code: 1.0.** Code that models the business domain, for example entities, value objects, aggregates and
  domain events.
- **Infrastructure: 0.4.** Plumbing, for example persistence and data access, web and API endpoints and controllers,
  messaging, configuration, hosting, gateways and clients.
- **Every other file: 0.7.**

`orphanFraction = Σ weight(orphaned files) / Σ weight(significant files)`.

## Thresholds
- **Orphan floor.** A file is an orphan candidate when its living knowledge is below **0.25**. That is roughly one
  focused commit's worth of knowledge within the last year.
- **Counted commits.** For the rescues, a file's **counted commits** are all the commits read that touched it, except
  those whose change to it needs no understanding. A removal is a counted commit, even though it gives no knowledge.
  Age does not matter here.
- **Focused commit.** A counted commit that changes at most 25 files. A removal can be a focused commit.
- **Principal builder.** This is the identity with the largest **builder measure** on the file:
  - when the file has line counts, the measure is the lines changed (added plus deleted) over the file's counted
    commits, across its whole history and with no decay;
  - otherwise it is the sum of `focus` with no decay, taken over the file's focused commits. If the file has no
    focused commit, the sum is taken over all its counted commits.
- **Rescues.** An orphan candidate is not orphaned if any of these holds:
  1. **New file.** Its oldest commit read is less than 30 days before the moment of measurement.
  2. **Builder still here.** The principal builder is recently active.
  3. **Near peer still here.** An identity that changed at least half as many of the file's lines as the principal
     builder (over the counted commits) is recently active.
  4. **Recent material change.** The file's newest focused commit meets all three conditions: it changed at least 20
     lines of the file (added plus deleted), it falls within 182.625 days of the reference point, and its author is
     recently active.
  5. **Area change.** This applies only to a file with no focused commit. Take the file's newest counted commit that
     changed at most 100 files. The rescue holds when that commit's author holds at least half the principal builder's
     builder measure and is recently active.
  6. **Surviving lines.** In the file as it stands at the analysed commit, one author meets all three conditions: they
     wrote at least half as many of its current lines as its largest current author, they made at least one focused
     commit to the file, and they are recently active.
- **Minimum history.** At least 50 commits must be read.

## Score
`score = clamp(10 − 10 × orphanFraction, 0, 10)`

10 means no significant file is orphaned. Each orphaned file lowers the score by 10 × (its role weight ÷ the total
role weight of the significant files).

## Not measured when
- The repository has no version-control history.
- Fewer than 50 commits are read.
- The population is empty. Examples: a single-commit history; no source code at all; fewer than 10 production files,
  none of them reaching 2,400 bytes; or production code that is only tests, examples, scaffolding templates, constant
  enumerations, generated or vendored code.
- **History too condensed.** Before rescues, both of these hold: orphan candidates make up at least 0.5 of the weighted
  fraction, and the number of significant files is more than 3 times the number of commits read.
- **Activity contradicts the reading.** Before rescues, all of these hold:
  - there are at least 20 orphan candidates;
  - they make up at least 0.5 of the weighted fraction;
  - at least 30 commits read (any author, merges included) are within 90 days before the moment of measurement;
  - fewer than 50 significant files are not orphan candidates.

## What the result is not
- It does not measure understanding. It measures recent, meaningful commits by people still present. Code that is
  often read but seldom changed reads as orphaned.
- It does not tell stable, finished code apart from forgotten code, unless the person who built the file is still
  around.
- It does not say who owns a file. Concentration is D16.
- It does not cover small files below the size floor, examples, scaffolding templates, constant enumerations, or files
  beyond the 3,000 largest.
- Knowledge decays up to the moment of measurement, so the same commit can score differently when measured on a later
  day.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them, and a later decision under
decision 0013 will replace each with a threshold on the property.

- Knowledge half-life: 182.625 days. The same value is also the presence window, the recent-change window and the
  limit on how far back the reference point may move.
- Focus weight: `1 / √N`, where N is the number of files a commit changed.
- Size weight: `min(1, √(L / 20))`. The same 20-line bar applies to a removal and to a material change.
- Orphan floor: 0.25.
- Focused commit: at most 25 files. Area commit: at most 100 files. Comment sweep: 3 or more files.
- Recently active: within 90 days.
- Near peer: at least half the principal builder's lines (rescue 3) or builder measure (rescue 5). Surviving lines: at
  least half the current lines of the file's largest current author (rescue 6).
- New-file grace: 30 days.
- Size floor: 2,400 bytes. It is waived when the repository has 10 or more production files and none of them reaches
  the floor.
- Cap: the 3,000 largest files that meet the size floor. The cap is taken before files no commit read touched and
  automation-only files are removed, and smaller files do not fill the places of removed files.
- Constant enumeration: only a file smaller than 65,536 bytes can be a constant enumeration. A file of 65,536 bytes or
  more stays in the population even when it holds only enumeration constants. A smaller file is one when it has at
  least 8 constant members across the whole file, and those members make up at least 95 % of the file's code lines.
  Blank lines, comments, and the enumerations' declarations, braces, attributes and imports do not count as code lines.
- Role weights: domain 1.0, infrastructure 0.4, all other files 0.7.
- Condensed-history guard: 0.5 weighted fraction and more than 3 files per commit. Activity guard: 20 candidates, 0.5
  weighted fraction, 30 commits in 90 days, fewer than 50 files with living knowledge.
- Knowledge below 0.0001 from a single commit is dropped from living knowledge. That commit is still a counted commit.
