# R6: Tooling

**Lens:** productionReadiness · **Scored:** yes

## Property

Whether the project wires up each of test, lint and type-check runs: in a package.json script, judged by the command the script runs (for example eslint, tsc, vitest, jest or playwright) rather than by its name, so a script named test that runs no test tool does not count; or in a CI (continuous integration) workflow that invokes such a tool, so a tool run only in CI also counts. The presence of that wiring, not evidence that the checks run or pass.

## Applies to

Repositories with a JavaScript or TypeScript frontend declared in a package.json manifest. The frontend file kinds are JavaScript (`.js`, `.mjs`, `.cjs`, `.jsx`), TypeScript (`.ts`, `.tsx`) and single-file components (for example Vue or Svelte).

The wiring itself is not source code. It is read from the wiring sources listed under Population. A tool from any language counts once one of those sources runs it.

## Population

- **Frontend source:** production code as [production-code.md](../production-code.md) defines it, limited to the frontend file kinds. Unlike [production-code.md](../production-code.md), this dimension leaves out examples, samples, demonstrations, proofs of concept, sandboxes and playgrounds. Performance and load-test scripts are benchmark code and are out as well.
- **Manifests:** the project's own package.json files. These are the workspace root and its member packages, including members in folders the workspace itself declares. A manifest is out of scope when it sits in generated code, vendored code, build output, a hidden folder, an example, sample or demonstration (unless the workspace declares that folder as a member), or a test fixture or evaluation input (for example a sample project the repository's tests read).
- **Wiring sources:**
  - the `scripts` of every manifest in scope;
  - a repository-local script file that one of those scripts runs directly. This reaches one step only, for example `node scripts/check.mjs`;
  - the pipeline files of any CI system the repository configures (for example GitHub Actions, GitLab CI, Azure Pipelines or Jenkins);
  - the build recipes and task-runner files at the repository root (for example a Makefile, a Justfile or a Taskfile);
  - a package's own task-runner file or build recipe (for example a gulp file, a Grunt file or a package Makefile), when a script of that package or a CI step runs it;
  - a check wired into the build tool's own configuration (for example a linter or type-checker plugin in a bundler configuration, or a framework build that lints as it builds), when a script or a CI step runs that build. A run that only serves or watches does not count as a build.

  A comment line is not wiring.

## Unit and denominator

The unit is a **leg**. There are three legs, and each one is either wired or not wired for the whole repository:

- **Test:** something runs a test runner. For example vitest, jest, mocha, playwright, cypress, `node --test`, `go test`, `cargo test`, `pytest` or `dotnet test`.
- **Lint:** something runs a linter, or a formatter in check mode. For example eslint, stylelint, oxlint, `biome lint`, `prettier --check`, rubocop, ruff or `golangci-lint`. A task-runner target, build recipe or script counts when it runs a linter itself (for example a Makefile target that runs eslint).
- **Type-check:** something runs a static type checker or a type-checking compiler. For example `tsc`, `vue-tsc`, `svelte-check` or `astro check`. The compiler build or check of a statically typed language also counts (for example `go build`, `cargo check`, `dotnet build`), as does a gradual checker such as mypy or pyright. A task, recipe target or script counts when it runs a type checker itself.

A leg is wired when at least one wiring source in the population runs a tool of that kind. Every source is judged by the command it runs, never by its name. The placeholder `test` script that a package manager writes (it prints that no test is specified and exits with an error) runs no test tool and does not count.

There is no denominator. The legs are counted for the repository as a whole.

## Thresholds

- A leg counts when one wiring source runs one tool of its kind. One is enough.
- No minimum number of scripts, workflows or packages applies.
- The dimension is measured only from 5 frontend files upward (see Not measured when).

## Score

The score is the sum of the weights of the wired legs:

| Leg        | Weight |
|------------|--------|
| Test       | 3.4    |
| Lint       | 3.3    |
| Type-check | 3.3    |

The only possible scores are therefore 0, 3.3, 3.4, 6.6, 6.7 and 10. A score of 10 means all three legs are wired. A score of 0 means none is.

## Not measured when

- The repository has no package.json manifest in scope.
- The repository has fewer than 5 files of the frontend kinds. This count includes tests and test support as well as production code. Generated code, vendored code, build output, hidden folders, examples and demonstrations, and the other [production-code.md](../production-code.md) exclusions do not count.
- None of those files is production code, for example because every one is a test or build glue.

## What the result is not

- It is not evidence that the checks run, pass or block a merge. A wired test suite that cannot load still counts as wired.
- It does not judge how good, strict or complete the tests, the lint rules or the type checking are.
- It does not show which packages each leg covers. One wired package marks the leg wired for the whole repository.
- A tool run only from somewhere outside the wiring sources above is not seen. Examples are a CI system configured outside the repository, a script reached only through another script, or a manifest beyond the cap below. A missing leg may therefore be wired somewhere this reading does not look.

## Pending re-definition

These values are parameters of the existing reading's model, and today's scores depend on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Manifests read:** the 40 shallowest package.json manifests in scope, the workspace root first. Wiring that exists only in deeper manifests does not count.
- **File size:** a manifest, workflow, recipe or script file larger than 1,000,000 bytes is not read.
- **Leg weights:** 3.4 for test and 3.3 each for lint and type-check.
