# D16: Bus Factor

**Lens:** maturity · **Scored:** yes

## Property
Whether knowledge is concentrated in too few people (the "bus factor").

## Applies to
Any language. The dimension reads the repository's version history of production code, including what each commit changed in each file. The score does not depend on the structure of the code at the analysed commit.

## Population
- **History:** commits, people and machine accounts as [people.md](../people.md) defines them, including its automation-only file rule. A machine commit gives knowledge of files in the same way as a person's commit.
- **Files:** production code as [production-code.md](../production-code.md) defines it. This dimension also leaves out:
  - examples, samples, demonstrations, sandboxes and playgrounds (for example a folder of demo apps run by the project's own end-to-end tests);
  - scaffolding templates: starter code that the project's generator or project template copies out to its users (for example a project-creation tool's folder of starter files). A product's own templates that it uses at run time stay in;
  - test fixtures and test data in any folder.
- **Significant files only:** a file must be at least 2,400 bytes. The one exception: if no production file in the repository reaches 2,400 bytes and the repository has 10 or more production files, every production file is in scope.
- **Cap:** only the 3,000 largest files by bytes are read.
- A file that is in scope but holds no knowledge (every contribution below the negligible limit, see Unit) is in neither the numerator nor the denominator.

## Unit and denominator
**Knowledge of a file.** Each commit gives its author some knowledge of each file it changes:

`contribution = 0.5^(age / 182.625 days) × 1/√n × min(1, √(L / 20))`

- *age* is the time from the commit date to the reference time (see Pending re-definition).
- *n* is the number of distinct files of any kind that the commit changes. A file renamed during the history counts as one file under its current name.
- *L* is the larger of two numbers: the lines the commit added to the file and the lines it deleted from it. If there are no line counts (for example for a binary file), the last factor is 1.
- A contribution below 0.0001 is dropped.
- An edit that needs no understanding of the file gives no knowledge, but it still dates the file. These edits are: a pure move or rename of the file; a change only to whitespace, tool directives, imports, logging, one identifier's name, a licence header, one value, or a stamp; and comment-only edits in a commit that makes comment-only edits to 3 or more files.
- Removing content gives no knowledge of that file. A removal is a change that adds fewer than 20 lines and deletes at least 20 more lines than it adds.

A holder's knowledge of a file is the sum of the holder's contributions to it. A holder is a person or a machine account.

- **Top share:** the largest holder's knowledge divided by the file's total knowledge. The total counts all holders, including machine accounts and people who have stopped committing.
- **Living knowledge:** the file's knowledge held by holders (people or machine accounts) whose newest commit anywhere in the repository is no more than 182.625 days before the reference present (see Pending re-definition).

**Silo:** a file that meets all three conditions: its top share is at least 0.9, its living knowledge is at least 0.25, and its oldest commit read is at least 30 days before the reference time.

**Denominator:** every file in the population that holds knowledge. Each file is weighted by its role:
- domain code (the business model, for example entities, aggregates, value objects): 1.0;
- infrastructure code (for example persistence, adapters, web controllers, configuration, hosting): 0.4;
- all other production code: 0.7.

`siloFraction = Σ weight(silo files) / Σ weight(files holding knowledge)`

## Thresholds
- Silo: top share ≥ 0.9.
- Silo: living knowledge ≥ 0.25.
- Silo: the file is at least 30 days old.
- Minimum history: 50 commits read, machine commits included.
- Carrying set: the smallest group of people that covers at least 80 % of people's commits, taking people in order of commit count, largest first.
- Condensed history: siloFraction ≥ 0.5 and more analysed files than 3 × the commits read.

## Score
`teamFactor = clamp((people − 1) / 4, 0.25, 1.0)`, where *people* is the number of distinct people in the commits read.

`score = clamp(10 − siloFraction × 10 × teamFactor, 0, 10)`

A score of 10 means no weighted file is a silo. In a team of 5 or more people, a silo file costs its full weight. In a team of 2, it costs a quarter of its weight.

## Not measured when
- The repository has no version history, or no commits could be read.
- The commits read come from one person or from no person.
- The carrying set is one person, at any commit count. If the other people average at least 5 % of people's commits each and at least 50 commits were read, the result is reported as a finding (one person carries the repository). It is still not scored.
- Fewer than 50 commits were read.
- No file in the population holds knowledge. Examples: a dormant repository, a repository with no source, or a repository with fewer than 10 production files and none of at least 2,400 bytes.
- No analysed file has living knowledge of at least 0.25 (the repository is dormant).
- The history is condensed: siloFraction ≥ 0.5 and the analysed files outnumber 3 × the commits read (for example a squashed or imported history).

## What the result is not
- It does not measure understanding. Knowledge passed on through pairing, review or documentation does not show in the history.
- It is not line authorship at the analysed commit (blame). A broad refactor that rewrites a file does not take ownership of it.
- It is not the classic count of how many people would have to leave. It is a weighted share of files whose knowledge sits with one holder.
- It does not judge stale knowledge. A file that nobody still understands belongs to knowledge freshness (D34), not to this dimension.
- It does not verify identities ([people.md](../people.md)).

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them. A later decision under decision 0013 will replace each one with a threshold on the property.
- **Decay:** a half-life of 182.625 days.
- **Breadth down-weight:** 1/√n per file, for a commit that changes n files.
- **Change-size weight:** min(1, √(L / 20)). Content removal: fewer than 20 lines added and at least 20 net lines deleted. Comment sweep: 3 or more files.
- **Negligible contribution:** below 0.0001.
- **Living knowledge:** at least 0.25, counted over holders active within 182.625 days.
- **Reference time:** the time of analysis. The reference present for activity is the repository's newest commit if that commit is no more than 182.625 days older than the analysis. Otherwise it is the time of analysis.
- **Minimum file age:** 30 days.
- **File size floor:** 2,400 bytes. It does not apply to a repository with 10 or more production files of which none reaches 2,400 bytes.
- **Cap:** the 3,000 largest files.
- **Role weights:** domain 1.0, other 0.7, infrastructure 0.4.
- **Team factor:** (people − 1) / 4, kept between 0.25 and 1.0.
- **Carrying set:** 80 % coverage. The other people count when they average at least 5 % of people's commits each.
- **Condensed history:** a siloFraction of 0.5 and a ratio of 3 files per commit.
