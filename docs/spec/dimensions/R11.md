# R11: Import Boundaries

**Lens:** architecture · **Scored:** yes

## Property
Whether imports in the frontend code respect the boundaries of the architecture layout the code follows, either a feature-sliced layout (code split into ordered layers, each split into slices by feature or business area, where code in a slice may import from its own slice and from lower layers, never from another slice of its own layer, and reaches another slice only through that slice's public entry point) or a layered src directory (where a layer imports only from the layers it is built on); and whether one package imports another package's internal files instead of its public entry point (a deep import).

## Applies to
Frontend code:
- JavaScript and TypeScript, including JSX and TSX and their module and CommonJS forms.
- Vue and Svelte single-file components.

Stylesheets (CSS and its preprocessor dialects) count only for the installed-dependency case of rule 6. Package manifests (for example `package.json`) are read for package names, entry points, exports and dependencies. The manifests are not judged.

## Population
- **Files read:** the frontend files of production code as [production-code.md](../production-code.md) defines it, with these differences:
  - **Test code is in.** Tests count in the denominator, and the layout rules judge them. Rule 11 judges only test code.
  - **Examples are mostly out.** Examples, samples, demonstrations and benchmark trees are out. The exception is code in them that the product itself imports.
- **Importers judged by rules 6 to 12:** production code only. These rules never judge test code, test setup files, tool configuration files, files in a tool's hidden folder (for example `.storybook`), type declaration files, or test step glue (for example Cucumber steps). Rule 11 is the exception: it judges only test code.
- **Layouts:** a package follows a layout through the direct subfolders of its `src` folder (see Pending re-definition). Each package is judged by its own layout. The repository root counts as a package.

## Unit and denominator
**Unit: a boundary breach.** A breach is one import site (importing file and line) that breaks one of the rules below. A breach counts once per target and rule, so an import that breaks two rules counts twice. A "type-only" import names only types.

**Feature-sliced layout.** The layers, from highest to lowest, are `app`, `processes`, `pages`, `widgets`, `features`, `entities` and `shared`. A slice is a folder directly under a layer. The files directly in a layer folder form one group, the layer's root group.

1. **Upward import:** a file imports a strictly higher layer. A file in `shared` breaks this rule by importing any other layer. Type-only imports count.
2. **Cross-slice import:** a file imports another slice of its own layer, or that layer's root group. This rule does not apply in `app` or `shared`. Type-only imports count. The exception is a type-only import through the target slice's `@x` cross-import folder.

**Layered src.** The rings, from innermost to outermost, are:
- domain;
- application (also called use cases);
- outer: infrastructure (also infra), adapter or adapters, persistence, presentation, ui, api and web.

A folder's ring is the ring its name's words denote. A name that denotes two rings has no ring.

3. **Upward import:** a file imports a file in a ring further out than its own. That is, domain imports application or outer, or application imports outer. Files in the same ring may import each other, and different outer-ring folders may import each other. Type-only imports count.
4. **Upward import through a re-export:** a file in a ring imports a name from a module that is in no ring, and that module re-exports the name from a ring further out than the importer's own.
5. **Package upward import:** production code of a workspace package whose name denotes a ring imports a package in a ring further out than its own. Type-only imports count. This rule does not depend on any `src` layout.

**Any layout, including none:**

6. **Relative cross-package import:** production code reaches another named package by a relative path. This includes:
   - asset files (for example `../other/src/theme.scss`);
   - any relative path through an installed-dependency folder (for example `../../node_modules/x/y.css`), also from a stylesheet.

   It does not count in three cases:
   - the two folders belong to one published package;
   - the target is a workspace root that publishes nothing;
   - the importing module names its own dependencies by URL or registry prefix (for example `https://…`, `jsr:` or `npm:`, as Deno modules do), and the path resolves to a file the target package's manifest declares public: its main, module or types entry, or an exports key or value.

   Type-only imports count.
7. **Deep import:** production code imports a subpath of a package in this repository whose manifest declares exports, and those exports do not include that subpath. A subpath that an exports pattern matches counts as declared. Type-only imports count.
8. **Third-party deep import:** production code imports a subpath into the build output or internals of a declared third-party dependency (for example `pkg/dist/x`). Asset files do not count. Only runtime imports count.
9. **Undeclared workspace dependency:** a workspace package that publishes an entry point and keeps a dependency list imports a sibling workspace package by name at runtime, but does not list that sibling. This does not count for a package whose published manifest is generated when the package is packed.
10. **Application's undeclared workspace dependency:** this rule covers a workspace package that meets all three conditions:
    - it publishes no entry point;
    - it keeps a runtime dependency list (dependencies, peer dependencies or optional dependencies);
    - it already lists some other workspace sibling in one of its dependency lists.

    The breach is an import of a sibling's public entry by exact name when no dependency list names that sibling. The sibling must publish an entry point and must not depend on the importer. Only runtime imports count. This does not count for a package whose published manifest is generated when the package is packed.
11. **Test code into another package's internals:** test code of a named package uses a relative path to reach production code of another package that publishes an entry point. It does not count when the target is a path that the target package's manifest declares public. Only runtime imports count.
12. **Production code depending on the test suite:** production code imports either of these at runtime:
    - by relative path, a module of a test suite that is not below the importer's own folder;
    - by name, a workspace test kit. A test kit is a package that the tests import and that either only development dependencies consume or whose code is mostly test code.

    For this rule, scripts that drive the product's built output (for example conformance or end-to-end checks) count as test code.
13. **Declared rule:** an import that the repository's own boundary rules forbid (for example dependency-cruiser forbidden rules, Nx dependency constraints, or eslint-plugin-boundaries element rules). It counts only at an import site that none of the rules above already counted.

**Denominator (the first case that applies):**
- If any package follows a layout: the frontend files under the `src` folders of the packages that follow a layout.
- Otherwise: all frontend files read.

The numerator counts breaches anywhere in the repository, whichever denominator applies.

## Thresholds
- Every breach counts. There is no minimum size and no severity weight.
- Pending re-definition lists the minimum number of frontend files and the thresholds that decide whether a package follows a feature-sliced layout or a layered src.

## Score
r = breaches × 100 / denominator (breaches per 100 files).

score = clamp(10 − 1.2 × r, 0, 10)

- 0 breaches gives 10.
- The score reaches 0 at about 8.33 breaches per 100 files.
- If there are breaches but the denominator is 0, then r = 0.5 × breaches.

## Not measured when
- The repository has fewer than 5 frontend files (see Pending re-definition).
- None of its frontend files is production code, for example when all of them are tests or test support.
- The repository has no package manifest, and every production frontend file is one of the authors' own developer tools.
- No package follows a layout and there are no breaches. The dimension is then not applicable and is not scored, rather than scored 0.

## What the result is not
- It does not count an import into a lower-layer slice's internal files that skips that slice's public entry. Only same-layer and upward imports count.
- It does not score loops between slices as loops. Only the individual imports that form a loop change the score.
- It does not count file-level import cycles. Another dimension covers those.
- It does not cover a bespoke layout. A layout that matches neither layout's folder names is judged only by rule 5 (when package names denote rings) and rules 6 to 13. A layout that uses those names in another sense can read as breaking rules it never adopted.
- It does not judge whether the chosen layout is good, only whether imports respect it.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Minimum size:** the dimension is measured only when the repository has at least 5 frontend files.
- **Feature-sliced layout:** a package follows it when all of these hold:
  - its `src` has at least 2 of the 7 layer folders as direct subfolders;
  - at least one of those is `processes`, `widgets`, `features`, `entities` or `shared`;
  - its layer folders outnumber its other direct subfolders.

  This test comes before the layered src test.
- **Layered src:** a package follows it when its `src` has at least 2 of `domain`, `application`, `infrastructure`, `presentation`, `ui` and `api` as direct subfolders, or has subfolders that name at least 2 different rings.
- **Package rings:** rule 5 applies only when the workspace's package names denote at least 2 different rings. A package's ring comes from the last segment of its name, or else from its folder name.
- **Re-export chains:** rule 4 follows a name through at most 8 re-export steps beyond the imported module.
- **Build output and internal folders (rule 8):** a subpath whose first folder is `dist`, `build`, `out`, `lib`, `src`, `internal`, `internals` or `private`.
- **Test kit by its code (rule 12):** a package in which more than half of the production modules load a test-only package at runtime, or import a module of the same package that does.
