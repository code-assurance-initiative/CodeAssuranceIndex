# X6: Hand-rolled structured-format parsing

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property
Whether JSON or XML text is parsed by hand with regular expressions or string operations (for example pulling a value out by matching its key or tag), while a dedicated parser for that same format (for example a parsing library, or the language's standard-library module) is already referenced in the same project or build unit (for example a package or module), as a dependency or by an import in its code: a common source of silent data bugs.

## Applies to
Any programming language that can match text with regular expressions or cut strings. The formats are JSON and XML. Tag-shaped markup counts as XML, so a parser of XML or of HTML counts as a parser for it.

## Population
Production code as [production-code.md](../production-code.md) defines it. This dimension adds no exclusions of its own.

The parser condition is checked within one build unit, for one language and one format:

- **Build unit:** the package or module the file belongs to. This is the nearest directory above the file that holds a build or package manifest (for example a project file, `package.json`, `go.mod`, `Cargo.toml` or `pyproject.toml`). Where there is no manifest, the build unit is the whole repository.
- **Same format:** a JSON parser counts only for hand-rolled JSON parsing. An XML or HTML parser counts only for hand-rolled XML parsing.
- **Same language:** the parser counts only when code in the site's own language, in the same build unit, references it. A parser that code in another language in that build unit references does not count.
- **Platforms that provide both parsers:** in C#, F# and Visual Basic .NET the platform provides a JSON parser and an XML parser. A parser of each format is therefore treated as always referenced, and a site in these languages needs no parser in use.
- **Every other language:** the parser counts when the build unit references it. That means the build unit declares the parser as a dependency, or its code in the site's language imports or calls it. A parser that ships with the language counts only when that code imports or calls it (for example a call to a built-in JSON parse function). Being available is not enough.

## Unit and denominator
**Unit:** one hand-rolled parse site. A site is one pattern or one searched-for literal used to read a value out of JSON or XML text. The pattern can be a regular expression, or the literal can be a key or tag searched for in a string. A site meets all four conditions below.

1. **The literal spells the format's syntax.** For JSON, a quoted key name followed by a colon. For XML, an element tag: a start tag, an end tag, or a start tag with an attribute.
2. **The text is a JSON or XML document, and a field of it is read.** A pattern that only finds a whole JSON object or XML document so that a parser can read it is not a site. A pattern over text that is not a JSON or XML document is not a site either, for example a log or progress line that only quotes a name in JSON style.
3. **It extracts.** The pattern matches or captures a value. Code can also extract by finding the key or tag in a string and then, in the same function, cutting the value out of that same string. For example, it takes a substring or slice from the found position, or it splits the string at the key and picks one piece.
4. **It does more than strip or divide.** A pattern used only to replace text (for example to remove markup tags) is not a site. A split that keeps every piece is not a site. A split at both the start tag and the end tag of the same element is a site, because it cuts out that element's content. A search that only finds a position (for example to insert text there) is not a site.

A pattern stored under a name (for example a compiled pattern, a constant or a field) is judged by how that name is used. If every use only strips or divides, it is not a site. If any use extracts, it is a site.

Each site counts once. There is no cap.

A file that cannot be read is listed as unread and is not treated as clean. The other files are still read, and the result covers the files that were read.

**Denominator:** none. The result is the list of sites and their count.

## Thresholds
- A site counts only where the parser condition under Population holds for the site's format, language and build unit.
- No count or share threshold applies. A single site is a finding.

## Score
No score curve is defined: the one existing engine reports findings only, with no 0-10 reading.

## Not measured when
- The repository has no production code.
- No in-scope file can be read.

## What the result is not
- It is not proof that a parse is wrong. It flags parsing that silently misreads a document that is reordered, re-spaced or typed differently, where a parser would fail loudly.
- It does not cover formats other than JSON and XML (for example CSV or YAML).
- Outside C#, F# and Visual Basic .NET, it says nothing about a build unit whose code in the site's language does not reference a parser of the format. Hand-rolled parsing there is not a finding.
- From the code alone, some text delimited by tags cannot always be told apart from XML, so such a site may be reported. Examples are a language model's tagged reply, or rendered HTML split at both tags of an element.
- It does not judge whether a full parser is the better choice for a given input, for example a trusted fragment of fixed shape.
