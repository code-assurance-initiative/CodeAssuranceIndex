# DM10: One transaction, one aggregate

**Lens:** domainModelling · **Scored:** yes

## Property

Whether a single operation mutates more than one aggregate root. An aggregate is a consistency boundary, so saving two together fuses them into one — the second's invariants come to depend on the first's transaction, and the pair can no longer be separated. Reads of other aggregates are not counted.

## Applies to

Any language in which code saves domain objects to storage, for example through repositories, a document session or a database context.

## Population

The population is production code as [production-code.md](../production-code.md) defines it, with one more exclusion:

- **Data seeding:** code whose job is to fill a store with fixed starting data or fixture data, for example a data seeder. This code has no consistency boundary to keep, so its writes are not operations under this rule. They are not counted as violations and are not in the denominator.

This dimension applies only to a repository that models its domain with aggregates. Its production code must declare a domain model in the domain-driven style: aggregate roots or entities with identity, together with things such as value objects, domain events, repositories for those roots, or a separate domain layer. A repository whose code has no such model (for example a library of building blocks, or a script collection) is outside this dimension.

## Unit and denominator

**Operation.** An operation is a callable with a body that runs as one unit of work. That is a method, or a request handler that is defined inline and registered to run on its own for each request (for example a route handler passed to a route registration). Such a handler is its own operation and is not part of the method that registers it. Any other anonymous function belongs to the operation that encloses it.

**Write.** A write is a call by which the operation creates, changes or deletes saved state (for example add, update, save, remove, delete, insert, store) through a persistence boundary. Examples of a persistence boundary are a repository, a store, a data-access framework's session or set, or a unit-of-work port. Reads (get, find, load, query, list, count, any) are never writes.

**Committing is not a write.** Committing a unit of work (for example saving all tracked changes of a database context) is not a write in itself and goes through no boundary of its own. Its only effect is that the change-tracked commands in the same operation count as writes.

**Change-tracked command.** A change-tracked command is a state-changing command on a loaded aggregate root, made in an operation that also commits the unit of work tracking that root. It is a write. Commands made in code the operation calls count too, when that code receives the root from the operation, or works on the operation's own unit of work without committing it itself. A change-tracked command goes through no persistence boundary.

**What a write saves.** A write saves the type of the domain object it passes. If a write passes only an identifier, a plain value or an enumeration value, it names no saved type.

**One persistence boundary.** Two writes go through the same persistence boundary when they go through the same kind of persistence object, whatever entity type it is declared for. For example, two sets of one database context are one boundary, a database context and its own sets are one boundary, and one generic repository type used for two entity types is one boundary. Two different repository types are two boundaries.

**Not a second aggregate.** These writes are left out of both counts below. A persistence boundary that carried only these writes is left out as well:

- A record of a message stored beside a root, for example a transactional outbox row built from an event.
- A side table of a root that the same operation also saves. This is a type with no identity of its own, keyed by that root's identity. It is the same aggregate stored in another table, so it counts as that root and not as a second type. A side table whose root the operation does not save counts as a saved type like any other.

**Unit:** a writing operation, meaning an operation with at least one write.

**Denominator:** all writing operations in the population.

## Thresholds

A writing operation has two counts. They are kept separate and never combined:

- **(a) Saved types:** the distinct types its writes save. An entity that another saved type reaches through its own collection (directly or through further collections) is inside that root's boundary, so it is not counted separately. If two types each reach the other, both are counted.
- **(b) Persistence boundaries:** the distinct persistence boundaries its writes go through. Every write that goes through a boundary counts, whether or not it names a saved type. Change-tracked commands and commits are not in this count.

A writing operation is a **violation** when count (a) is **2 or more**, or count (b) is **2 or more**. Otherwise it is **clean**. For example, saving an Order through an order repository and deleting a customer by identifier through a customer repository is a violation, because the writes go through 2 boundaries. Adding an entity and deleting another by identifier through the same repository is clean. Adding an Order to a context's order set and then committing the context is clean.

## Score

```
clean share = (writing operations − violations) / writing operations
score       = 3 + 7 × clean share
```

The score is rounded to 2 decimals. A score of 10 means every writing operation mutates one aggregate. The lowest score is 3, reached when every writing operation is a violation. The curve is linear between them. The rule has a recognised deliberate exception, so a few violations among many clean operations lower the score in proportion and do not fail it.

## Not measured when

- No operation in the population writes. The rule then has nothing to judge, for example in a read-only codebase.
- The repository does not model its domain with aggregates (see Population).

## What the result is not

- It does not tell a deliberate exception from an accident. Saving two aggregates together on purpose, for example to keep one value consistent in both, counts the same as doing it by mistake.
- It does not count reads. Loading a second aggregate for context is normal and costs nothing.
- It is not a count of aggregate instances. Saving two orders in one operation saves one type.
- It does not judge whether the aggregate boundaries are drawn well. It only judges whether operations respect the boundaries the code declares.
- It is not a check of transactions at run time. It reads what one operation writes and commits in the code.
