# P2: Observability

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether the code is diagnosable in production — structured logging, tracing/metrics, health checks.

## Applies to
Any programming language in production code. Markup (HTML) and styles (CSS) are not read. The dimension applies to a repository that ships a process: something that runs as a program or a service. It does not apply to a repository that only ships libraries for others to host (see Not measured when).

## Population
Production code as [production-code.md](../production-code.md) defines it. In addition, this dimension leaves out:

- **Examples, samples and demonstrations**, because nothing in them is operated in production.
- **Files generated by the build**, for example designer files and files the build writes into its output folders. These are already outside production code; they are named here because they never count as logging, as executable behaviour or as I/O.

Comments and string literals are not code. A comment or a quoted string that names a logger, a tracing library or a health check does not count as using it.

## Unit and denominator
**The unit is a project:** one unit of the build that declares itself, for example a .NET project file, a `package.json`, a `Cargo.toml`, a `go.mod`, a Maven or Gradle build, a `pyproject.toml`, together with the production files it holds. A project built for several targets (for example several framework versions) counts once. Its signals are combined across the targets, so a project that logs under only one target counts as logging.

Each project is read for these properties:

- **Logs:** some code in the project emits a log record. This covers a call to a logging framework, a call to the repository's own logging facade or wrapper, a write through the platform's trace or diagnostics writer, a game engine's log call, code that configures the logging pipeline for the application, an invoked log callback that the host supplies, and an event written through a diagnostics source the host can subscribe to (for example an event source or an activity source). A write to the console is not logging.
- **Console-channelled:** the project logs, and a service-shaped file in it also reports through the console. A service-shaped file declares a hosted or background service, a request or message handler, a controller, or a type named as a service, handler or endpoint. Console writes do not count when they report why the process is ending (a top-level catch, an unhandled-exception handler, a command-line framework's exception handler), when they are debug-only, or when console output is the file's purpose.
- **Executable behaviour:** the project contains behaviour that could reasonably log, for example a program entry point, a web endpoint, a request or message handler, a hosted service, a database context or an HTTP client. A project that only declares data shapes (contracts, DTOs, models, events, abstractions, entities, value objects) does not have it.
- **Operated:** the project ships a process of its own, according to its own declaration (for example an executable output type or a declared entry point).
- **Own I/O:** the project performs I/O on a resource it creates itself, for example files, directories, sockets, database connections or an HTTP client it constructs. An HTTP client handed in by the host is not own I/O.

**The denominator is the service-like projects.** A project is service-like when it logs. A project that does not log is service-like only when it has executable behaviour and is either operated or has own I/O. If a project's declaration cannot be read, the project counts as operated.

**Repository-wide signals:**

- **Any logging:** at least one production project logs.
- **Tracing/metrics:** some production code uses a tracing or metrics instrument, for example OpenTelemetry, an activity source or a metrics registration, or a project declares such a dependency.
- **Health checks:** some production code registers or exposes a health check, for example a health-check endpoint that an orchestrator or load balancer can probe.

## Thresholds
- A project logs if one call anywhere in it emits a log record. One file is enough.
- A project is console-channelled if one service-shaped file has one console write that counts.
- Tracing/metrics and health checks are each present if one use appears anywhere in production code.
- **User-launched binary:** every process the repository ships is launched by its user (a command-line tool, a desktop application or a game), none is a web API, web application, worker or service, and nothing in the repository hosts a web server.

## Score
```
breadth = (service-like projects that log − console-channelled service-like projects) / service-like projects
          (0 when there are no service-like projects)

score   = 4 × [any logging] + 3 × breadth + 2 × [tracing/metrics] + 1 × [health checks]
```

Each bracket is 1 when the signal is present and 0 when it is absent.

For a user-launched binary without health checks, health checks do not apply, so the score is `score × 10 / 9`. A user-launched binary that does register health checks keeps the plain sum.

The result is rounded to one decimal and clamped to 0-10.

## Not measured when
- **Library only:** the repository ships libraries for others to host and no process it operates. It is not a web API, web application, worker or service, and it deploys no service.
- **Static browser application:** the only thing that would run is a browser application that is built to static files and served by a web server or CDN, so there is no server process.
- **Template or exercise:** the repository is a starter template or an exercise (for example a kata) and shows none of logging, tracing/metrics or health checks. A template that shows any of them is scored.
- **Product not read:** the engine cannot read the language that holds the repository's product, or the product's projects failed to load. This is reported as the engine's gap, not as a score of 0.

## What the result is not
- It measures presence, not runtime quality. Telemetry that is configured but broken reads the same as telemetry that works.
- It does not check that logs are structured. Any logger counts, including plain-text trace writes.
- It does not measure logging coverage within a project. One logging call makes the whole project count as logging.
- Tracing/metrics and health checks are repository-wide yes/no signals, not per service.
- It does not judge log levels, message content, the handling of sensitive data in logs, or alerting.
