# D40: Network Egress Confinement

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether Kubernetes workloads restrict network EGRESS with a NetworkPolicy (or Cilium policy), limiting where a compromised pod can send data or reach a command-and-control server. Presence of committed egress-restricting policy, not runtime enforcement.

## Applies to
Any language. The dimension reads the repository's committed Kubernetes manifests written in YAML (files ending `.yaml` or `.yml`), not its source code. A YAML file may hold several documents, each one resource. Each document is read on its own.

## Population
The population is the repository's own Kubernetes manifests: the workloads and network policies that the project itself deploys. These manifests are configuration, not production code, so [production-code.md](../production-code.md) does not decide which files are in scope. It is used here only for the meaning of the categories below.

In scope:
- **Workloads:** resources that run containers from a pod template. Examples are a Deployment, Pod, DaemonSet, StatefulSet, ReplicaSet, Job, CronJob or a progressive-delivery Rollout. Any other resource that declares a pod template with containers also counts, for example a serverless Service or a workflow. A cluster-governance resource that only describes pods (for example an admission policy's pattern) is not a workload.
- **Network policies:** a Kubernetes NetworkPolicy, or a network policy of a cluster networking layer (for example a Cilium NetworkPolicy or ClusterwideNetworkPolicy, or a Calico NetworkPolicy or GlobalNetworkPolicy).

Not in scope:
- Tests and test support, including test fixtures and golden expected-output manifests.
- Examples, samples, demonstrations and benchmarks. A manifest in such a tree is sample input, not something the project deploys. Production code includes these trees, but this dimension does not.
- Documentation, including example manifests in a documentation tree.
- Build output, tool state and vendored third-party content, for example a copied-in third-party chart.
- A manifest that only appears as text inside another file or resource. Examples are a manifest in a script string, or a pod spec stored as data in a ConfigMap.

## Unit and denominator
The unit is the repository. Two controls are checked, each present or absent:

1. **Network policy:** at least one network policy is in the population.
2. **Egress restriction:** a network policy in the population restricts egress, and no egress rule in the population is open.
   - A policy restricts egress when it applies egress rules: it lists Egress among its policy types, or it has egress rules that it applies.
   - An **open egress rule** allows both every address and every port:
     - **Every address:** it names no destination, or an empty destination list. It also counts if one destination is all addresses (`0.0.0.0/0` or `::/0`) with no exceptions, or the "world" or "all" entity.
     - **Every port:** it names no port, or one entry has no port number, or one entry covers the whole range 1 to 65535.
   - A rule narrowed by a selector of pods or namespaces, a service, a domain, a specific address range, an exception list or a port is not open.

The denominator is the 2 controls. `present` is the number of controls present, from 0 to 2. Egress restriction can only be present when a network policy is, so `present` is 0, 1 or 2.

## Thresholds
- A control is present or absent. Nothing is partly present.
- One open egress rule anywhere in the population removes the egress-restriction control.
- An address range counts as "every address" only when it is exactly `0.0.0.0/0` or `::/0` with no exceptions. A port range counts as "every port" only when it starts at 1 or below and ends at 65535 or above.

## Score
`score = clamp(6.0 + 4.0 × present / 2, 6.0, 10.0)`

| Controls present | Score |
|---|---|
| none | 6.0 |
| network policy only, or a policy with an open egress rule | 8.0 |
| network policy that restricts egress, with no open egress rule | 10.0 |

The curve leans toward reward. 6.0 is a neutral floor and the score never goes below it, so a repository with workloads and no egress control is not punished below 6.0.

## Not measured when
The population holds no Kubernetes workload. The result is then "not applicable", not a score, because egress may be controlled at the platform or firewall layer outside the repository.

## What the result is not
- It does not show that the cluster enforces the policy. It reads committed manifests, not a running cluster.
- It does not show that every workload is covered. One policy that restricts egress for some workloads counts for the whole repository.
- It does not see egress control that lives outside the repository. Examples are a cluster-wide policy applied by a platform team, a service mesh, or a cloud firewall.
- It is not a judgement on how narrow the allowed destinations are. Only a rule open to every address on every port counts against the score.
- It does not cover baseline container misconfiguration (for example running as root or privileged containers). Another dimension scores that.
