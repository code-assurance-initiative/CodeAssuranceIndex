# X21: Side-effecting pattern guard

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property

Whether a pattern-match guard (in C#, the `when` clause of a switch case or switch-expression arm) is free of side effects: a guard that increments, decrements or assigns while deciding whether its arm matches applies that change during pattern matching, on an arm that may not be selected, and skips it entirely when it sits where a short-circuiting operator in the guard can skip it (the right operand of and, or or null-coalescing, a branch of a conditional, or after a null-conditional access) and that operator answers first.

## Applies to

Any language with a switch or match construct that runs an expression while it decides which arm to take, where that expression can change state.

A **guard** is an expression that a match arm or case label runs to decide whether its arm is taken. There are two kinds:

- **A separate guard clause on an arm** (for example a C# `when`, a Rust or Scala `if`, or a Python `case ... if`). That clause is one guard. In these languages an arm without such a clause has no guard and is not counted.
- **An arm whose own condition is an arbitrary expression** that the language runs while choosing an arm (for example a JavaScript or PHP `case`, a Ruby `when`, a Kotlin branch, an Elixir `cond` clause, or a Visual Basic `Case`). In these languages every label or arm except the default one is a guard, whether it is a constant or not. A label or arm with several conditions is one guard.

A default arm (for example `default`, `else`, `Case Else`, or a `cond` clause whose condition is the literal `true`) has no guard.

For example:

- **C#:** the `when` clause of a `case` label or of a switch-expression arm.
- **Java:** the `when` guard of a `case`.
- **Python:** the `if` guard of a `case`.
- **Dart:** the `when` guard of a switch case, a switch-expression arm or an if-case.
- **Rust:** the `if` guard of a `match` arm, including the guard of `matches!`.
- **Scala and Haxe:** the `if` guard of a `case`, including a `case` of a Scala `catch`.
- **F# and OCaml:** the `when` guard of a match rule (of `match`, `function` or `try ... with`).
- **Swift:** the `where` clause of a `case`.
- **Ruby:** the `if` or `unless` guard of an `in` pattern, and each `when` clause's conditions (also in Crystal).
- **JavaScript and TypeScript** (including the script of single-file components, for example Vue or Svelte): each `case` label.
- **PHP:** each `case` label, and each arm's conditions in a `match`.
- **Kotlin:** each branch's conditions in a `when`, including the branch's `if` guard.
- **Groovy:** each `case` of a `switch`.
- **Visual Basic .NET:** each `Case` clause's values in a `Select Case`.
- **Go:** each `case` of an expression switch.
- **Elixir:** each clause's condition in a `cond`.

Go, Swift and Visual Basic .NET do not allow an increment or an assignment inside a condition. In these languages a guard can change state only through a call.

Erlang guards and Elixir `when` guards are not counted: the compiler accepts only guards without effects. In C, C++ and Objective-C a `case` label is a constant, so the dimension does not apply to them. It does not apply to Erlang either.

## Population

Every guard, as Applies to defines it, in production code as [production-code.md](../production-code.md) defines it. A guard is in the population whether it changes state or not.

A guard on a rule of an exception handler that pattern-matches the exception is in scope (for example F# or OCaml `try ... with`, or a Scala `catch` case). A filter attached to a catch clause rather than to a match arm (for example C#'s `catch (E) when (...)`) is not.

## Unit and denominator

**Unit:** a side-effecting guard. This is a guard with at least one mutation in a skippable position (see Thresholds). A guard with several such mutations counts once.

A **mutation** is a change that the guard makes while it runs, to state that outlives the guard's arm:

- an increment or a decrement, prefix or postfix;
- an assignment of any kind, for example `=`, a compound assignment such as `+=` or `??=`, Python's `:=`, or PHP's `.=`;
- a call made by the guard that changes such state, for example passing state as a `ref` or `out` argument, calling a method whose body writes a field, adding to or removing from a collection, or sending a message.

These are not mutations:

- A change to a variable that the arm's own pattern declares, or that the guard itself declares. Such a variable cannot outlive the arm.
- A change inside a function that the guard builds but does not run, for example a callback stored for later, or a method of an object the guard constructs. A function that the guard passes to a call that runs it during the guard is part of the guard. For example, `b => seen.Add(b.Id)` in `items.All(b => seen.Add(b.Id))` is part of the guard.

**Denominator:** the number of guards in the population.

## Thresholds

- A mutation counts only when it is in a **skippable position**, meaning an operator inside the guard can skip it:
  - the right operand of a short-circuiting (conditional) and or or, for example C#'s `&&` and `||`, Visual Basic's `AndAlso` and `OrElse`, or Python's `and` and `or`;
  - the right operand of a null-coalescing operator;
  - either branch of a conditional expression;
  - anything after a null-conditional access.
- An operator that always runs both operands, for example a non-short-circuiting `&`, `|`, `And` or `Or`, does not make a mutation skippable.
- A mutation that runs every time the guard runs (for example `when ++n >= max`) does not count.
- Only the guard's own operators decide. These do not make a mutation skippable:
  - an earlier arm or label that matches first;
  - an earlier condition in the same guard's list that matches first (for example `a` in `Case a, b`, `a, b ->` or `when a, b`).

## Score

Let F be the number of side-effecting guards and P the number of guards. Then:

- N = max(P, F + 1)
- d = F / N
- isolation = max(0, 1 - d / 0.10)
- headroom = min(1, log10(N) / log10(200))
- ceiling = 6 + 2 × isolation × headroom
- score = 1 + (1 - d) × (ceiling - 1), rounded to two decimals

If F = 0, the score is 10. If F is 1 or more, the score is between 1 and 8, and before rounding it is above 1. Once 10 % or more of the guards are side-effecting, the score is at most 6.

## Not measured when

- The production code has no guard. For example, the repository has no switch or match constructs, or its production code is only in Erlang, C, C++ or Objective-C. The dimension is then not measured, which is different from scoring 10.

## What the result is not

- It is not a finding about mutations that a guard runs every time. These happen once for each guard tried, a reader can predict them, and some code counts this way on purpose.
- It is not a finding about catch-clause filters, or about changes inside functions that the guard only builds.
- It does not show that a counter or flag is actually wrong at run time. It shows only that the update depends on the order in which the guard is evaluated.
- No published score includes it today, because the one existing engine reports it advisory.

## Pending re-definition

These values are parameters of the existing reading's model, and today's score depends on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Ceiling for a non-zero count:** 6, raised by up to 2 (to 8) for an isolated finding in a large population.
- **Density at which the raise is gone:** 10 % of guards.
- **Population at which the raise is full:** 200 guards.
- **Denominator floor:** the denominator is at least one more than the number of side-effecting guards. So when every guard is side-effecting, the score before rounding is not exactly 1.
