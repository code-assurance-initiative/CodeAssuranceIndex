# C4: Data Retention

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether data has a defined lifetime — retention periods, TTLs, cleanup jobs (storage limitation).

## Applies to
Any programming language in which code stores data. The dimension also reads the repository's database schema and migration files (for example SQL migrations), because they declare what is stored and can declare a store-level expiry. It does not apply to markup (HTML) or styles (CSS).

## Population
- Production code as [production-code.md](../production-code.md) defines it, plus the repository's database schema and migration files.
- The dimension applies only to a repository that **keeps personal data**. A repository keeps personal data when either of these is true:
  - a persisted data model has a field that holds data about a person. A persisted model is, for example, an entity, a table, a document schema or a migration's columns. Such a field is, for example, an email address, a name, a date of birth, a phone number or a stored credential.
  - the code keeps user accounts, for example through an identity or user-account model.
- A postal code on its own describes an area, not a person, so it is not personal data. A field on a type that is never stored does not count, even if it holds data about a person.
- Lifetimes of things the application does not keep as data are out of scope. Examples are a cache entry, a cookie, a lock, a rate-limit window, and anything a sign-in holds for a while (for example a token, a session, an OAuth state or a one-time code).

## Unit and denominator
The unit is the repository. Each of three retention mechanisms is recorded as present or absent. Each is defined by what it does.

- **Expiry limit:** a length of time, with its unit, that sets how old stored data may get before it is no longer kept. Examples:
  - a store-level expiry the store applies to each record, for example a TTL index or an expiry on a date field.
  - a store's retention policy with an interval.
  - a setting or constant whose value is that maximum age, for example `retentionDays = 90`, `MaxAgeHours = 24` or `RetentionWindow = TimeSpan.FromDays(30)`.
  - the age cutoff of a purge, for example "delete rows older than 30 days". The cutoff is the maximum age the purge enforces, whether it is written inline or read from a setting.

  A declaration that gives no length of time is not an expiry limit. Examples are a policy label such as `RetentionPolicyName`, or a purge that deletes records whose own stored expiry time has passed without giving a length.
- **Purge:** a deletion of stored records once they pass an age, which runs without a user asking for it. It can be:
  - code, for example a recurring job, a hosted or background service, a timer loop, or a step the application runs at start-up. Dropping aged partitions also counts.
  - the store's own scheduled deletion job, which the repository sets up, for example a store retention policy with an interval.

  An expiry the store applies to each record by itself (for example a TTL index) is not a purge.
- **Documented retention period:** a declaration in code that presents itself as the lifetime or retention period of stored data, for example a constant or setting called the data's retention period or expiry (`DataRetentionPeriod`, `retentionDays`, `ExpiresAfter`). It does not have to give the length. These are not documented retention periods:
  - a word such as retention used in another sense, for example customer retention.
  - a label that names a policy but not a period, for example `RetentionPolicyName`.
  - a call that sets up a store's own retention policy. That call configures the store. It does not declare a period in the code.

**One thing can count as more than one mechanism.** It counts as each mechanism whose definition it meets:
- `retentionDays = 90` presents itself as the data's retention period and gives its length, so it is both an expiry limit and a documented retention period.
- `MaxAgeHours = 24` is a maximum age that does not present itself as the data's retention period, so it is only an expiry limit.
- A declaration that presents itself as the data's lifetime but gives no length is only a documented retention period.
- A purge with an age cutoff (for example a scheduled delete of rows older than 30 days) is both a purge and an expiry limit.
- A store retention policy with an interval, which the store runs as its own scheduled deletion, is both an expiry limit and a purge.
- A per-record store expiry (for example a TTL index) is only an expiry limit.

A mechanism anywhere in the population counts, even if it does not name the personal-data model it limits. A mechanism that appears only in a comment does not count.

There is no denominator.

## Thresholds
- A mechanism counts once it is present at least once. More occurrences add nothing.
- Cascade delete (removing dependent rows when their parent is removed) is referential integrity, not retention. It adds nothing.
- Event-sourced storage (append-only event streams) does not change the score.

## Score
If at least one mechanism is present, the score is the following sum, capped at 10.0:

- 4.0 for having any mechanism
- plus 2.5 if an expiry limit is present
- plus 2.5 if a purge is present
- plus 1.0 if a documented retention period is present

| Mechanisms present | Example | Score |
|---|---|---|
| documented period only | a retention period declared without its length | 5.0 |
| expiry limit only | a store TTL index, `MaxAgeHours = 24` | 6.5 |
| purge only | a scheduled delete of records whose stored expiry time has passed | 6.5 |
| documented period and expiry limit | `retentionDays = 90` alone | 7.5 |
| documented period and purge | a declared retention period with no length, and a scheduled delete of expired records | 7.5 |
| expiry limit and purge | a scheduled delete of rows older than 30 days; a store retention policy with an interval | 9.0 |
| all three | `retentionDays = 90` and a scheduled purge | 10.0 |

If no mechanism is present, there is no score (see below). Absence never gives a score of 0.

## Not measured when
- **Not applicable:** the repository keeps no personal data.
- **Not evidenced:** the repository keeps personal data but has no expiry limit, purge or documented retention period, so no score is given. Retention can be enforced outside the repository (for example by a database setting or an external job), so its absence from the code does not prove there is none.
- **Not assessed:** the code writes to a data store but declares no persisted model, so whether it keeps personal data cannot be established. Examples are writes through raw queries, or a hosted backend configured elsewhere.

## What the result is not
- It does not show that retention works at run time, or that a purge job is deployed and running.
- It does not judge whether a retention period is lawful or short enough.
- It does not show that every store of personal data is covered. One mechanism anywhere in the repository counts.
- It does not see retention enforced only by infrastructure outside the repository. That case gives no score, not a low one.
- It does not count cascade deletes, and it does not count deleting a user's data at their request. Erasure on request is a data-subject right, not storage limitation.
