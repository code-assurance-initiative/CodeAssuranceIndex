# X8: JS interop contract

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property

Whether string-named JS interop bindings resolve against the first-party JavaScript, and whether anything guards the boundary against renames.

## Applies to

The boundary between .NET code written in C# and JavaScript that runs in a browser or web view:

- **The .NET side:** C#, including the C# in Razor components and views.
- **The JavaScript side:** JavaScript files (`.js`, `.mjs`, `.cjs`), inline `<script>` blocks in the repository's own markup (HTML, Razor components and Razor views), and JavaScript source held in a C# string that the application registers or evaluates at runtime.

A repository with no such boundary is not measured (see Not measured when).

## Population

- **Calls:** calls in production code as [production-code.md](../production-code.md) defines it. Calls in tests, generated code and vendored code are not in scope.
- **Definitions:** a binding is checked against the first-party JavaScript only. That is JavaScript in production code, inline scripts in the repository's own markup, and JavaScript held in the repository's own C# strings. Vendored scripts, scripts loaded from a content delivery network, scripts a package ships, and scripts fetched or built at runtime are not searched.
- **Server-side templates:** [production-code.md](../production-code.md) leaves these out as files. This dimension still reads two things in them: the interop calls in their C# and the inline `<script>` blocks in their markup.
- **Names the platform provides:** a binding to something the browser itself provides resolves without a first-party definition. Examples are `window`, `document`, `console`, `localStorage`, `navigator.clipboard`, `fetch`, `setTimeout`, `eval` and `import`. So does a binding to the interop framework's own script.
- **Dynamic names:** a call whose function name is computed at runtime is not a binding and is not counted. A name only counts when the code gives it as a string literal or a compile-time string constant.

## Unit and denominator

**Unit: a string-named binding.** This is a call across the boundary that names its target as a string shaped like a JavaScript identifier path (for example `board3d.update`). There are two directions:

- **.NET to JavaScript:** a C# call on a JavaScript runtime or on a JavaScript object reference that names the JavaScript function to invoke. Examples are `InvokeAsync`, `InvokeVoidAsync`, `Invoke` and `InvokeVoid` in Blazor or MAUI.
- **JavaScript to .NET:** a JavaScript call that names a .NET method to invoke, either on a .NET object reference or as a static entry point of an assembly the repository builds. A call into an assembly the repository does not build is not judged.

**Resolved** means the name reaches a definition, following the language's own rules:

- **On the runtime:** the name is a global path (`a.b.c` is `window.a.b.c`) that first-party JavaScript defines, or that the platform provides.
- **On a module reference:** the first segment of the name is an export of the module the reference was imported from. A module that re-exports everything covers any name.
- **On a reference a JavaScript function returned:** the first segment of the name is a member of the object that function returns.
- **JavaScript to .NET:** the identifier is one a .NET method declares as invokable from JavaScript. That is the identifier given in its invokable declaration, or else the method's name.

**Unresolved** means the name reaches no definition. At runtime such a call throws or does nothing.

**Guard:** the boundary is guarded when something fails before runtime if either side is renamed. Examples are typed JavaScript (TypeScript) on the JavaScript side, or a test of the interop contract.

**Denominator:** all string-named bindings in the population, in both directions.

## Thresholds

- One unresolved binding is one finding.
- The boundary counts as unguarded when no guard exists and at least one first-party JavaScript file exists. This is one finding for the repository, whether or not every binding resolves today.

## Score

No score curve is defined: the one existing engine reports findings only, with no 0-10 reading.

## Not measured when

- The production code holds no .NET to JavaScript string-named binding. This applies even if JavaScript to .NET calls exist.

## What the result is not

- It is not a check of bindings into vendored or delivery-network scripts. A binding whose definition lives only there is not checked, and it is not reported as unresolved.
- It is not a check of argument count, argument types or return types. Only the name is checked.
- It is not a check of calls whose name is computed at runtime.
- It does not prove that a resolved binding works. It only shows that a definition with that name exists where the call reaches.
- "Unguarded" is not a defect today. It means a rename on either side would compile cleanly and fail only at runtime.

## Pending re-definition

These are parameters of the existing reading's model. The population depends on them today, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Status:** the catalog does not declare it advisory, yet no score curve exists; a decision either declares it advisory or sets its curve.
- **Markup file size:** a markup file larger than 2,000,000 bytes is not searched for inline scripts.
- **Markup volume:** inline scripts are searched in at most 16,000,000 bytes of markup in total. Markup is read in this order: Razor components, then Razor views, then HTML (`.html`, then `.htm`). Markup past the limit is not searched.
