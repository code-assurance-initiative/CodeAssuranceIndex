# P4: Deployment & Rollback

**Lens:** productionReadiness · **Scored:** yes

## Property

Whether releases are automated and safely reversible (probes, rolling updates, approval gates) — from manifests/pipeline files, not the live environment.

## Applies to

Any language. This dimension reads the files that describe how the repository is released. It does not read the product's source code. The file kinds are:

- pipeline definitions (CI and CD workflow files in any dialect);
- deployment and orchestration manifests, for example Kubernetes manifests, Helm charts and compose files;
- container build recipes, for example a Dockerfile;
- hosting-platform deploy descriptors, for example a Procfile or a platform's deploy configuration file;
- infrastructure templates, for example Terraform, Bicep or ARM templates;
- release-tool configuration;
- the repository's own release scripts, for example package-manager scripts, shell scripts and Makefile or justfile targets;
- manifests that the repository's documentation tells operators to apply. These count as deployment manifests.

## Population

The population is the repository's own release path, as committed at the analysed commit.

**In scope:** release files that the repository uses to ship its own product. The product may be a running service or a published artifact (for example a package-registry upload, release binaries or a container image push). A deploy to any environment counts. The environment can be long-lived (for example staging or production) or created by the pipeline itself (for example a preview or per-branch stack).

**Out of scope:**

- release files that belong to any of these, in the sense of [production-code.md](../production-code.md): tests and test support, evaluation inputs, samples, demos and showcases, development-container setups, vendored code, and build output;
- a workflow whose only release is publishing the documentation site.

Nothing configured outside the repository is part of the population. For example, protection rules in the code host's settings, branch protection, organisation deployment policies and the runner's configuration are all out.

## Unit and denominator

The unit is the repository. Each of three properties is judged true or false for the whole repository:

1. **Deploy automation.** A committed file builds or releases the product, so that no person has to do the release steps by hand. Any one of these counts:
   - a pipeline step that deploys or rolls out the product;
   - an automated publish of a release (for example a registry publish, a release with uploaded artifacts, or an image push);
   - a hosting-platform deploy descriptor of the product;
   - a deployment or orchestration manifest of the product;
   - a container build recipe of the product.
2. **Rollback safety.** A bad release is caught or can be undone. Any one of these counts:
   - readiness or liveness probes, or a container health check;
   - a platform health-check path;
   - a rolling, blue/green or canary rollout strategy;
   - release lifecycle hooks;
   - a migration job run as part of the rollout;
   - a rollback step in the pipeline;
   - a staging slot swapped into production;
   - a hosting-platform deploy descriptor of the product (the same descriptor that counts as deploy automation). The platform keeps the previous release one step away. A pipeline step that deploys straight onto a hosting platform is not rollback safety by itself;
   - a package-only release, which needs all three of these:
     - nothing is deployed as a service;
     - at least one workflow publishes a package;
     - every workflow that publishes runs only from a version tag, a published release or a manual dispatch.

     A bad version can then be withdrawn at the registry, and the previous version stays installable.

   A strategy that replaces the running workload with no overlap (for example "recreate" or "on delete") is not rollback safety.
3. **Release gate.** A release cannot reach users unchecked. Any one of these counts:
   - **A person approves.** For example:
     - a manual job or approval step in the pipeline;
     - a deployment environment declared with required reviewers, a protection rule, a wait timer or a branch policy;
     - releases published as drafts that a person must promote;
     - a release workflow whose only trigger is a manual dispatch;
     - a release workflow whose only trigger is a person publishing a release. This form does not count if any workflow triggered by a push or a tag creates a published (not draft) release by itself;
     - a tag-only publish restricted to named maintainers.
   - **The tests gate it.** At least one pipeline job ships the product, and every job that ships waits for a job that runs the tests and fails when they fail.
   - **A release script gates it.** At least one release script ships the product, and every release script that ships runs the tests first and stops on a failure. This form counts only when deploy automation is present and no pipeline publisher ships untested.

A comment or a display name is not a declaration. Only constructs that act count.

There is no denominator.

## Thresholds

A property is true when at least one of its forms is present. There are no other thresholds.

## Score

score = 5 × deploy automation + 3 × rollback safety + 2 × release gate

Each property is 1 when true and 0 when false. The possible scores are 2, 3, 5, 7, 8 and 10. A score of 5 comes either from deploy automation alone or from rollback safety plus a release gate. The score is never 0: when none of the three properties holds, the dimension is not measured (see below).

## Not measured when

- None of the three properties holds. The result is "not evidenced", never 0. Finding no release evidence does not show that releases are manual or unsafe.
- The repository cannot be read.

This dimension reads release files, not source code. Whether the repository's CAI is published at all follows the 95 % rule of [production-code.md](../production-code.md).

## What the result is not

- It does not inspect the live environment. A gate or rollout rule that lives in the code host's settings, in a runner or in a separate operations repository is invisible.
- It does not check that the probes, gates or rollback steps work. It only checks that they are declared.
- It does not judge individual releases. It gives one judgement per repository.
- It does not grade quality within a property. One form of rollback safety earns the same credit as several.
- It does not measure deployment frequency, lead time or failure rate.
