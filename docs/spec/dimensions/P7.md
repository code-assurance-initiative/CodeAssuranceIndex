# P7: Outbound HTTP resilience

**Lens:** productionReadiness · **Scored:** yes

## Property

Whether outbound HTTP calls are wrapped in resilience (retry/timeout/circuit-breaker) so a failing dependency doesn't cascade.

## Applies to

This applies to any language on the production-lines list whose code sends HTTP requests to other services.

## Population

The population is production code as [production-code.md](../production-code.md) defines it, minus these:

- **User-interface code on the user's device:** code that runs in a browser, or in the user-interface layer of a mobile or desktop app. For example, a UI component that calls `fetch`, a module that only a web page's scripts load, a SwiftUI view, or a Flutter app package. A call from there has no service process to take down and no downstream service to cascade into.
- **An HTTP client's own implementation:** code that implements an HTTP client stack, for example a language runtime's own HTTP library. That code is the client. It does not use one.

Libraries, command-line tools and build tools are in scope. An unbounded call in one of them hangs the process that called it.

An outbound HTTP call is a request that this code sends over HTTP to a server. It can go through any client: a standard-library client, a client library, a declarative client interface, or a raw socket helper used for HTTP. These are not outbound HTTP calls:

- a request the code builds and hands to its own router inside the same process;
- database, message-queue, gRPC and raw TCP calls.

## Unit and denominator

**Unit:** an outbound HTTP client. Each client is either bounded or unbounded.

- **A client that is one request:** some calls go through a client that keeps no settings between calls (for example a module-level `get` helper, or `fetch`). Each such call is its own client. It is judged by what is set on that call and by what wraps it.
- **A client the code builds or registers and keeps:** this client is bounded when a timeout, deadline or policy is applied to it, wherever in the code that happens. Every call through the client gets the same verdict.

A client is **bounded** when at least one of these applies to it:

- **A timeout or deadline the authors set.** For example a timeout on the call, a timeout on the client, or a cancellation deadline on the request.
- **A retry or circuit-breaker policy that wraps the call or the client.** A hand-written retry loop with a maximum number of attempts counts.
- **A deadline the request carries from its caller.** For example a request built with a cancellation context that the caller passes in.
- **A process-wide default that the authors set once for one client library.** For example a global default timeout for that library. It bounds only calls made through that library.
- **A framework's application-wide deadline.** Some application frameworks provide an HTTP client service and put a deadline on the whole request for every client they hand out. This counts when the application owns that setting in one place and can change it there. For example, a content-management framework's HTTP client service sends every request with a 30-second whole-request timeout, and the site's settings can override it.

**What does not count:**

- **A client type's built-in default.** A timeout counts only when the repository's authors set it, or when the application framework applies it as an application-wide setting (above). A client type's built-in default never makes a client bounded, however long or short it is. Examples: a client class's fixed whole-request default of 100 seconds, or a client library's own default timeout, such as 5, 10 or 30 seconds.
- **An idle-only timeout.** A timeout that only limits how long a connection may sit idle does not count.
- **A timeout set to no limit.** Setting a timeout to "infinite" removes a bound. It does not add one.

A policy or timeout bounds only the clients it applies to. A timeout on one client does not bound a different client in the same file.

**Denominator:** every outbound HTTP client in the population.

## Thresholds

- One unbounded client is enough for the lower score.
- There are no other thresholds.

## Score

| Clients in the population | Score |
|---|---|
| Every client bounded | 10 |
| One or more clients unbounded | 3 |

No other score is possible. The score does not depend on what share of the clients is unbounded.

## Not measured when

- The population makes no outbound HTTP call. The result is "not applicable", not a score.

## What the result is not

- **Not resilience outside the code:** the code cannot show a service mesh, sidecar, gateway or proxy that adds retries or timeouts at the platform level. Such a layer does not make a client bounded.
- **Not the quality of the bound:** the score does not judge whether a bound is well chosen. A one-hour timeout counts as bounded. So does a retry without back-off.
- **Not a share:** a repository with one unbounded client scores 3, the same as one where every client is unbounded.
- **Not inbound resilience:** the score does not cover rate limiting, load shedding, or timeouts on requests the code serves.
- **Not other protocols:** database, message-queue, gRPC and raw TCP calls are not counted.
