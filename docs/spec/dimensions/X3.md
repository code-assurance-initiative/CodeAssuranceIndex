# X3: Exception handling

**Lens:** codeHealth · **Scored:** yes

## Property
Whether exceptions are handled rather than silently swallowed or rethrown with lost stack traces.

## Applies to
C#, Java, Kotlin, Scala, PHP, Python, Ruby, Dart, Swift, Erlang, Go, JavaScript and TypeScript. This includes the script blocks of single-file components (for example Vue or Svelte). Other languages are not read, including F# and Visual Basic .NET.

## Population
The population is the failure handlers in production code, as [production-code.md](../production-code.md) defines it. This dimension adds nothing to that definition and leaves nothing else out.

A **failure handler** is a place where the code receives a failure and decides what to do with it:

- **Every language with exceptions:** each `catch`, `except`, `rescue` or equivalent clause of a `try` statement, typed or untyped.
- **Ruby:** also each `rescue` modifier on a statement (`expr rescue fallback`). It rescues `StandardError` and counts as a catch-all.
- **C#:** also each task continuation written as a lambda (`ContinueWith(...)`). It handles the task's failure.
- **JavaScript and TypeScript:** also each promise rejection handler. That is the argument of `.catch(h)` and the second argument of `.then(ok, h)`.
- **Go:** each branch whose condition tests an error value against `nil`, and each `recover()`. Also each **discarded error**: a call to a function whose results include an `error`, where that error is thrown away. It is thrown away when it is assigned to `_`, or when the call is written as a bare statement.

## Unit and denominator
**Violations** (the numerator, v) are counted one by one:

1. **A swallowing handler.** This is a handler that is not deliberate (below) and whose body is empty or does nothing with the failure. A body does something with the failure when it calls something, constructs an object, throws, awaits, names the caught failure, or writes a variable or field that the code reads after the handler. In Go, sending on a channel, a `goto`, and returning an error value also count, and so does a bare `return` when the function names its results. In every language, returning a value in place of the failure does not count: for example `return null`, `return false`, a zero value, or in Go `return nil`. None of these count as doing something either:
   - output that a release build does not contain, or that only an attached debugger reads (for example `Debug.WriteLine`, or code under `#if DEBUG`);
   - assigning a made-up default or empty value, or zero-filling a buffer;
   - testing the failure's type or properties without passing it on;
   - a pause inside a retry loop that ends silently when its last attempt fails.
2. **A rethrow that loses the stack trace (C#).** Each statement in a handler that throws the caught exception variable again (`throw ex;`) counts once. This applies only to C#, where such a throw resets the trace. In the other languages read, a rethrow keeps the trace.
3. **An unguarded deserialized null (C#).** A local takes the result of a JSON deserializer that returns null for the document `null` (for example `JsonSerializer.Deserialize`). The local is then dereferenced, and the method never tests it for null. This counts only inside a `try` where no handler catches a null-reference failure. It is a violation but not a member of the population.
4. **A discarded error (Go).** A discarded error is a violation in two cases:
   - it was assigned to `_` and another result of the same call is used afterwards (read for its value, not just compared to `nil` or overwritten);
   - the whole call is a bare statement.

   A discarded error is deliberate, and not a violation, in two cases:
   - a reason (below) is on that line or directly above it;
   - the call cannot fail on the input it is given. For example: a write to an in-memory buffer or a hash; a standard-library conversion of constant input, such as parsing a literal URL or compiling a literal pattern; encoding a value whose type always encodes; or a standard-library copy between in-memory streams.

   A deliberate discarded error still counts in the population.
5. **A lost error (Go).** An error is lost when the code reports or returns an error variable that cannot hold an error at that point, because it is always nil there. For example: an inverted `if err == nil { return err }`; a branch that reports a different error that an earlier check already proved nil; or a deferred cleanup that tests an outer error while the failure leaves through an inner variable of the same name. Reporting the zero value of a type assertion that failed is also a lost error. A lost error is a violation but adds nothing to the population.
6. **A fail-open authorization.** This is a handler whose `try` asks whether access is allowed, and which answers the failure by granting access. It grants access when it returns or stores the allowing answer (for example `True` or an allow constant) and the code after the `try` reads it. It also grants access when it falls through to code that allows, skipping a denial or leaving an allowing default in place. It counts even when the handler is narrow or a comment gives a reason. It replaces any swallow count for the same handler and is not added to it.

**A deliberate handler is not a swallow.** A handler is deliberate when any of these is true:

- **It catches cancellation:** for example .NET's `OperationCanceledException` or `TaskCanceledException`.
- **It is narrow and a comment gives the reason.** Narrow means it catches one specific failure kind or has a filter, rather than the language's catch-all. Even with a reason, it is not deliberate in two cases: the guarded block itself throws that very type, or another handler in the same type catches the same type around the same call and does handle it.
- **It is a bounded retry:** its filter tests the counter of the loop around it.
- **It sits in a `TryX` method:** one that returns `bool` and has an `out` parameter, where the statement after the `try` returns `false`.

A **catch-all** is an untyped handler, or one whose type is at or near the root of the language's failure hierarchy. Examples are `Exception` in C#, `Throwable` in Java, `BaseException` in Python and `StandardError` in Ruby. In Go, a branch on `err != nil` alone is a catch-all, and a condition that also asks which failure it is counts as narrow. In JavaScript and TypeScript every `catch` is a catch-all.

**A reason** is a comment in one of these places:

- inside the handler;
- trailing the handler's header;
- on the lines directly above the handler or its `try`, with no blank line between;
- on a warning-suppression directive in force at the handler.

These comments are not reasons: one that only restates the swallow (for example `// ignore`), one that records unfinished work (`TODO`, `FIXME`), commented-out code, and a bare linter directive.

**The population** P is the number of failure handlers. **The denominator** is max(P, v + 1).

## Thresholds
- Any single violation counts. There is no size or severity threshold.
- The density is d = v / max(P, v + 1), limited to the range 0 to 1.

## Score
- v = 0: the score is **10**.
- v ≥ 1, with N = max(P, v + 1):
  - isolation = max(0, 1 − d / 0.10)
  - headroom = min(1, log10(N) / log10(200))
  - ceiling = 6.0 + 2.0 × isolation × headroom
  - score = 1.0 + (1 − d) × (ceiling − 1.0), limited to [1.0, ceiling] and rounded to 2 decimals.

So a repository with any violation never scores above 8.0. A density of 10 % or more caps the score at 6.0, and the score falls towards 1.0 as violations become pervasive. For example, 1 violation among 200 handlers scores 7.87, and 1 among 10 scores 5.50.

## Not measured when
- The production code read holds no failure handler and no violation. The dimension is then not applicable, rather than 10.
- The repository has no production code in the languages under Applies to.
- The filesystem refused every in-scope file. The result names refused files in every case.

## What the result is not
- It does not show that failures are handled well. A handler that logs and carries on in the wrong state is not a violation.
- It does not judge whether a catch is too broad when the handler does handle the failure.
- It does not judge failures that no handler surrounds, except Go's discarded errors.
- It does not judge whether a reason comment is true.
- It is not a count of failures that are lost at runtime.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them, and a later decision under decision 0013 will replace each one with a threshold on the property.

- **Rot density:** 10 %. At or above this density, a violation earns no headroom above 6.0.
- **Population saturation:** 200 handlers. At this denominator the headroom is full.
- **Ceiling band:** 6.0 for any violation, rising to at most 8.0 for an isolated violation in a large population.
- **Floor:** 1.0.
