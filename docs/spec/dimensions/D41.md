# D41: Kernel & Syscall Confinement

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether Kubernetes workloads confine the kernel boundary — a seccomp profile (RuntimeDefault/Localhost) plus an AppArmor/SELinux mandatory-access-control layer — shrinking the syscall attack surface a container escape would use. Presence of committed confinement config, not runtime enforcement.

## Applies to
Any language. The dimension reads the repository's committed Kubernetes deployment configuration, not its source code:

- YAML manifests (`.yaml`, `.yml`), including chart templates and overlays that render to manifests.
- Committed seccomp profiles (JSON) that a workload's `Localhost` profile names.

## Population
The population is the repository's Kubernetes workloads. A workload is a resource that carries a pod template, for example a Pod, Deployment, DaemonSet, StatefulSet, ReplicaSet, Job, CronJob or Rollout, or any other resource whose spec holds a pod template with containers. A resource that only describes pods without running them is not a workload, for example an admission policy or another cluster-governance resource.

Each workload is read as the repository's own configuration would apply it:

- A chart template is read as it renders with the values the repository commits. A template that those values do not render is not in the population.
- A manifest that an overlay renders is read in that overlay's rendered form, with its patches applied over its bases. Each rendered deployment of a base counts as its own workload.

Out of scope:

- Manifests in tests and test support (for example fixtures and golden expected output).
- Manifests in samples and examples.
- Manifests in documentation.
- Vendored third-party manifests (for example a copied-in third-party chart).
- Build output and tool state.

The categories are as [production-code.md](../production-code.md) defines them. The production-code file list itself does not apply here, because manifests are not source files.

A workload is left out of the denominator when its seccomp profile in force cannot be known from the committed configuration. For example, the value comes from a template expression that the committed values do not resolve, or the document is not valid YAML.

## Unit and denominator
The unit is one workload. Each workload can earn two controls:

1. **Seccomp confinement.** The workload has at least one container. Every container (init, regular and ephemeral) runs under a seccomp profile in force that filters system calls. The profile in force is the container's own `seccompProfile`, or the pod's when the container sets none. A profile filters when:
   - its type is `RuntimeDefault`; or
   - its type is `Localhost` and the profile it names is not committed in the repository (it lives on the node and is credited by its type); or
   - its type is `Localhost`, the repository commits the profile, and the profile denies by default. This means its default action is anything other than allow or log.

   These do not filter: `Unconfined`, any other type, no profile at all, and a container named only by the deprecated alpha seccomp annotation (current Kubernetes ignores it). A committed `Localhost` profile that allows or logs by default also does not filter, whether it blocks nothing or blocks only a deny list.
2. **Mandatory access control.** The workload declares at least one AppArmor or SELinux setting, on the pod or on any container, that is not an opt-out, and it has no opt-out anywhere:
   - An AppArmor profile type other than `Unconfined` counts as a declaration. So does an AppArmor container annotation whose value is not `unconfined`, and any SELinux options whose type is not `spc_t`.
   - AppArmor `Unconfined`, the `unconfined` annotation value and SELinux type `spc_t` are opt-outs.
   - A workload that declares nothing earns no credit and loses none: the runtime's default profile is not counted either way.

The numerator is the number of controls earned across all workloads. The denominator is twice the number of workloads in the population.

## Thresholds
- A seccomp profile confines only if it is in force for every container of the workload. One unconfined container loses the control for the whole workload.
- One MAC opt-out anywhere in a workload loses that workload's MAC control, even if another setting declares a profile.
- Both controls carry equal weight.

## Score
score = 6.0 + 4.0 × (controls earned) / (2 × workloads), clamped to 6.0 to 10.0.

- No control earned on any workload: 6.0. An unconfined workload sits at this neutral floor, not at 0.
- Every workload seccomp-confined, none with MAC: 8.0.
- Every workload earns both controls: 10.0.
- Workloads exist but none can be judged (every one is left out of the denominator): 6.0.

## Not measured when
The repository's in-scope manifests hold no Kubernetes workload. The dimension is then not applicable.

## What the result is not
- It is not runtime enforcement. A profile applied off the repository is not seen, for example by a cluster-wide pod security default or by a mutating admission webhook. A declared profile is not proof that the node loaded and enforced it.
- It does not check that an uncommitted `Localhost` profile exists on the node or what it allows.
- It does not grade how tight a deny-by-default seccomp allow list is.
- It is not baseline container hardening: running as non-root, a read-only root filesystem, dropped capabilities and privileged mode belong to another dimension. This one gives credit only for kernel-boundary confinement and never deducts below the floor.
