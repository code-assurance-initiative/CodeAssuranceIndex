# D5: Coupling

**Lens:** architecture · **Scored:** yes

## Property
Whether volatile projects sit underneath others that depend on them (so their churn ripples upward), and whether project dependencies form cycles. A widely-depended-on but stable shared/kernel project is healthy, not penalised.

## Applies to
This dimension applies to any language whose code is split into modules that declare their dependencies on each other. A module is the unit that a build declares and that other modules reference. Some examples: a .NET project, a Gradle or Maven module, a Cargo crate, an npm package, a Go module, a Python distribution, a SwiftPM target, an sbt project, a Composer package, an OTP application, a pub package, or a CMake or Bazel target.

A dependency is a direct reference that one module of the repository declares to another module of the same repository. A module reached only through another module is not a direct dependency. Dependencies on outside packages are not counted.

Some source has no build that declares its modules. In that case each top-level directory of that source is a module. Source in one directory that imports code from another directory is a dependency.

Abstractness (below) applies only to languages that declare abstractions. JavaScript and Ruby code has no abstractness.

## Population
- **Production modules:** modules whose code is production code as [production-code.md](../production-code.md) defines it. Test modules, test support modules, benchmark modules, and sample or example modules are not production modules. This differs from [production-code.md](../production-code.md): this dimension also leaves samples and examples out. Only production modules and the dependencies between them are counted.
- **Which graph is scored:** a repository can hold module graphs of more than one build kind. The .NET project graph is one graph. The graphs of all other build kinds, read together, are the other graph. Only one of the two is scored. Pending re-definition says which.
- **Entry points:** a module that declares itself an executable or application, for example a web host, a worker or a console program. It wires the other modules together. An entry point is never an unstable hub. A dependency from an entry point does not make the module it references a hub.
- **Shared kernel:** a module whose declared purpose is to hold what other modules share, for example base types, contracts, common primitives or building blocks. It is exempt from the off-main-sequence penalty.
- **Isolated modules:** a module that has no production dependents and depends on nothing. It is never off the main sequence.
- **Types for abstractness:** the module's own production classes and interfaces. Generated types are not counted. Platform types copied in to back-port the platform are not counted either, for example polyfills of the standard library's own attributes.

## Unit and denominator
**N** is the number of production modules in the scored graph.

Each production module gets the values below. They count only direct dependencies between production modules, and each referencing module counts once.
- **Ca (afferent):** the number of modules that depend on it.
- **Ce (efferent):** the number of modules it depends on.
- **Instability I** = Ce / (Ca + Ce). I is 0 when both are 0.
- **Abstractness A** = abstract types / all counted types in the module. A type is abstract when it is one of these:
  - an interface, protocol or trait;
  - a behaviour (a module that declares callbacks);
  - an abstract class or a sealed hierarchy;
  - a class that leaves an inherited abstract member open.

  Classes, records, structs, mixins and traits that leave nothing to implement are concrete. Some languages put behaviour in free functions (for example Go, TypeScript, Python, Swift, Elixir and Erlang). There, the free functions of one file, module or package count as one concrete type. These are not counted: enumerations, newtypes and aliases, constraint-only interfaces, and data-only shapes (for example a TypeScript interface with only data properties, or a Python TypedDict). A module with no counted type has no A and is never off the main sequence.
- **Distance D** = |A + I − 1|.

Three counts feed the score:
- **c, cycle members:** the production modules that sit on a dependency cycle, meaning they can reach themselves by following dependencies between production modules. A module counts once however many cycles it is on.
- **h, unstable hubs:** the production modules that meet the hub thresholds below.
- **o, off the main sequence:** the production modules that meet the off-main-sequence thresholds below and are not shared kernels.

## Thresholds
- **Unstable hub:** all three of these hold:
  - I > 0.8;
  - at least one production module that is not an entry point depends on it;
  - it is not itself an entry point.
- **Off the main sequence:** D > 0.7, and the module is not isolated. When the .NET project graph is scored, a module on the concrete side (I < 0.5) that is neither an entry point nor a shared kernel counts only when both of these hold:
  - at least 2 distinct production modules that are not entry points depend on it;
  - it is not stable, as Pending re-definition defines it.

  When the other graph is scored, neither condition applies.
- **Degenerate graph:** the scored graph has fewer than 2 production modules, or no production module has a production dependent. On a degenerate graph, o is 0.
- **Low surface:** both of these hold:
  - fewer than 2 production modules contain code;
  - the scored graph's languages have fewer than 1,500 production lines, as [production-code.md](../production-code.md) counts them.

## Score
```
score = clamp(10 − 20·c/N − 10·h/N − 8·o/N, 0, 10)
```
With low surface, the score is min(score, 6.9).

A graph scores 10 when it has no cycles, no unstable hubs and no counted off-main-sequence modules. The score reaches 0 in any of these cases: half the modules are on a cycle, every module is an unstable hub, or the three counts together reach the same penalty.

A .NET project graph with a single production module is measured. It is a degenerate graph, and the low-surface cap usually applies.

## Not measured when
- The .NET project graph is scored because it has at least one project, but none of its projects is a production module, for example a solution that holds only test projects.
- The other graph is scored and has fewer than 2 production modules.
- The other graph is scored and its languages hold less than 50 % of the repository's production lines. A .NET project graph has no such check: once it is chosen for scoring, it is measured whatever share it holds.

## What the result is not
- It is not coupling inside a module. Dependencies between classes, files and namespaces within one module are invisible.
- It is not a count of dependencies. A module is not penalised just because many others depend on it.
- It is not a check of named layers or architecture rules.
- It reads history only to judge whether a concrete, depended-on module in a .NET project graph is stable. Everywhere else, I stands in for how likely a module is to change. The result does not measure how often a module has changed.
- It covers only the scored graph. Modules of the graph that is not scored are not counted.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Stable module:** a module is stable when all three of these hold. The window is the 365 days that end at the newest commit in the history.
  - At most 1 commit in the window changed one of its source files. Creating a file does not count as a change. Neither does only moving a file, or editing only the module's build file.
  - It had commits before the window.
  - Some other production module changed at least 4 times in the window.

  Where history is missing or incomplete, no module is stable.
- **Graph choice:** the .NET project graph is scored when it has at least one project of any kind. The exception is when both of these hold: the other graph has at least 2 production modules, and the source the .NET projects compile holds less than 15 % of the repository's production lines. In that case the other graph is scored. When there is no .NET project, the other graph is scored.
- **Concrete-side conditions by graph:** the 2-dependent and stability conditions on off-main-sequence modules apply only to the .NET project graph.
- **Minimum modules for the other graph:** 2 production modules.
- **Majority share for the other graph:** 50 % of the repository's production lines.
