# P5: DR & Backup

**Lens:** productionReadiness · **Scored:** yes

## Property

Whether disaster recovery is planned and codified — backups, geo-recovery, RTO/RPO, persistence guarantees — from IaC + container manifests + docs, never the live cloud.

## Applies to

Any language. The evidence comes from these file kinds:

- infrastructure as code, for example Terraform, Bicep, ARM templates and CloudFormation or SAM templates;
- deployment and container manifests, for example Kubernetes manifests, Helm charts, container compose files and
  application-host definitions that declare a container stack;
- schedule definitions, for example a scheduled CI workflow, a Kubernetes CronJob, a scheduled worker or a crontab
  entry, together with the scripts and modules the schedule runs;
- operational documentation in prose, for example readmes, documentation folders, runbooks, and deployment,
  operations, backup, restore and disaster-recovery documents, in any natural language;
- production code as [production-code.md](../production-code.md) defines it, but only for the in-product backup control below.

The live environment (a cloud account, a running cluster, a backup service's console) is never read.

## Population

The whole repository at the analysed commit, limited to the file kinds above. These are left out:

- tests, test support and test fixtures, including compose files, manifests and schedules that exist only as test
  inputs;
- build output, vendored code and generated code.

Code shown in documentation (for example a command or a configuration example) is code, not prose. A heading or
comment inside it is not a documentation section.

## Unit and denominator

The unit is the repository. Three kinds of evidence are each either present or absent. Nothing is counted per file,
so there is no denominator.

1. **Backup.** At least one of these is present:
   - infrastructure as code or a deployment manifest declares a backup, a snapshot control (for example a snapshot
     schedule, policy or retention), geo-redundant storage, or replication. A version tag or a test snapshot is not a
     snapshot control;
   - operational documentation sets out backups: a section on how, when or how long backups are made or kept (for
     example "## Backup strategy" or "nightly backups"), not a passing mention of the word;
   - the repository schedules a job that backs up a whole data store: the job runs a dedicated backup tool, or it
     reads the whole store and writes the result to storage;
   - operational documentation shows a scheduled (crontab) entry that runs a backup or a dump of a data store;
   - the production code implements both creating a backup and restoring from one (for example `createBackup` and
     `restoreBackup`). Only one of the two is not enough.
2. **DR documentation.** Operational documentation has at least one of these:
   - a section that sets out disaster recovery or geo-recovery (for example a plan, runbook or drill), not a passing
     mention;
   - a section on restoring from a backup, snapshot or dump;
   - a documented restore command, shown as code, that restores from a backup, snapshot or dump or runs a tool whose
     only job is restoring;
   - a section that sets out failover in the recovery sense: failover between regions, data centres, clusters or
     replicas, or to a standby;
   - a recovery time objective (RTO) or recovery point objective (RPO) stated as a target duration, in any layout
     (for example "RTO: 4h" or a table of targets). A bare mention of the acronym does not count.
3. **Persistence guard.** At least one of these is present:
   - a cloud resource is protected against deletion (for example purge protection, soft delete, deletion protection
     or prevent destroy);
   - a container stack keeps data in a named volume that survives a container being recreated. A mount of a host path
     does not count, and neither does a mount of a dependency or build cache (for example `node_modules` or `.m2`);
   - a deployment manifest claims a persistent volume, for example a PersistentVolumeClaim or a StatefulSet's volume
     claim templates. Temporary and host-path volumes do not count.

## Thresholds

- Backup is worth 4 points, DR documentation 3 points and a persistence guard 3 points.
- A persistence guard earns its points only when Backup or DR documentation is also present.
- A backup that lives in the product's own code counts only when both a create and a restore are present.

## Score

score = 4 × Backup + 3 × DR documentation + 3 × (persistence guard AND (Backup OR DR documentation))

Each term is 1 when present and 0 when absent. The score is clamped to 0-10. The possible scores are 0, 3, 4, 6, 7
and 10. A persistence guard with no Backup and no DR documentation scores 0.

## Not measured when

None of the three kinds of evidence is present: no backup, no DR documentation and no persistence guard. The
dimension is then reported as not evidenced, with no score. This happens whether or not the repository holds
production data, for example a published library that deploys nothing, a repository that holds no code, or a
system whose recovery is run from another repository.

## What the result is not

- It is not proof that recovery works. A declared backup and a written plan do not show that a restore has been
  tested.
- It is not a reading of the live environment. A managed-service backup configured outside the repository reads as
  not evidenced.
- It does not judge how good the targets are. An RTO of four weeks counts the same as one of four minutes.
- A persistence guard on its own is not disaster recovery. A volume that survives a container being recreated is not
  a restore after a catastrophic loss.
- "Not evidenced" is not a score of 0, and it does not claim that the system has no recovery plan.

## Pending re-definition

These are parameters of the existing reading's model. Today's scores depend on them, and a later decision under
decision 0013 will replace each with a threshold on the property.

- **In-product backup control:** only the first 4,000 production code files are read when looking for a backup
  create and a backup restore.
- **Scheduled backup jobs:** for one scheduled job, at most 40 files it runs (its entry module and the modules it
  imports, or the scripts a workflow or crontab entry runs) are read. A file larger than 1 MiB is not read.
