# C1: Data Protection

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether sensitive data is encrypted at rest and in transit and keys are vaulted.

## Applies to
Any language. The dimension reads application code, plus the declarations that say what data the application stores (for example database schema and migration files, including SQL) and the configuration through which the application serves HTTP (for example a headers file that sets response headers).

## Population
Production code as [production-code.md](../production-code.md) defines it. In addition to production code, this dimension reads:

- **Declarations of stored data:** persisted record types, database tables and columns, and schema and migration files (for example SQL `CREATE TABLE` statements). These decide only whether the repository stores personal data.
- **The repository's own serving configuration:** files that set the HTTP response headers the application sends. These decide only whether HTTPS is enforced.

Comments and documentation are not code. A control mentioned only in a comment or in prose does not count.

## Unit and denominator
The unit is the repository. The dimension asks whether the repository's code has each of five data-protection controls:

- **Encryption:** the code encrypts data with a symmetric cipher or with a platform data-protection or secure-storage facility (for example AES, a web framework's data-protection API, the operating system's keychain or keystore).
- **HTTPS:** the application enforces HTTPS for its own traffic, either by redirecting to or requiring HTTPS, or by sending a `Strict-Transport-Security` header from its own code or serving configuration. The control is also met when the application is configured to run behind a reverse proxy that terminates TLS for it (for example it honours forwarded-protocol headers).
- **Key vault:** the code reads keys or secrets from a secrets vault or key-management service (for example a cloud key vault's secret client).
- **Column encryption:** stored fields are encrypted one by one, for example with database column encryption or a mapping that encrypts a property's value before it is stored.
- **Key derivation:** the code derives keys or hashes passwords with a key-derivation function (for example PBKDF2, bcrypt, Argon2).

There is no denominator. Each control is either present in the repository or absent.

**Personal data** decides whether the dimension applies. A repository stores personal data when its code or schema declares stored records about real people: a user account, or a persisted record with fields that identify or contact a person (for example email, first name, date of birth), or stored user credentials. Fictional or game content shaped like personal data (for example a game character's first name) is not personal data.

## Thresholds
- A control is present when the code uses it at least once, anywhere in the population. One use is enough, and the dimension does not check that the control covers the personal data.
- The dimension applies when the repository stores any personal data (one record type is enough).

## Score
The score is the sum of the weights of the controls that are present:

| Control | Weight |
|---|---|
| Encryption | 3.5 |
| HTTPS (enforced in the application, or a TLS-terminating reverse proxy) | 3.0 |
| Key vault | 2.0 |
| Column encryption | 1.5 |
| Key derivation, only when encryption is absent | 1.0 |

Key derivation adds nothing when encryption is present, so the two weights are never added together. The sum is rounded to one decimal and kept between 0 and 10. The maximum is 10 (encryption, HTTPS, key vault and column encryption). Without encryption the maximum is 7.5.

A score of 0 means the repository stores personal data and has none of the five controls.

## Not measured when
- **No personal data:** the repository stores no personal data. The dimension is not applicable. HTTPS enforcement is still scored, under S1.
- **Project template:** the repository is a project template (a starter that users generate their own application from) and has none of encryption, column encryption or key derivation. At-rest protection belongs to the application built from it, so the dimension is not applicable. A template that has at least one of those three is scored.
- **Personal data cannot be established:** the code writes to a data store but declares no stored record type or schema that can be read (for example it writes only through raw queries built at run time or through a hosted backend). Whether personal data is stored is then unknown, so the dimension is not measured.
- **Language not read:** an engine that cannot read the language of the repository's product code does not measure the dimension.

A result that is not measured is left out of the lens. It is not a score of 0.

## What the result is not
- It does not show that the personal data itself is encrypted. It shows that the controls are present somewhere in the code. The controls may protect other data, or none of it.
- It does not check run-time behaviour, deployment, the strength of algorithms or keys, or key rotation.
- It does not check that the reverse proxy assumed in front of the application actually enforces HTTPS.
- A low score does not prove that data is unprotected. Protection may be provided outside the repository (for example storage encryption managed by the database or the platform).
- It is not a compliance verdict under any data-protection law.
