# D15: Churn × Complexity Hotspots

**Lens:** maturity · **Scored:** yes

## Property
Files that change often and are also complex — the riskiest hotspots.

## Applies to
Any language. Only a file in a programming language on the production-lines list of [production-code.md](../production-code.md) can be a hotspot, because a hotspot needs functions. The denominator (see Unit and denominator) counts changes to text files of every kind: code, markup (HTML), styles (CSS), documentation, configuration, data and build files.

## Population
- **Files:** a file counts only if it exists at the analysed commit. Changes made under an earlier name count toward the file's current name.
- **The dimension's files:** every file that is not binary (for example images, archives, fonts, compiled libraries) and that changed in the window, except the files in the next list. The denominator is summed over these files.
- **Left out of the whole dimension, numerator and denominator alike:**
  - tests and test support, evaluation inputs, benchmark projects, generated code and vendored code, as [production-code.md](../production-code.md) defines them, including files the repository itself declares generated or vendored;
  - fuzzing harnesses: code that only feeds generated input to the product to test it;
  - source files whose only content is one literal data value, as [production-code.md](../production-code.md) defines them;
  - examples, samples, demonstrations, prototypes, proofs of concept, mockups, sandboxes and playgrounds;
  - project templates that the product copies out to start a user's new project;
  - the authors' own developer tools and scripts that the product does not publish (for example a root `tools/` folder with no package of its own).
- **Kept in the denominator, though [production-code.md](../production-code.md) says they are not production code:** every other category on its list. For example documentation in prose markup, data and configuration files, lockfiles, build scripts, tool configuration files, shell and SQL scripts, committed build output, files in hidden folders (for example `.github` workflows), documentation-site output and showcases, specimen collections, server-side templates, TypeScript declaration files, and source the product's own build leaves out. A change to any of them is part of the window's churn.
- **Hotspot candidates:** only production code as [production-code.md](../production-code.md) defines it, from the dimension's files.
- **History:** the commits reachable from the analysed commit whose commit date falls in the window (see Thresholds), including commits that reached a file through a merged branch. Every author counts, people and machine accounts alike. The rules in [people.md](../people.md) do not apply.
- **Functions:** a function is any named or anonymous callable with a body, as the language defines it. An anonymous function belongs to the function that encloses it. These functions cannot make a file a hotspot:
  - a declaration with no body (for example an interface or abstract method);
  - a function that is only one lookup table (for example a switch whose arms each return a constant);
  - a flat dispatcher (see Thresholds).

## Unit and denominator
- **A change to a file:** a non-merge commit in the window that changes the file's content. These do not count:
  - the commit that created the file;
  - a pure move or rename with no content change;
  - a commit that reverts another commit in the window, together with the commit it reverts, for the files both touch;
  - a second landing of the same change (for example the same patch cherry-picked onto another branch), which counts once.
- **A file's churn:** its number of changes in the window.
- **A change to a function:** a change to the file that altered at least one line of that function's body.
- **Complexity:** a function's cyclomatic complexity, as D1 defines it.
- **Hotspot:** a candidate file with at least 2 changes in the window that holds at least one function that:
  - has cyclomatic complexity above the threshold, and
  - was changed by at least 2 of those changes.

  The file's hot function is the most complex such function.
- **Hotspot score:** the file's churn × the cyclomatic complexity of its hot function.
- **Denominator, total churn volume:** the sum of churn over all the dimension's files (see Population), hotspot or not. A commit that changes three such files adds 3.

## Thresholds
- **Window:** 90 days, ending at the commit date of the analysed commit.
- **Churn floor:** at least 2 changes to the file and at least 2 changes to its hot function.
- **Complexity floor:** cyclomatic complexity strictly above 15, which is D1's threshold. A function at exactly 15 does not qualify.
- **Flat dispatcher:** a function with cyclomatic complexity above 15 that also has:
  - cognitive complexity of at most 8, or cognitive complexity without boolean-operator sequences of at most 4; and
  - at most 15 decisions in guards on switch arms.

  This is D1's rule.
- **Hotspots summed:** the 10 hotspots with the highest scores.

## Score
```
intensity = (sum of the top 10 hotspot scores) / total churn volume / 15
score     = clamp(10 − 2 × intensity, 0, 10), rounded to 2 decimals
```
- Intensity is the complexity carried per change on the hottest files, in multiples of the complexity floor. Each multiple costs 2 points.
- With no hotspot, the score is 10.
- With no change in the window but more than one commit in the history, the score is 10.

## Not measured when
- The repository has no version-control history.
- At most one commit is reachable from the analysed commit.
- Function complexity cannot be read for languages that hold at least half of the repository's production lines.

A history cut short by a shallow clone is still scored, and the evidence says the history was shallow.

## What the result is not
- It is not a defect rate. It does not ask whether the changes were fixes.
- It is not a judgement of complexity on its own. A complex file that nobody changed in the window is not a hotspot (D1 reports it). A file that settled just before the window is not seen.
- It is not about the whole file. It counts only the complex functions that the changes touched.
- It is not a measure of test coverage, and it does not say a hotspot lacks tests.
- It does not judge code size or how much code moved. A change is one change whatever its size.
- A file whose functions are all simple is not a hotspot however often it changes. Any report of repeated repairs in such a file is not scored.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Window length:** 90 days.
- **Top hotspots summed:** 10.
- **Points per multiple of intensity:** 2.
- **Denominator scope:** total churn volume counts changes to documentation, data, configuration, build and other files that are not production code, not only production code.
