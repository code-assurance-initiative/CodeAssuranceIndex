# D18: Solution Shape

**Lens:** codeHealth · **Scored:** yes

## Property
Whether the solution is laid out in a sensible, conventional structure.

## Applies to
.NET solutions of C# and Visual Basic .NET projects. This covers the solution files, the project files they list, and the source files of those projects. Razor components and pages (`.razor`, `.cshtml`) count only as evidence that a project has code of its own (see Unit). F# projects are not read.

## Population
- **Projects:** every C# or Visual Basic .NET project in every solution the repository builds. When a repository has several solutions, their projects are read together and each project counts once.
- **Left out of the score:**
  - **Vendored projects:** third-party code copied in, as [production-code.md](../production-code.md) defines vendored code.
  - **Non-shipping harnesses:** a project that declares it is not packed, does not also declare a package identity, and is test, benchmark or fuzz scaffolding (for example a test project, a benchmark host or a fuzz entry point).
  - **Orchestration hosts:** a project whose SDK requires it to be a separate, thin host that declares the other services (for example an Aspire app host).
  - **Published packages:** a project that declares package metadata for publishing and does not opt out of packing. Package metadata is, for example, a package id, project URL or tags, or authors together with a description.

  If these rules leave out every project, all projects are scored.
- **Test projects:** a test project, as [production-code.md](../production-code.md) defines tests, stays in the score unless it is a non-shipping harness (above), meaning it declares that it is not packed and declares no package identity. Test projects are never production consumers (see Unit).
- **Significant lines of a project:** the lines of its own source files in its language (`.cs` or `.vb`) that are neither blank nor only a comment. Generated code and build output, as [production-code.md](../production-code.md) defines them, are not counted.
- **Small project:** a project with fewer than 50 significant lines.

## Unit and denominator
The unit is a **project**. Each project in the population gets a weight from 0 to 1. L is the project's number of significant lines.

- **Declares something of its own:** at least one of these:
  - a type with a member, a primary-constructor parameter or a base type
  - an enum with a member
  - a delegate
  - top-level statements
  - a Razor component or page with content

  An empty template class, global usings, assembly attributes and Razor import or start files do not count.
- **Shell, weight 0:** a project with fewer than 10 significant lines that declares nothing of its own and is not code-free on purpose. Code-free on purpose means one of these:
  - a build automation project
  - an ahead-of-time or trimming compatibility harness
  - a metapackage that only rolls up references
  - a packaging or payload project (for example an installer or extension container, a build-order list, custom build tasks, copied content, or per-variant entry points to shared build logic)
  - a project whose code is generated from a schema it declares (for example a `.proto` or OpenAPI file)
  - an executable that references 3 or more other projects
  - a content-only project (for example documentation surfaced in the solution)
  - a second assembly that a test project references
  - a vendored project
- **Small project with a purpose, weight 1:** a small project that declares something of its own and has one of these roles:
  - an executable.
  - a sample or an issue reproduction.
  - a contract or wiring assembly, where every type it declares is a contract or wiring. A contract is an interface, an enum, a delegate, or a type with only properties, fields, events and constructors. Wiring is a static class or module whose methods are all extension methods.
  - a Razor component library.
  - a project that another project references, unless it is a fragment.
- **Fragment:** a *small implementation project* is a small project that declares something of its own and is not an executable, a sample or reproduction, a contract or wiring assembly, or a component library. A *production consumer* of a project is another project in the solutions that references it and is not a test project. The count covers all C# and Visual Basic .NET projects of the solutions, including the projects left out of the score (vendored projects, non-shipping harnesses, orchestration hosts and published packages). Within that set, collect the small implementation projects that each have at most one production consumer (zero or one). If there are 2 or more, each of them is a fragment, and being referenced is not a role for any of them. If there is only one, it is not a fragment.
- **Code-free on purpose, weight 1:** a project under 10 significant lines that declares nothing of its own but is not a shell.
- **Every other project:** weight = clamp((L − 10) / 40, 0, 1).

The denominator is the number of projects in the population. The score uses the mean weight over the population and the number of shells in it.

## Thresholds
- **Shell size:** fewer than **10** significant lines.
- **Small project:** fewer than **50** significant lines.
- **Size weight:** 0 at **10** significant lines or fewer, 1 at **50** or more, and linear in between.
- **Composing executable:** an executable that references **3** or more other projects is code-free on purpose.
- **Fragments:** **2** or more small implementation projects, each with at most **1** production consumer.
- **Confirmed build failure:** a solution build failed with compiler errors about the code. When the repository has several solutions, each one is built. The result is a confirmed failure if any of them fails with compiler errors about the code that none of the reasons below explains. One build's outside reason does not excuse another build's errors. A build is not a confirmed failure when it did not run or did not finish. It is also not a confirmed failure when it failed only for a reason outside the code:
  - a missing SDK, target framework or toolchain
  - a failed restore
  - a source generator or project that could not be loaded
  - an uninitialised submodule
  - build inputs missing from the checkout

## Score
1. If the build is a confirmed failure, the score is **3.0**.
2. Otherwise:
   - surface deficit = 8 × (1 − mean weight)
   - shell cost = 1.5 × number of shells
   - deduction = min(8, max(surface deficit, shell cost))
   - score = 10 − deduction, clamped to 0 to 10 and rounded to 2 decimals.

When the build is not a confirmed failure, the score is never below 2.0. When the build status is unknown, the score rests on structure alone. Build warnings do not change the score.

## Not measured when
**Does not apply:**
- The repository has no .NET project files.
- All of its .NET projects are F#.
- C# and Visual Basic .NET hold less than half of the repository's production lines.
- .NET source (C#, Visual Basic .NET and F#) holds less than 15 % of the repository's production lines, and either the repository has no solution file or its solutions load no project.

**Could not be assessed:**
- The repository is a .NET repository that the rules above do not rule out, but it has no solution file, or its solutions load no C# or Visual Basic .NET project.

Neither outcome is a score of 0.

## What the result is not
- It is not build health. Warning counts and warning density are scored by the build-health dimensions.
- It is not behaviour or correctness. A solution that builds and is split into real projects scores high whatever its code does.
- It is not a size judgement. One large project is not a defect here. Other dimensions judge whether a project holds together.
- It is not a judgement of naming or folder conventions.
- It does not show which solution file a team uses day to day.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them. A later decision under decision 0013 will replace each with a threshold on the property.

- **Size-weight ramp:** 0 at 10 significant lines, 1 at 50, linear in between.
- **Small-project size:** fewer than 50 significant lines.
- **Composing executable:** 3 or more referenced projects.
- **Fragment count:** 2 or more small implementation projects, each with at most 1 production consumer.
- **Curve terms:** a maximum surface deduction of 8, and 1.5 per shell.
- **Build-failure cap:** 3.0.
