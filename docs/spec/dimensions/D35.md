# D35: Change Coupling

**Lens:** architecture · **Scored:** yes

## Property
Whether files that change together actually belong together: pairs that repeatedly co-change in recent git history despite having no explicit code dependency, surfacing the hidden/logical coupling (and boundaries in the wrong place) a static scan can't see. A pair is read over the last 20 changes of the less often changed of its two files, and only while the two have changed together within the year before the analysed commit, so a coupling that is broken leaves the reading.

## Applies to
Any language on the production-lines list in [production-code.md](../production-code.md), read through the repository's version history. A pair may join two files in different languages.

## Population
Production code as [production-code.md](../production-code.md) defines it, with these differences:

- **Also left out:** examples, samples and demonstrations; scaffolding templates (for example a starter project that a project template generates); the authors' own developer tools and scripts that are not published with the product; end-to-end test scripts kept outside a test folder; built or minified script bundles; literate documentation scripts.
- **Bookkeeping files are left out:** files that only hold declarations other files depend on. Examples are an import or global-using registry and an assembly-metadata file. Two more kinds of file count as bookkeeping. In both, content lines are lines that are not blank, a comment or an attribute:
  - **Module root:** the file that is its module's root (for example `lib.rs`, `mod.rs`, `main.rs`, `index.ts` or `__init__.py`). It is bookkeeping when at least 90 % of its content lines are module declarations, imports or re-exports, and at most 6 lines are anything else.
  - **Facade:** any other file. It is bookkeeping when at least 90 % of its content lines re-export another module's surface, for example re-exports and public module declarations. Plain imports do not count toward the 90 %. At most 6 lines may be anything else.
- **History, not only the tree:** a file is in the population when at least one commit read changed it. This includes production files that no longer exist at the analysed commit. A renamed or moved file counts once, under the name it has at the analysed commit. These files count in the denominator and in the 10 % of the sweep cap.
- **A pair is not read** when either file does not exist at the analysed commit.

**Commits read:** the commits reachable from the analysed commit, newest first by commit date, up to the limit under Pending re-definition. Every date is the commit date. A merge commit counts as a commit but changes no files for this reading. Authorship plays no part. A commit from a machine account counts like any other commit, and the automation-only file rule of [people.md](../people.md) does not apply here.

## Unit and denominator
- **Commit counted for a file:** a commit read that changed the file and is not a sweep (see Thresholds). These commits are the file's *revisions*.
- **Pair window:** each file's window opens at its 20th most recent revision. If a file has fewer than 20 revisions, its window opens at the start of the commits read. A pair is read from the older of its two files' openings up to the analysed commit. In other words, it is read over the last 20 revisions of whichever file reaches back further. Every count for the pair is taken inside this window.
- **Shared commit:** a counted commit inside the window that changed both files, is not a mechanical commit, and changed each file's own code. A change that is only whitespace, a tool directive, or a build stamp written onto import lines is not a code change. Such a change still counts as a revision.
- **Degree of coupling:** shared commits ÷ the smaller of the two files' revision counts, both counted inside the window.
- **Unit:** a **strongly coupled pair**. This is two production files that pass every threshold below and have no explicit dependency between them.
- **Explicit dependency:** one file references something the other declares, for example through an import, a type reference, inheritance or a registration. These also count as an explicit dependency:
  - a third file that maps one file's type to the other's;
  - relationships the language or build declares, for example alternative implementations of one declaration for build targets that never compile together (Go files with mutually exclusive build constraints, or the Kotlin `actual` implementations of one `expect`);
  - a native host file and the app code it serves through a declared platform channel.
- **Also not a pair:** a pair where either file is:
  - a version stamp: a file whose only content is at most 3 constants, each set to a plain string or number, at least one of which is a version or build number;
  - a catalogue of string literals and nothing else (at least 20 key-to-string entries);
  - a generated file that says it is generated.
- **Denominator:** the number of production files in the population, as defined above.

## Thresholds
- **Sweep commits** are left out of both revisions and shared commits. A commit is a sweep when either:
  - it changes more paths than the sweep cap, counting every path in the commit, production or not;
  - it changes at least 5 production files directly in one directory (not in its subfolders), and those are at least 25 % of the production files directly in that directory.

  The sweep cap is under Pending re-definition.
- **Mechanical commits** count as revisions but never as shared commits. They are:
  - a dependency update;
  - a release preparation or version bump;
  - a formatting, style, lint or spelling pass;
  - a move, rename or reorganisation of files or modules;
  - a documentation or API-schema migration pass;
  - an IDE cleanup, file-header or copyright pass;
  - one textual substitution applied the same way to every production file of a commit that changes at least 3 of them.
- **Each file:** at least 10 revisions inside the pair window.
- **Shared:** at least 5 shared commits inside the pair window.
- **Strength:** degree of coupling at least 50 %.
- **Live:** the pair's newest shared commit is within 365 days of the analysed commit's date.
- **Above its neighbourhood:** the two files must change together more often than files in their package usually do. The parameters are under Pending re-definition.

## Score
```
couplingRate = strongly coupled pairs ÷ production files
score        = clamp(10 − 20 × couplingRate, 0, 10), rounded to 2 decimals
```
Every strongly coupled pair counts once. This includes pairs inside a group of files that are all coupled to each other, and pairs that cross a module boundary. How findings group or rank pairs does not change the score.

## Not measured when
- The repository has no version history.
- No production file was changed in the commits read.

## What the result is not
- It does not judge whether a coupling is healthy cohesion or a leak. It only shows that two files change together.
- It only sees files that change in the same commit. It misses a coupling split across separate commits, or one that runs through configuration or build files.
- Sweeps and mechanical commits are left out, so a coupling that only ever shows up in such commits is not read.
- A coupling older than the pair window, or with no shared commit in the last year, is not read.
- It is not a static dependency measure. Other dimensions cover coupling that is visible in the code.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Commits read:** the 10,000 most recent commits.
- **Sweep cap:** the larger of 5 and (the smaller of 30 and 10 % of the production files), rounded up.
- **Directory sweep:** at least 5 production files directly in one directory (not in its subfolders), and those are at least 25 % of the production files directly in that directory.
- **Uniform substitution:** at least 3 files.
- **Bookkeeping file:** for a module root, at least 90 % module declarations, imports or re-exports and at most 6 other lines; for a facade, at least 90 % re-exports and at most 6 other lines.
- **Version stamp:** at most 3 constants.
- **String catalogue:** at least 20 entries.
- **Neighbourhood test.**
  - **Package:** a file's package is the nearest enclosing folder that declares a package or project. If there is none, the package is the whole repository.
  - **Which file it is read from:** the test is read from the pair file with fewer revisions inside the window. On a tie, it is read from each file, and the pair stays if either passes.
  - **Neighbours:** the other production files of that file's package, leaving out both files of the pair. With fewer than 8 neighbours, the pair stays.
  - **Package pass:** a commit whose code-changing production files include at least 5 of the package's files and at least 25 % of them.
  - **Counts:** all counts are taken inside the pair window. The file's *shared count* with another file is the number of commits the two share. Its *own work* with another file is that shared count minus the shared commits that were a package pass over the file's package.
  - **Outside the scatter:** a count is outside the scatter of a set of counts when it exceeds m + 2 × max(√m, 1.4826 × d). Here m is the median of that set and d is its median absolute deviation.
  - **M:** the median of the file's shared counts with its neighbours.
  - **Own outside:** M > 0, and the pair's own work is outside the scatter of the file's own work with each neighbour.
  - **When the pair stays:** the pair stays if either of these holds:
    - its shared count is outside the scatter of the file's shared counts with its neighbours, and either M = 0 or own outside holds;
    - own outside holds and the pair's own work is at least 5.
  - Otherwise it is not a strongly coupled pair.
