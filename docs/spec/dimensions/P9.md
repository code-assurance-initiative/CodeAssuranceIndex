# P9: Domain vs controller coverage

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether test coverage falls on the domain layer (the business rules) rather than on the web or controller layer, the code that receives requests and hands them to the domain and should hold little logic of its own.

## Applies to
Any language in which the repository's own tests can be run and the lines they execute can be recorded.

## Population
- **Domain layer:** production code, as [production-code.md](../production-code.md) defines it, that holds the business rules. For example entities, aggregates, value objects, domain services and the domain model, wherever the repository keeps them.
- **Web or controller layer:** production code that receives requests at the application's boundary and passes them on. For example controllers, endpoint definitions, API route handlers and page handlers (for example Django views). Application-layer command or query handlers are not web code. This layer is compared against the domain, but it does not change the score.
- **Excluded:** every file that is not production code (../production-code.md). Also excluded is every file with no executable lines, for example a file that only declares a type or a marker record. Such a file can be neither covered nor uncovered.
- **Coverage source:** the lines executed when the repository's own test suite runs at the analysed commit. A coverage report committed in the repository does not count, because it has no proven date, origin or subject.

## Unit and denominator
- **Unit:** an executable line in a domain-layer file that the test run executes (a covered line). A line is executable as the language's coverage reporting defines it.
- **Denominator:** all executable lines in domain-layer files, whether the tests execute them or not.
- **Domain coverage** is covered domain lines divided by executable domain lines, summed over all domain files. A large file weighs more than a small one. It is not the average of per-file percentages.

## Thresholds
No threshold changes the score. Two findings are reported alongside it, and neither one moves the score:
- **Inverted priorities:** web-layer coverage is 20 or more percentage points above domain coverage.
- **Low domain coverage:** when the first finding does not apply, domain coverage is below 50 %.

## Score
With `f` as domain coverage, a fraction from 0 to 1:

`score = 1 + 9 × f`, rounded to two decimals.

- f = 0 gives 1. f = 0.5 gives 5.5. f = 1 gives 10.
- The score depends only on domain coverage. Web-layer coverage does not enter it.
- A domain layer that the tests never execute is measured: f = 0, and the score is 1.

## Not measured when
- The test run at the analysed commit produced no line coverage, for example because the tests could not be built or run.
- The coverage from the run is empty or contradicts itself (see Pending re-definition).
- The test run reports no domain-layer production file with executable lines. Then there is no domain to compare, so the result is not measured, which is different from a 0. This does not apply to domain files that the run reports with all their lines uncovered. Those are measured and score 1.

## What the result is not
- It is not overall test coverage. Code outside the domain layer counts neither for nor against the score.
- It is not a judgement of test quality. A line counts as covered when a test executes it, whether or not the test checks the result.
- It does not show that the web layer is thin. It only shows where coverage falls.
- It says nothing about a repository with no recognisable domain layer. Such a repository is not measured and is not marked down.
- It is not mutation strength or branch coverage.

## Pending re-definition
These are parameters of the existing reading's model, and today's scores depend on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Empty coverage:** a run whose files hold fewer than 10 executable lines in total counts as empty and is not measured.
- **Self-contradictory coverage:** a run counts as broken and is not measured when both of these hold: its whole-run line coverage is at or below 1 %, and its whole-run branch coverage is more than 5 percentage points above its line coverage.
