# R5: Dependency Freshness

**Lens:** productionReadiness · **Scored:** yes

## Property
How outdated the npm dependencies are (a maturity signal). JS/npm CVEs are scored separately in D30 (JS/npm Dependency Vulnerabilities).

## Applies to
This dimension applies to JavaScript and TypeScript projects whose dependencies are managed with npm and pinned in an npm lockfile (`package-lock.json`). Single-file components, for example Vue or Svelte, count as part of such projects. A repository whose JavaScript dependencies are pinned only by another package manager's lockfile (for example yarn, pnpm or bun) is not measured.

## Population
- **The repository has a JavaScript or TypeScript frontend.** It holds at least 5 JavaScript, TypeScript, Vue or Svelte source files, and at least one of them is production code as [production-code.md](../production-code.md) defines it. A repository without one gets no R5 result.
- **Only one npm project is read: the repository's own npm project nearest the root.** This is the npm project that has an npm lockfile and sits closest to the repository root. A lockfile does not count as the project's lockfile if it is in vendored or copied-in third-party code, an installed dependency folder, build output or a hidden folder, as [production-code.md](../production-code.md) defines them. A lockfile in a test project or an examples folder can count. Other npm projects deeper in the repository are not read.
- **The dependencies in scope are the project's direct dependencies.** These are the packages its manifest declares, development dependencies included, at the versions its lockfile pins. A package that only arrives through other packages is not counted.
- Unlike most dimensions, R5 does not apply the test exclusions. A development dependency used only by tests counts like any other.

## Unit and denominator
- **Unit:** an outdated package. A direct dependency is outdated when either of these is true:
  - its pinned version is older than the newest release its declared range allows;
  - its pinned version is older than the release under the registry's latest tag.

  Either one is enough. A package already at the newest version its range allows still counts if a newer release carries the latest tag. A package counts once, however far behind it is.
- **Denominator:** none. The score depends on the absolute number of outdated packages, not on their share of all dependencies.

## Thresholds
- A package counts as outdated as soon as it is one release behind. How far behind it is (patch, minor or major) makes no difference.
- At 80 or more outdated packages the score reaches its floor of 2.

## Score
With `n` the number of outdated packages:

```
score = max(2, 10 - 0.1 × n)
```

- `n = 0` gives 10.
- Each outdated package lowers the score by 0.1.
- From `n = 80` the score stays at 2. It is never lower than 2.

## Not measured when
- The repository has no JavaScript or TypeScript frontend as defined under Population. There is no result at all.
- The repository's own code has no npm lockfile. This includes a repository whose JavaScript dependencies are pinned only by another package manager's lockfile.
- The newest published versions cannot be read, for example because the package registry cannot be reached or refuses the request. This is a failure of the measuring environment, not a statement about the repository.
- The check for newest versions returns an error or no readable answer. A failed reading is never treated as zero outdated packages.

## What the result is not
- It is not a security result. A current package can still have known vulnerabilities, and an outdated one can have none. Vulnerabilities are D30's concern.
- It does not weigh how far behind a package is. A package one major version behind and one a patch behind count the same.
- It does not cover dependencies that only arrive through other packages, other npm projects in the same repository, or dependencies in other ecosystems (for example NuGet, PyPI or Maven).
- It is not a share. A project with many dependencies scores lower than a small one with the same proportion outdated.
- It does not say whether upgrading is safe or worthwhile.

## Pending re-definition
These are parameters of the existing reading's model. Today's scores depend on them, and a later decision under decision 0013 will replace each one with a threshold on the property.

- **Frontend presence:** at least 5 JavaScript, TypeScript, Vue or Svelte source files, at least one of them production code.
- **Penalty per outdated package:** 0.1 points.
- **Score floor:** 2, reached at 80 outdated packages.
- **One project only:** only the npm project nearest the repository root is read.
