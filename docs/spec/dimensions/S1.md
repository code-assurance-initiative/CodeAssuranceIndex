# S1: Web-Security Posture

**Lens:** securityCompliance · **Scored:** yes

## Property
Transport security, security headers, secure cookies, input validation, middleware order and crypto hygiene (presence, not runtime).

## Applies to
- **Web controls** (transport, security response headers, cookies, input validation, middleware order): code in any language that serves HTTP itself, and the serving configuration the repository commits for that surface. Examples of serving configuration are a web server configuration, a static host's header file and an application server's configuration file.
- **Crypto hygiene, outbound TLS and credential handling:** code in any language, whether or not it serves HTTP. This also covers the committed configuration that the code's clients read.
- **Third-party script integrity:** markup the repository ships (HTML, and the markup in views and single-file components), whether or not the repository serves that markup itself.

## Population
The population is production code as [production-code.md](../production-code.md) defines it. This dimension adds four things:
- **Serving configuration:** the configuration files the repository commits to serve its own HTTP surface. An example is a web server configuration that sets response headers.
- **Client configuration:** committed configuration that the code's clients read, for example a database connection string. It is read for defects such as certificate validation turned off. It does not make a web surface.
- **Shipped markup:** pages and views the repository ships to its users. This includes pages a library hands to its consumers.
- **Views, for script integrity only:** this dimension also reads server-side view templates (for example Razor or Blade views) for third-party script integrity. It reads them for nothing else. [production-code.md](../production-code.md) otherwise excludes them.

Configuration under tests, test support or build output is excluded, the same way code there is.

A repository **has a web surface** when it serves HTTP itself. That means its production code serves HTTP, or it commits the serving configuration for its own HTTP surface. Examples of code that serves HTTP:
- an HTTP API;
- a web UI with server endpoints or server-rendered views;
- web middleware it runs (HTTPS redirection, HSTS, security headers, cookie handling);
- a token-validating request pipeline it configures for itself.

These have no web surface:
- a library, command-line tool, desktop app or worker that starts no server;
- a library that builds on a server framework, or configures other applications' pipelines, but starts no server of its own.

A server that listens only on the loopback interface still has a web surface. When every server the repository starts listens only on loopback, its traffic never crosses a network, so:
- its transport counts as secured;
- its cookies need not set Secure, though HttpOnly still applies.

## Unit and denominator
The unit is the **control**. A control is a property that a repository's production code and configuration either show or do not show. Each control counts once per repository, however many places show it. There is no denominator.

**A weak hash** is MD5 or SHA-1 used for a security purpose, meaning one where security depends on collision or preimage resistance. Examples of such purposes:
- a password;
- a signature or MAC;
- a derived key or token;
- a digest compared to authenticate a caller;
- a digest used to admit content.

A digest whose code shows only a non-security purpose is not a weak hash. Examples are a checksum, an ETag, a cache key or cache-file name, a lock or temp file name, a content address, a shard pick, or a digest a protocol requires. A digest whose code shows no purpose at all counts as a weak hash.

**A weak cipher** is DES, 3DES, RC4, RC2 or Blowfish.

**Positive controls** are read only when the repository has a web surface:

| Control | Holds when |
|---|---|
| Transport | any one of these holds: HTTPS is enforced (plain requests are redirected to HTTPS, or TLS is served); HSTS is sent; the app runs behind a TLS-terminating proxy that the repository configures; or every server listens only on loopback |
| Security headers | the repository sets security response headers, in code or in serving configuration (see Thresholds) |
| Secure cookies | no cookie the code sets leaves HttpOnly or Secure off (Secure is not required when every server listens only on loopback), and the code either configures cookie flags or sets no cookies |
| Input validation | inbound requests are validated before a handler acts on them (for example declared model validation, or a validation library) |
| Middleware order | authentication and authorisation middleware run in the order that makes them work (authentication first), or no such middleware is present |
| Crypto algorithms | no weak hash and no weak cipher is used |

**Weak algorithms** (a weak hash or a weak cipher) are read in every repository.

**Defects** are read in every repository:
- A password hashed with a fast digest and no key-derivation function.
- A password hash compared in a way that is not constant-time.
- A password or credential sent in a URL query string.
- Passwords stored as plaintext.
- Personal or diagnostic data sent in an outbound URL.
- TLS certificate validation turned off, in code or in committed configuration (for example a connection string that trusts any server certificate).
- An obsolete protocol allowed (SSL 3.0, TLS 1.0, TLS 1.1).
- A weak hash used as the only integrity check on content the code then trusts.
- **Fixed key material:** a cipher key, a passphrase, a key-derivation salt or data-protection entropy that is fixed in the source. A published standard test vector used in a known-answer self-test does not count. An IV is not key material. It is judged only as a static IV.
- **A static IV:** encrypting code gives every message it encrypts the same initialisation vector. Either the IV is fixed in the source, or it comes from the same key derivation as the key, so it changes only when the password changes. Code that only decrypts, and reproduces an IV chosen by the encrypting side, does not count. A fixed IV counts here only, never also as fixed key material.
- Ciphertext produced without authentication, for example CBC with no MAC.
- An encryption transform used in the wrong direction.
- A crypto stream opened in a mode that contradicts its use.
- A key-derivation function run below its work-factor floor.
- A secret serialised into a log.
- A shipped page that loads a third-party script without integrity verification (Subresource Integrity).
- An access-token check with one of its validations turned off.

## Thresholds
- **Core security headers:** Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options and X-Frame-Options.
  - Other recommended headers count as "headers configured" but earn nothing.
  - A repository that sets headers through a means that sets the whole recommended set at once holds all four.
  - A repository that sets security headers without its code or configuration naming the individual headers holds all four.
- **Key-derivation work-factor floors:** a use is a defect when the cost the source fixes (a literal or a constant) is below the floor for its function. Where the call leaves the cost out, the cost is the library's default. A cost that the code takes from configuration or a parameter is not judged.
  - PBKDF2-HMAC-SHA1: 1,300,000 iterations.
  - PBKDF2-HMAC-SHA256 or PBKDF2-HMAC-SHA224: 600,000 iterations.
  - PBKDF2 with any other pseudo-random function (for example SHA-384 or SHA-512), or with one the source does not name: 210,000 iterations.
  - bcrypt: work factor 10.
  - scrypt: N at least 8,192 and N·r·p at least 655,360.
  - Argon2: memory at least 7,168 KiB, and memory (KiB) × iterations at least 35,840.
- **Token validation severity**, most severe first: signing-key validation, signed tokens required, audience, issuer, lifetime.

## Score
Apply the first case that fits.

**1. The repository has a web surface.** The base is the sum of the positive controls it holds:
- Transport: 2.0
- Security headers: 0.5 for each core header set, from 0 to 2.0. A repository that holds all four under Thresholds gets 2.0.
- Secure cookies: 1.5
- Input validation: 2.0
- Middleware order: 1.5
- Crypto algorithms: 1.0

**2. The repository has no web surface, and has a weak algorithm or a defect other than token validation turned off.** The base is 10. Subtract 2.0 if it uses a weak hash and 2.0 if it uses a weak cipher.

**3. Otherwise** the dimension is not measured (see below).

In cases 1 and 2, subtract from the base each defect that is present. Each defect counts once:

| Defect | Deduction |
|---|---|
| Password hashed without a key-derivation function | 4.0 |
| Certificate validation turned off | 4.0 |
| Fixed key material | 4.0 |
| Password in a query string | 3.0 |
| Plaintext password storage | 3.0 |
| Secret serialised into a log | 3.0 |
| Personal or diagnostic data in an outbound URL | 2.0 |
| Obsolete TLS or SSL version allowed | 2.0 |
| Weak hash as the only integrity check | 2.0 (on top of the weak-hash cost) |
| Third-party script without integrity verification | 2.0 |
| Unauthenticated ciphertext | 2.0 |
| Wrong-direction transform | 2.0 |
| Crypto stream mode contradiction | 2.0 |
| Static IV | 2.0 |
| Key-derivation function below its floor | 2.0 |
| Non-constant-time hash compare | 1.5 |
| Token validation off | only the most severe validation turned off is charged: 3.0 for signing key or signed tokens, 2.0 for audience or issuer, 1.0 for lifetime |

The result is rounded to one decimal and kept within the range 0 to 10.

## Not measured when
- The repository has no web surface, no weak algorithm and no defect other than token validation turned off. The dimension is then not applicable and is left out of the securityCompliance lens.
  - This includes a repository without a web surface whose only defect is token validation turned off.
  - It also includes a repository without a web surface whose only MD5 or SHA-1 use serves a non-security purpose.

## What the result is not
- It is not a runtime test. It reads whether controls are present in code and configuration, not whether a deployed service enforces them. For example, it does not see headers that a proxy outside the repository adds.
- It is not a vulnerability scan or a penetration test.
- Whether an MD5 or SHA-1 use is a weak hash is judged from the purpose its code shows. Where the code shows no purpose, the use counts. The finding names the use so a reader can judge it.
- A high score does not mean the application is free of injection, access-control or logic flaws.
