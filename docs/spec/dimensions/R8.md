# R8: Dependency Hygiene

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether an npm package's declared dependencies match what its code uses: dependencies its package.json declares that the code does not use, packages the code imports (by any form of loading, for example import or require) that are not declared anywhere, and packages needed only for types or tests (for example @types packages or a test runner) declared as production dependencies rather than development dependencies. Built-in runtime modules and relative imports of the package's own files are not packages. Not a check of whether dependencies are outdated, vulnerable or licensed.

## Applies to
This dimension covers JavaScript and TypeScript code in npm packages, including single-file components (for example Vue or Svelte). An npm package is a folder that holds a `package.json`. Code in other languages is not read. A file belongs to the package in the nearest folder above it that has a `package.json`.

## Population
- **Manifests:** every `package.json` of the repository's own packages, read in four declaration blocks: `dependencies`, `devDependencies`, `peerDependencies` and `optionalDependencies`. Manifests inside vendored code, installed dependency folders and build output are not in scope.
- **Code read, for all four checks:**
  - production code as [production-code.md](../production-code.md) defines it;
  - tests and test support;
  - the package's own tool configuration files and build scripts (for example `vite.config.ts`), which [production-code.md](../production-code.md) leaves out of production code but which load packages;
  - the package's `package.json` scripts.

  Generated code, vendored code and build output are not read.
- **Out of scope for the type-only and test-only checks:** a `package.json` that is itself test support (for example a test fixture's manifest). Its split between production and development dependencies ships to no one.
- **Out of scope for the unused check:** a package whose shipped code is build output that the repository does not hold. None of the code that would import its dependencies is present.
- **Not packages:** a specifier that names no installable npm package is not a package. Examples:
  - built-in runtime modules (for example `fs` or `node:fs`);
  - relative and absolute file imports;
  - the repository's own workspace packages;
  - path aliases the project's own build or compiler settings define;
  - a package's own declared subpath imports (`#...`);
  - virtual modules a build tool or framework supplies;
  - names npm does not accept as a package name;
  - modules the host runtime injects (for example `vscode`);
  - modules the repository supplies itself, either declared in its own code (for example a TypeScript `declare module`) or created by its own scripts;
  - packages that another ecosystem's manifest declares and delivers to the JavaScript build.

## Unit and denominator
There are four kinds of finding. Each is counted once per pair of a `package.json` and a package name, however many files or lines are involved.

- **Unused dependency (U):** a name in a package's `dependencies` or `devDependencies` that nothing in that package uses. A name in both blocks counts once.
  - A package is used when anything the package holds loads, runs or consumes it. Examples:
    - an import, a `require` or a dynamic import;
    - a script or build command that runs it;
    - a tool configuration that loads it by name;
    - the compiler loading its types (for example through a tsconfig `types` or `extends` entry);
    - another declared dependency that requires it as a peer;
    - code in a nested workspace member that imports it.
  - A sibling package's use does not count, because that use belongs in the sibling's own manifest.
  - An `@types/*` package is used when the compiler reads it.
- **Unlisted import (N):** a package that code imports but that neither its owning `package.json` nor any `package.json` above it declares, in any of the four blocks.
  - It counts as declared when another member of the same workspace declares it and the workspace installs all members' dependencies into one shared tree.
  - A type-only import also counts as declared when its `@types` companion is declared.
  - Code that no `package.json` owns is counted under the repository root.
  - The pair counts once, even when every import of it is type-only.
- **Type-only production dependency (T):** a name in `dependencies` (not `devDependencies`) that the package's code needs only for types. Examples are a package whose every import is type-only (for example `import type`) and an `@types/*` package. It is not counted when the package also needs it in production. That is the case when:
  - the package's own published type declarations import it, so consumers need it installed;
  - another production dependency requires it as a peer at runtime;
  - the build consumes it without importing it (for example a CSS framework);
  - every use of it is in tool configuration files, which the tool runs.
- **Test-only production dependency (X):** a name in `dependencies` that only tests and test support use. Component showcase files (for example stories) count as test support here. A package that a non-test script also runs (for example in `build` or `start`) is not counted. A pair counted under T is not also counted under X.

There is no denominator, so the counts are absolute. The number of declared names only decides whether the dimension is measured. That number is each `package.json`'s `dependencies` plus `devDependencies`, de-duplicated within one manifest and summed across manifests.

## Thresholds
- One qualifying pair is enough for a finding. There is no minimum count and no minimum share.
- The dimension is not measured when the repository declares zero names (see below).

## Score
score = 10 − 0.5 × U − 2.0 × N − 1.0 × T − 1.0 × X, clamped to the range 0 to 10.

Each weight applies per finding:

| Finding | Weight |
|---|---|
| Unlisted import (N) | 2.0 |
| Type-only production dependency (T) | 1.0 |
| Test-only production dependency (X) | 1.0 |
| Unused dependency (U) | 0.5 |

For example, the score reaches 0 at 5 unlisted imports or at 20 unused dependencies. Repository size does not scale the score.

## Not measured when
- The repository has no JavaScript or TypeScript code in scope.
- No `package.json` in scope declares any name in `dependencies` or `devDependencies`. Imports may then resolve through a host runtime rather than npm, so there is nothing to check them against.

## What the result is not
- It is not a check of whether dependencies are outdated, vulnerable, licensed, pinned or locked.
- It is not proof that a removal is safe. A package loaded only through a value the code computes at runtime can read as unused.
- It is not a measure of how many dependencies a package has. A package with many correctly declared dependencies scores 10.
- It is not relative to size. One unlisted import costs the same in a small package as in a large monorepo.
- It does not judge whether the packages in `peerDependencies` or `optionalDependencies` are used. Those blocks only count as declarations.
