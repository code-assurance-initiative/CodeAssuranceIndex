# M3: Folder & project structure

**Lens:** maturity · **Scored:** yes

## Property
Whether the repository is organised deliberately: production code and tests are set apart in a way its ecosystem or the repository itself declares.

## Applies to
Any language. The dimension reads how the whole repository is laid out: where its production code and its tests sit, and what its build, package and test configuration declares about them. It does not read project or namespace names.

## Population
- **Production code:** as [production-code.md](../production-code.md) defines it. This includes the authors' own scripts and tools, wherever they sit.
- **Test code:** test files and test support as [production-code.md](../production-code.md) defines them. It also includes test-only code that the ecosystem sets apart inside a production file, for example a Rust `#[cfg(test)]` module or a Homebrew formula's `test do` block.
- **The repository root:** the top folder of the repository. A file is "at the root" when it sits directly in that folder.
- **Product directories:** the folders directly below the root, except:
  - hidden folders, whose names start with a dot;
  - folders for documentation, examples and samples, assets, continuous integration or the repository's own tooling;
  - folders that hold only test code.
- **Examples and samples:** code in a top-level examples or samples folder cannot earn the production half. It still counts in the production lines of the test half.
- **Everything else:** anything else [production-code.md](../production-code.md) leaves out is ignored here, for example generated code, vendored code, build output, tool configuration files, build scripts and specimen collections. None of it can earn a credit or cost one.

## Unit and denominator
The unit is the repository. The dimension asks it two yes-or-no questions, called halves.

**Production half: is production code set apart?** It holds in either of these cases:
- **(a) A declared source location.** Production code sits where the ecosystem's build or package tool, or the repository's own manifest, says its source lives. For example:
  - a root `src/` or `lib/` folder;
  - each member's own source folder in a declared workspace (for example a JavaScript, Cargo, BEAM umbrella, pub or JVM multi-module workspace, or a JVM `src/main`);
  - the targets a Swift package manifest declares;
  - a Composer autoload root, or the source root a TypeScript project declares;
  - a gem's `lib/` or an OTP application's `src/`;
  - the folder a framework requires for application code (for example a Next.js `app/`).

  A Go module declared at the root (its `go.mod` sits at the root) is enough on its own, because Go places a module's packages at paths relative to the module root, the root included. In case (a), production files at the root do not withhold the half.
- **(b) A clean root.** No production code file sits at the root, and production code sits beneath at least one product directory. The folder's name does not matter, for example a Rails `app/`, a .NET project folder, or a folder named after the product. Any production code file at the root withholds this case, including the authors' own scripts and tools (for example a `release.py`). Files that are not production code do not withhold it, for example a tool configuration file or a build script.

**Test half: are the tests set apart?** It holds when both of these are true:
1. **Test code is set apart in a way the ecosystem or the repository declares.** For example:
   - a test folder, at the root or inside each package, module, crate or component (`tests/`, `test/`, `spec/`, `specs/`, `__tests__/`);
   - a declared test project (for example `Product.Tests/` holding its own project file);
   - a test target or test source set (for example Xcode or Swift package test targets, `src/test/` or `src/jvmTest/`);
   - the ecosystem's naming convention for test files placed beside the code they test (for example `_test.go`, or `name.spec.ts` beside `name.ts`);
   - a test-only compilation unit (for example a Rust `#[cfg(test)]` module);
   - a test block that the packaging tool runs on its own (for example a Homebrew formula's `test do` block).

   A test inside a production build unit is not set apart when nothing declares it apart, for example a test class inside the production project. A folder that holds no test code, or only test data, does not set any tests apart.
2. **The tested languages are the product.** The tested languages are the languages of the test code that step 1 finds set apart. The denominator is the repository's production lines, as [production-code.md](../production-code.md) defines them, including the authors' examples, samples and demonstrations.
   - Test-only code inside a production file (for example a `#[cfg(test)]` module) is not a production line.
   - JavaScript and TypeScript count as one language here, because a JavaScript suite may test TypeScript source.

A repository with no test code has not set any apart.

## Thresholds
- **Production half:** either
  - at least one production code file in a declared source location, or a Go module declared at the root; or
  - zero production code files at the root and at least one production code file beneath a product directory.
- **Test half:** both of these:
  - at least one test code file set apart as described above;
  - the tested languages hold more than 50 % of the production lines. This is a strict majority: at exactly 50 % the condition is not met, and with zero production lines it is not met.

## Score
The score starts at 6:

- add 2 when the production half holds;
- add 2 when the test half holds.

| Production half | Test half | Score |
|---|---|---|
| no | no | 6 |
| yes | no | 8 |
| no | yes | 8 |
| yes | yes | 10 |

No other scores are possible. A repository with no production lines never earns the test half. It scores 8 when its production half holds, for example when a Go module is declared at the root, and 6 otherwise.

## Not measured when
Only when there is no repository to read. In every other case M3 is measured and scored.

## What the result is not
- **It is not a grade of the architecture.** It does not judge whether the folders inside the product are well chosen, how modules depend on each other, or whether names are consistent.
- **It never asks for one particular folder name.** Any layout the ecosystem or the repository declares counts the same.
- **It does not measure tests.** It does not judge how many tests there are, what they cover or how good they are. Other dimensions do that. With no tests, the test half is simply not credited.
- **It is never below 6.** A score of 6 means neither half holds. It does not mean the repository is disorganised. A repository that mixes everything at the root and one that has nothing to separate both score 6.
- **It is about the product, not a minor part of it.** Tests that exist only in a minor language do not stand in for an untested product.
