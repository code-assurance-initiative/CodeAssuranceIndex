# X18: Disposal-pattern correctness

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property
Whether a type's disposal matches what it OWNS — releasing what it created, leaving alone what it was handed, and not declaring a finalizer for state that has nothing unmanaged to finalize.

## Applies to
Any programming language in which code holds resources that it must release explicitly, beyond memory the runtime reclaims on its own. Examples are disposable and closeable types, finalizers, files, sockets, connections, transactions, locks and raw handles. Markup and styles are out of scope.

## Population
Production code as [production-code.md](../production-code.md) defines it. In addition:

- **One type, several parts.** A type whose declaration is split across several parts (for example a generated designer part and a part the developer edits) counts as one type. Whatever its generated part creates, the type created. Its release may be in any part.
- **Values that hold nothing to release.** Some values have a releasable type but hold nothing that needs releasing, for example an in-memory stream over its own buffer, a string reader or a string writer. Such a value is not a site and cannot carry issue 2, 4 or 8. Releasing one that the type was handed is still issue 1.
- **Values released completely by scope.** A value that the language releases fully and correctly when its owner leaves scope is not a site, for example a Rust file handle whose drop closes it. A value whose automatic release is not the release it owes is a site. Examples: a transaction whose drop rolls back, a buffered writer whose drop throws away the flush error, a value whose release is an explicit consuming call.

## Unit and denominator
**A site** is one place in the code where ownership of a releasable resource is decided. Each place counts once, even when more than one description below fits it. Each kind of site can carry only the issues listed with it:

- **A type that makes a disposal claim.** The type declares itself releasable (for example it implements `IDisposable`, `IAsyncDisposable` or `AutoCloseable`), declares its own parameterless release method, or declares a finalizer. Its fields belong to this site and are not sites of their own. Issues 1, 2, 3, 7.
- **A field in a type with no disposal claim.** The type keeps a releasable resource in a field. Either every assignment opens a new resource for the type to own (for example a file or a connection), or every assignment constructs the value and some caller creates the owning object into a local per call and drops it. Issue 2.
- **A held resource.** A block acquires a releasable resource or a lock. It either binds the resource to a local outside a construct that releases it at the end of scope, or does not keep it at all. Examples of such constructs: a C# `using`, a Java try-with-resources, a Python `with`, a JavaScript `using`, a block form that closes on exit. A local that is later handed on (passed, returned, stored or captured) is still a site and carries no issue. A local released later is the same site. Issues 4, 8, 11.
- **A release suppressed by hand.** Either code explicitly stops an owned value's automatic release (for example Rust's `mem::forget` of an owned value, or wrapping a local in `ManuallyDrop`), or a type has a field whose automatic release is switched off. Each such call or field is one site. Issue 9.
- **A raw handle taken.** Code gives up an owned value in exchange for a raw pointer or descriptor (for example `into_raw` or `into_raw_fd`). Issue 10.
- **A replacement or detach.** An assignment replaces or detaches a releasable value that an object holds. Issue 5.
- **A scope.** A block creates a scope that it has to release, for example a dependency-injection scope. Issue 6.

**An issue** is one mishandled release at a site:

1. **Releases what it was handed.** A type releases a field, property or constructor parameter it does not own. It does not own a value when every assignment takes a value passed in at construction, unless ownership moved with the hand-over. Ownership moves when the type wraps a value of its own family (for example a stream wrapping a stream), when the parameter is named, declared or documented as owned, when the release depends on a flag the caller passed (for example `leaveOpen`), or when every caller gives the value away. A handed value whose declared type is an interface or abstract resource class is an issue unless ownership moved. A handed value of a concrete type is an issue only when the code that handed it over also releases it, or when a container resolves it. A bare release token is judged under issue 7, not here.
2. **Never releases what it created.** The type owns a field (every assignment creates a new instance) and never releases it. Setting the field to null or default is not a release. If the type makes a disposal claim, its release method never releases the field. Any method of the same type that the release method calls counts as part of the release, and so does handing the field to a container or parent that the type releases. If the type makes no claim, nothing releases the field anywhere in the type or in the types it inherits from or that inherit from it, and nothing returns it, passes it on or captures it.
3. **Needless finalizer.** The finalizer's body is only a call to the type's own release method, and the type holds nothing unmanaged. Unmanaged means a native handle or pointer, a safe handle, an external or imported native member, or use of native memory or marshalling.
4. **Abandoned.** A block acquires a resource and never releases it. Either the value is not kept at all, or every reference to the local is a plain use through it.
5. **Lost on replacement.** A held releasable value is overwritten or detached without being released, where the same method shows that the previous value had to be released first.
6. **Unreleased scope.** A block creates a scope and never releases it.
7. **Unprotected token release.** The release method gives back a value the type was handed only so that it could give it back, such as a bare release token (for example a lock held for this instance). Earlier calls in the same method can throw, nothing protects them, and so a throw skips the release.
8. **Not released on every path.** A block releases a held resource on some way out but not on all of them. A way out can be:
   - the end of the block or function;
   - a return that does not return the resource;
   - a raise, throw or exit;
   - a yield in a generator;
   - rebinding the local, or the next turn of the loop that acquired it;
   - a failed clause of a match or `with` chain;
   - a failure of a statement between the acquisition and the release that can fail, for example a call or an asynchronous wait.

   A release in a `finally` or the equivalent (`after`, `ensure`, a deferred release) covers every way out. The wait that is itself the release (for example `await x.close()`) does not count. A site carries at most one of issues 4 and 8.
9. **Release suppressed and never restored.** The automatic release was stopped and nothing releases the value later. A forget is not an issue when the value's contents were moved to another owner first, when the value is the repository's own type whose release the forget means to skip (for example a guard being defused), or when the same function hands what the value holds on through a raw handle.
10. **Raw handle never reclaimed.** The raw handle is discarded on the spot, or nothing in the production code ever rebuilds an owner of that kind from a raw handle or closes the descriptor.
11. **Lock held across a wait.** A synchronous lock guard is still held at an asynchronous wait or a sleep. An asynchronous lock built to be held across a wait is not an issue.

The denominator is the number of sites. When the number of issues is at least the number of sites, the denominator is the number of issues plus one.

## Thresholds
- A field's ownership is judged only when every assignment to it in the declaring type agrees. If every assignment creates the value, the type owns it. If every assignment takes a constructor parameter, the value was handed over. A field whose assignments do not all agree is not judged. An assignment that clears the field (to null or default) does not count.
- A local is judged under issues 4, 8 and 11 only while every later reference to it is a use through it (a member read, call or write, a borrow, or an argument to a function that reads through it and keeps nothing).
- A lock taken by an explicit acquire call is a site only when the same function also releases it somewhere.
- Under issue 8, when the code returns the resource on some path, a failing statement does not count as a way out. For a value whose automatic release is the right outcome on failure (for example a transaction that rolls back), leaving on an error does not count either.
- A finalizer counts as needless only if its single statement is the call to the type's release method.

## Score
Let `k` be the number of issues and `s` the number of sites.

- If `k = 0`, the score is 10.
- Otherwise let `n = max(s, k + 1)` and `d = k / n`, clamped to between 0 and 1. Then:
  - `isolation = max(0, 1 - d / 0.10)`
  - `headroom = min(1, max(0, log10(n) / log10(200)))`
  - `ceiling = 6 + 2 × isolation × headroom`
  - `score = 1 + (1 - d) × (ceiling - 1)`, clamped to between 1 and `ceiling` and rounded to 2 decimal places.

Any issue caps the score at 8. One issue among many sites scores close to 8. Once issues reach 10 % of sites the ceiling is 6, and the score falls toward 1 as issues approach one per site.

## Not measured when
- The code has no site and no issue.
- The repository has no production code in a language this dimension applies to.

## What the result is not
- It is not a leak detector for the whole program. It judges ownership only where the code settles it. A resource that leaves its block, or a field whose assignments do not all agree, is not judged.
- It does not judge finalizers that do more than call the release method.
- It does not show that a release happens on every path, except where an issue on this page says so (issues 7, 8 and 11).
- No published score includes it today, because the one existing engine reports it advisory.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Density at which the ceiling bottoms out:** 10 % of sites (the `0.10` above).
- **Site count at which the ceiling stops rising:** 200 sites.
- **Ceiling range for a non-zero count:** from 6 up to 8.
- **Floor:** 1.
