# D29: Static Analysis (SAST)

**Lens:** securityCompliance · **Scored:** yes

## Property
Real static-analysis (SAST) findings — likely security bugs in the code, any language.

## Applies to
Any language, and the files around the code that run or set up what runs. For example: source code in any programming language; markup (HTML) and server-side page templates, including scripts embedded in them; shell, PowerShell and batch scripts; make recipes and other build scripts; SQL, including database migrations; continuous-integration workflows; infrastructure-as-code and deployment manifests (for example Terraform files or Kubernetes YAML); environment and application settings files (for example `.env` or `appsettings.json`); and other YAML, XML or JSON configuration.

## Population
This dimension does not use the production code that [production-code.md](../production-code.md) defines, and those exclusions do not apply here. The population is every file that version control tracks, of any kind, except the files listed below. Nothing else is out of scope.

Out of scope:
- **Files version control does not track**, for example files a build or an install wrote into the working copy.
- **Committed data files**, for example tables, logs, serialised datasets and databases, and plain-text files. Two exceptions stay in scope: JSON files, which are read as configuration (for example access policies), and plain-text files that are build inputs (for example dependency requirement lists or CMake build files).
- **Generated code**, including compiled or minified bundles committed to the repository. Exception: a continuous-integration workflow that a tool generated stays in scope, because it runs in the project's own pipeline with the project's credentials.
- **Vendored code:** third-party code copied into the repository.
- **Files the repository itself declares not to be the product:** files its own settings mark as generated, vendored or documentation.
- **Documentation:** prose files (for example Markdown or reStructuredText) wherever they are, everything in a documentation folder tree, and code shown inside documentation.
- **Configuration and manifest files in test fixtures or samples**, for example Kubernetes YAML, Terraform or container files that a test reads as input.
- **Folders the language's own toolchain never builds**, for example Go's `testdata` folders and, in a Go module, folders whose names start with `_`.
- **Maintainer-only scripts:** a script that the maintainers run by hand, that no build, release or continuous-integration step runs, and that does not ship. For example, a one-off data-cleanup helper in a tooling folder. This also covers the modules of a development-only tool package that ships nothing. Exception: an installer that the project's own documentation tells users to run stays in scope.
- **Code in a conditional-compilation region** that no build configuration of the project ever compiles.
- **Container build files**, for example `Dockerfile` or `Containerfile`. D31 measures these.
- **Workflow files kept where no continuous-integration platform runs them.** For example, a complete workflow stored as a template or reference, or one nested inside another project's folder.
- **Test specimens for a static-analysis rule's own tests**, where every flagged line is vulnerable on purpose.
- **Exported monitoring dashboards.**

So these are **in scope**, unlike in [production-code.md](../production-code.md):
- tests and test support (test source is read like any other code)
- build scripts and tool configuration files
- shell and batch scripts, and SQL
- hidden folders, for example `.github/workflows`
- server-side templates (for example Razor or Blade views)
- benchmark projects
- evaluation inputs that are not configuration or manifest files
- specimen collections
- TypeScript declaration files
- package-manager lockfiles
- YAML, XML and JSON configuration

A linked folder's files count once, under their real location.

## Unit and denominator
**Unit:** a finding. A finding is one likely security weakness of a recognised kind (for example a kind listed in CWE or the OWASP Top Ten) at one place in the code (file and line). These rules decide what counts:
- A weakness counts once, however many rules describe it.
- A match that the cited code itself refutes is not a finding. For example, a "missing secure flag" claim on a cookie that sets the flag is not a finding.
- Sites that one decision fixes count as one finding:
  - every step that references the same out-of-support major version of a CI action;
  - every entry of one dependency-update configuration file that lacks an update cooldown.

  Two configuration files are two decisions, so they are two findings.
- An unpinned CI action reference is one that is not a full commit hash. It is reported, but it does not count toward this score when D36 measures that file's pinning. When D36 does not measure that file, the reference counts here.

Every finding has one severity: critical, high, medium or low. This is the severity its rule states. A rule that uses a three-level scale maps as follows: error is high, warning is medium, and anything else (for example informational) is low.

**Denominator:** none. The score depends on the weighted count of findings, not on the size of the code.

## Thresholds
Each finding adds its severity weight to the repository's weighted total W:

| Severity | Weight |
|---|---|
| Critical | 10 |
| High | 5 |
| Medium | 1.5 |
| Low | 0.4 |

## Score
score = 10 × 0.5^(W / 20), rounded to 2 decimals.

- W = 0 scores 10. This covers both no findings and nothing in scope.
- W = 20 scores 5. For example, four high findings or two critical findings give W = 20.
- Each further 20 halves the score again. For example, nine high findings give W = 45, which scores 2.10.
- The score falls toward 0. After rounding it reaches 0.00 once W is above about 220. For example, 23 critical findings give W = 230.

## Not measured when
- The analysis cannot run in the scan environment.
- The rule set did not load.
- The analysis report cannot be read.

In each of these cases the dimension has no score. It is not scored 10 and it is not scored 0.

If the analysis cannot fully parse a file, the dimension is still measured. The rest of the repository is scored, and the result discloses the files or regions that were not read.

## What the result is not
- It is not proof of security. A 10 means no finding was made. It does not see a weakness of a kind no rule describes, a flaw in business logic, or a weakness that shows only at runtime.
- It is not a density. A large repository gets no more allowance than a small one.
- It does not cover vulnerable dependencies, leaked secrets (D28) or container build files (D31). CI action pinning counts here only in files whose pinning D36 does not measure.
- It does not judge whether a finding can be exploited in a given deployment.
