# D23: Boundary Type-Coupling

**Lens:** architecture · **Scored:** yes

## Property
Whether domain types (IDs, enums, value objects) leak across bounded-context boundaries.

## Applies to
This dimension applies to any programming language that declares named types whose members other code can see, for example C#, Java, Kotlin, TypeScript, Go, Python and Dart. It does not apply to markup (HTML) or styles (CSS), because they declare no types.

## Population
- **Code:** production code as [production-code.md](../production-code.md) defines it. The dimension reads only the types the authors wrote, and only the public surface of those types.
- **Bounded contexts:** a bounded context is one business area of the codebase that sits next to other such areas. For example, the codebase may have one folder, module, package or project for each business area. An area is a context when it does either of these:
  - it owns its own domain model, which means it declares at least one entity or aggregate of its own;
  - it takes in another context's messages, for example by handling integration events that another context declares.

  If the repository declares its bounded contexts, that declaration decides. All the layers of one context belong to that context (for example its domain, application and infrastructure projects).
- **Not a context:**
  - A shared kernel: code that exists so that every context can depend on it (for example a shared-kernel, common, building-blocks or abstractions module, or a ports layer).
  - A shared library that owns no model (for example integration contracts or messaging plumbing).
  - A product-wide layer that sits above all the contexts.
- **Not leaks:**
  - A domain type that a shared kernel owns.
  - A type that its owning context publishes as its contract for other contexts (for example the types in a context's contracts module).

## Unit and denominator
- **Domain type:** a type that belongs to a context's model. It is any of the following:
  - a strongly-typed identifier (for example `OrderId` wrapping a GUID, or a branded id type);
  - a value object;
  - an enumeration, including a language's closed set of literal values (for example a TypeScript union of string literals, but not a success-or-error result union);
  - an entity;
  - an aggregate.
- **Public surface of a type:** for a public type, this is:
  - its public properties, fields and events;
  - the return types and parameter types of its public methods and constructors;
  - the interfaces it implements.

  A type named inside generic arguments, arrays, tuples or nullable wrappers counts as named.
- **Unit:** a leak is a place in the public surface of a public type in one context that names a domain type owned by a different context.
  - Each place counts separately.
  - One place that names two different domain types from another context counts as two leaks.
  - The same domain type named at the same place counts once.
  - One declaration that the language expands into several members counts once. For example, a record's positional parameter becomes a constructor parameter, a property and a deconstruction, but it is one leak.
- **Denominator:** the repository's production lines as [production-code.md](../production-code.md) defines them, in thousands, plus the smoothing term under Pending re-definition.

## Thresholds
- A leak needs two different contexts. A type used inside its own context never counts.
- At least 2 bounded contexts must exist for anything to count.

## Score
Let L be the number of leaks and P the number of production lines:

`density = L / ((P + 2000) / 1000)`

`score = clamp(10 − 2.0 × density, 0, 10)`

Each leak per thousand lines costs 2 points, so the score reaches 0 at 5 leaks per thousand lines. Example: 10,000 production lines with 6 leaks give a density of 0.5 and a score of 9.0.

## Not measured when
- **The codebase has fewer than 2 bounded contexts.** For example, it may be organised in layers, be a single project, or be only a shared core. The result depends on size, and neither case is scored:
  - A codebase of 20,000 or more production lines with no bounded contexts is reported as not measured, with a note that its contexts are unknown.
  - A codebase below 20,000 lines, a single production project, or a shared core on its own is reported as not applicable.
- **No type in the production code can be placed in any context.**

## What the result is not
- **Not a check of integration contracts.** A contract (for example a command, event, message or data-transfer type) may carry a strongly-typed id instead of the underlying primitive. This may be reported as advice, but it is not scored.
- **Not a judgement of where the boundaries are drawn.** It measures coupling across the context boundaries as they are now, not whether those boundaries are drawn well.
- **Not a count of every reference.** It does not count references in method bodies, private members or internal members. A context that uses another context's types only inside its own implementation scores 10.
- **Not a verdict on shared kernels.** It does not say whether shared-kernel types are good or bad.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them. A later decision under decision 0013 will replace each one with a threshold on the property.

- **Smoothing term:** 2,000 lines are added to the production lines before dividing, so small codebases are not scored on raw counts.
- **Size for reporting missing contexts:** 20,000 production lines.
