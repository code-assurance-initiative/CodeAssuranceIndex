# X27: Collection changed while being enumerated

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property
Whether a C# `foreach` leaves the collection it is walking alone: a body that adds to or removes from the very collection the loop is enumerating invalidates the enumerator the loop holds, so the next `MoveNext` throws `InvalidOperationException` and the remaining items are never seen. Collections whose enumerator survives such a change (for example concurrent or immutable collections, and arrays), and a change the loop exits straight after, are not this.

## Applies to
C#.

## Population
The population is production code as [production-code.md](../production-code.md) defines it, limited to its C# files. This dimension leaves nothing else out.

## Unit and denominator
**A loop** is either of these:
- a `foreach` statement in either form, including the deconstructing form `foreach (var (k, v) in d)`;
- a call to `List<T>.ForEach(callback)`. The callback is the loop body, because the list checks itself for changes after every callback, the same way `MoveNext` does.

The denominator is the number of loops in the population, whatever they walk. A loop over an array, a snapshot or a concurrent collection still counts in the denominator.

**The walked collection** is the collection instance whose enumerator the loop holds:
- A loop over a live `Keys` or `Values` view walks the dictionary under the view.
- A loop over a lazy query that pulls its source one element per step walks that source. Examples are `c.Where(...)`, `c.Select(...)`, and `Skip` or `Take` over such a query.
- A loop over a snapshot (for example `c.ToList()`, `c.ToArray()`, `new List<T>(c)`) walks the snapshot, not `c`.
- The collection is the same instance whatever expression names it. For example, a member that returns a stored field as it is hands back that field. A change made through that field is a change to the walked collection.

**The unit counted** is a change. A change is one place, in the loop body or in code the body calls, that changes the walked collection while the enumerator is live, in a way that invalidates that enumerator. Such a change adds, removes or reorders items, or is a write the collection itself treats as a new version (for example replacing a `List<T>` element). Each such place counts once, even when it writes several targets. One loop can hold more than one change.

## Thresholds
A change counts only when all of these hold:

- **The collection is fragile.** It is one of `List<T>`, `Dictionary<TKey,TValue>`, `HashSet<T>`, `SortedDictionary<TKey,TValue>`, `SortedList<TKey,TValue>`, `SortedSet<T>`, `Queue<T>`, `Stack<T>`, `LinkedList<T>`, `Collection<T>`, `ObservableCollection<T>`, `ArrayList` or `Hashtable`, or a type derived from one. These are never fragile:
  - concurrent collections, whose enumerators tolerate change;
  - immutable collections, whose "mutators" return a new instance;
  - arrays, which have no structural change.
- **The call is the collection's own change.** The call must be a member of the collection itself, inherited members included, that changes it in a way its enumerator detects: it adds, removes or reorders items. Examples are `Add`, `Insert`, `Remove`, `RemoveAt`, `Clear`, `Enqueue`, `Pop`, `AddFirst`, `Sort`, `Reverse` and `UnionWith`. A method of another type that only shares such a name (for example an extension method called `Remove`) is not a change.
- **An indexer write or `TryAdd` counts when the collection treats it as a new version.** A write through the indexer is any of these: plain assignment, compound assignment (for example `list[i] += x`), `++` and `--`, or an indexer target of a tuple deconstruction. These writes count:
  - every element write on `List<T>`, `ArrayList`, `Collection<T>` and `ObservableCollection<T>`, even when the new value equals the old one;
  - every write on `SortedDictionary`, `SortedList` and `Hashtable`, including overwriting a key that is already there;
  - on `Dictionary`, an indexer write or `TryAdd` that adds a key, on every runtime. Whether an indexer write that replaces the value of a key already there counts depends on the runtime (below).
- **The target runtime invalidates.** The runtime that decides is the oldest one the file is built for.
  - On .NET Core 3.0 and later, these `Dictionary` changes do not count: `Remove`, `Clear`, and an indexer write that replaces the value of a key already there. On older runtimes every `Dictionary` indexer write counts.
  - On .NET 5 and later, removing from a `HashSet` does not count either: `Remove`, `Clear`, `ExceptWith`, `IntersectWith`, `RemoveWhere`, and a `SymmetricExceptWith` that only removes. A `SymmetricExceptWith` that adds an item counts on every runtime.
  - A file that no build project covers, so no target runtime is declared for it, is treated as running on .NET 5 or later. Only changes that invalidate on every runtime count there.
  - A file in a build project whose declared target is not one of the runtimes above is treated as running on the oldest runtimes. Every change listed above counts there.
- **Another step follows.** A change after which the loop always exits does not count, for example `if (...) { c.Remove(x); break; }`.
  - In a `foreach`, the exits are `break`, `return`, `throw` and a `goto` out of the loop.
  - In a `List<T>.ForEach` callback, only `throw` leaves the loop. A `return` ends one callback, and the list goes on to the next item.
- **It runs under this loop's enumerator.** These do not count for this loop:
  - code inside a lambda or local function written in the body, because it does not run where it is written. The callback of `List<T>.ForEach` is the exception, because it is the body itself;
  - a change inside a nested loop over the same collection. It belongs to the inner loop, whose enumerator fails first.

## Score
Let `v` be the number of changes, `n` the number of loops, and `N = max(n, v + 1)`.

- If `v = 0`, the score is 10.
- Otherwise:
  - density `d = clamp(v / N, 0, 1)`
  - isolation `i = max(0, 1 − d / 0.10)`
  - headroom `h = clamp(log10(N) / log10(200), 0, 1)`
  - ceiling `c = 6 + 2 · i · h`
  - score `= clamp(1 + (1 − d) · (c − 1), 1, c)`, rounded to two decimals.

Any change caps the score at 8. A single change among 200 or more loops scores close to 8. At a density of 10 % or more, the score is at most 6, and it falls toward 1 as density rises.

## Not measured when
- The population holds no C# file.
- The population holds no loop and no change. That case is not measured; it does not score 10.

## What the result is not
- It is not a check of loops in languages other than C#, of `for` loops by index, or of `while` loops.
- It is not proof that the code throws on every run. A counted change throws only on the runs that actually reach it, for example when the condition guarding it is true for some item. Once a run reaches it, the next step throws even if no items remain.
- A 10 does not mean the code never changes a collection from another thread.
- No published score includes it today because the engine reports it advisory.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Call depth:** a change made in code the loop body calls counts only when it is at most 4 calls deep from the body.
- **Naming depth:** the walked collection is followed through at most 4 steps of members that return a stored field, local variables, lazy queries or read-only wrappers.
