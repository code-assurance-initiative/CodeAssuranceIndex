# C5: Data-Subject Rights

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether GDPR data-subject requests are supported in code — erasure, export/portability, consent.

## Applies to
Any programming language. To decide whether personal data is kept, this dimension also reads database schema and migration files, for example SQL CREATE TABLE or ALTER TABLE statements. It does not read markup (HTML) or styles (CSS).

## Population
The population is production code as [production-code.md](../production-code.md) defines it, with one addition. To decide whether personal data is kept, this dimension also reads database schema and migration files, for example SQL CREATE TABLE or ALTER TABLE statements, even where they are not production code. These files only decide whether personal data is kept. They do not make a right present.

The dimension covers personal data that the application keeps:

- **Personal data** is a stored field that identifies or describes a person. Examples are an email address, a first or last name, a date of birth, a phone number or a stored credential.
- **Kept** means the field is declared on a persisted record type. Examples are a database entity, a table or migration column, a document schema or a persisted model class.
- Personal data held only for a moment is not kept. An example is the input state of a sign-up form.

## Unit and denominator
The unit is a **right**. Three rights are read over the whole repository. Each one is either present or absent.

- **Erasure:** code that deletes or anonymises the personal data of one data subject. The subject must be identified as a person, for example by their user, account or customer id. Some code does not count:
  - A delete whose object is not a person, for example deleting a save slot or a store mapping.
  - A setting or flag about erasure, for example a permission to delete an account or a switch that shows a delete button.
- **Export / portability:** code that hands one data subject their personal data in a form they can take away. The subject must be identified as a person, for example by their user, account or customer id. An export whose object is not a person does not count, for example a report or a CSV dump of a table.
- **Consent:** either of these:
  - code that records a data subject's GDPR consent next to the personal data it authorises;
  - a setting that is off by default and must be turned on before the application sends data out (an opt-in gate).

Only code that implements a right counts. Comments, prose and names alone do not.

There is no denominator. The dimension reads which of the three rights exist in the repository's code.

## Thresholds
- A right is present once one path in production code meets its definition above. More paths for the same right add nothing.
- Personal data is kept once at least one personal-data field is declared on a persisted record type. The field can be in production code or in a database schema or migration file.

## Score
The score is the sum of the points for the rights that are present:

| Right present | Points |
|---|---|
| Erasure | 4 |
| Export / portability | 4 |
| Consent | 2 |

The possible scores are 2, 4, 6, 8 and 10. The score is 10 only when all three rights are present. When no right is present the score is not 0. Instead the dimension is not measured (see below).

Every repository falls into exactly one of three cases:

- not applicable (no personal data is kept);
- not evidenced (personal data is kept and no right is present);
- scored (personal data is kept and at least one right is present).

## Not measured when
- **No personal data is kept:** no personal-data field is declared on any persisted record type, in code or in schema and migration files. The dimension does not apply.
- **No right is evidenced:** personal data is kept, but none of the three rights is present in code. The result is "not evidenced" and has no score. A data subject's request may be handled by hand, or by a platform the code does not show. So a right missing from the code does not prove the request cannot be served.

## What the result is not
- It is not proof of GDPR compliance. It reads what the code supports, not the process, the policies or the legal basis.
- It does not check that a right is complete:
  - An erasure that leaves copies behind still earns the erasure points. The copies may be in browser storage on the subject's device or in a second data store.
  - An export that leaves out the copy on the device still earns the export points.
  - These gaps can be reported as findings, but they do not change the score.
- It does not count the other GDPR rights, for example rectification, restriction or objection.
