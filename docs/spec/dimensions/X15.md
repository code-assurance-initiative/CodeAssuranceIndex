# X15: Unvalidated length from an untrusted reader

**Lens:** securityCompliance · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property

Whether a length read out of the stream being parsed is bounded before it is allocated or read — an unchecked count taken from the input lets the input choose the allocation.

## Applies to

Any language whose code reads integers out of a byte stream or a buffer that it is parsing.

## Population

Production code as [production-code.md](../production-code.md) defines it. This dimension adds no exclusions of its own.

Within that code, the population is every **length site**. A length site is a value that meets all three of these conditions:

- It is an integer read out of the input the code is parsing, for example a file, a network message or a buffer filled from one. Examples are a fixed-width integer or a variable-length encoded integer read from a binary reader or a byte buffer.
- It is read from a field of 16 bits or wider, or from a variable-length encoded integer (see Thresholds).
- It is then **spent**. Spending means using it as the number of bytes to read from the input in one bulk read, or as the size of an array or buffer to allocate. The length may reach the spend through a cast or conversion, a local or a field, arithmetic, or a call to another function. It is still the same length.

A length that is read but never spent is not a site. A length that only steps a loop, with no allocation or bulk read sized by it, is not a site either.

## Unit and denominator

- **Unit:** an **unbounded length**. This is a length site whose value is not bounded from above before it is spent.
- **Bounded from above** means the code limits the value somewhere on its way from the read to the spend, before the spend. The limit may sit in the function that reads the length, the function that spends it, or any function it passes through. The code can bound the value in two ways:
  - It compares the value with a maximum the format allows, or with the bytes that remain in the input.
  - It passes the value through a call that caps it, for example a minimum, a clamp, a checked narrowing conversion, or a guard that fails when the value is greater than a limit (or when the remaining input is less than it).
- These do **not** bound the value:
  - a test against zero or a negative number (an emptiness or sign test);
  - a lower-bound guard (for example "fail if negative");
  - the condition of the loop that counts up to the length to consume it;
  - a check that comes only after the spend.
- Each length site counts once, however many times it is spent.
- **Denominator:** the number of length sites, with the floor stated under Score.

## Thresholds

- **Width:** a length read from a 16-bit, 32-bit or 64-bit field of the input, or a variable-length encoded one, is a site. A length read from a single byte is not.
- **Zero and below:** a comparison with zero or a negative constant is never a bound.

## Score

Let `v` be the number of unbounded lengths and `s` the number of length sites.

- If `v = 0`, the score is **10**.
- Otherwise let `n = max(s, v + 1)` and `d = v / n`, clamped to 0..1.
- `isolation = max(0, 1 - d / 0.10)`
- `headroom = clamp(log10(n) / log10(200), 0, 1)`
- `ceiling = 6 + 2 × isolation × headroom`
- `score = 1 + (1 - d) × (ceiling - 1)`, clamped to the range 1..ceiling and rounded to 2 decimals.

A repository with any unbounded length scores at most 8. When every site is unbounded, `n` is `v + 1`, so the score stays above 1.

## Not measured when

- The repository's production code holds no length site (no sites and no unbounded lengths). That is "nothing examined", not a 10.
- Production code in a language this dimension applies to could not be read. A score from the rest would present part of the code as the whole.

## What the result is not

- No published score includes it today, because the engine reports it advisory.
- It is not proof that an input can exhaust memory. Some buffers that look like untrusted input are filled by the operating system or by the program itself.
- It is not a check that the bound is correct. It only checks that an upper bound exists before the spend.
- It does not cover allocation that grows step by step as input arrives. It covers only an allocation or bulk read sized by one length.

## Pending re-definition

These are parameters of the existing reading's model. Today's score depends on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Ceiling with any unbounded length:** 6, raised by up to 2 (to 8) when unbounded lengths are isolated.
- **Isolation cut-off:** a share of unbounded lengths of 10 %. At and above it, the ceiling stays at 6.
- **Headroom saturation:** 200 sites, the denominator at which the full raise of the ceiling is available.
- **Floor:** a score of 1.
- **Denominator floor:** `v + 1`, which keeps a repository whose every site is unbounded off the floor.
