# P1: CI/CD gates

**Lens:** productionReadiness · **Scored:** yes

## Property

Whether an automated pipeline builds and tests every change.

## Applies to

Any language. P1 reads the continuous-integration pipeline definitions a repository holds. For example: GitHub, Forgejo or Gitea workflow files, GitLab, Azure Pipelines, Bitbucket, Travis, AppVeyor, Drone, Cirrus, Woodpecker, CircleCI, Buildkite and TeamCity pipelines, and a Jenkinsfile.

P1 also reads what those pipelines run:

- the templates the pipelines include;
- the recipes of the make targets they run;
- the scripts they name;
- the task files of the build tools they start;
- the per-project task configuration of a workspace task runner they start;
- the repository's own commands they run.

Unit and denominator says which of these count toward which credit. Pending re-definition says how far each kind is followed today.

## Population

- **In scope:** the pipeline definitions committed in the repository, in the place each CI service reads them from, and the files listed under Applies to.
- **Not production code:** pipeline files and build scripts are not production code as [production-code.md](../production-code.md) defines it. P1 still reads them, because they are its evidence. Production code is not P1's population.
- **Out of scope:** CI service settings the repository does not hold, and the live state of any CI service. P1 reads only the repository. Pipeline files inside vendored code or build output are not the repository's own, so P1does not read them.
- **Lines that do not run** earn no credit of any kind (gate, tests or build):
  - a line that is only a comment;
  - a step or trigger the pipeline switches off (for example `if: false`).
- **Tests a flag skips:** a step whose tests a flag skips earns no tests credit, full or partial. It can still earn the build credit when the pipeline text itself shows the build. For example, `mvn package -DskipTests` builds the product but runs no tests.

## Unit and denominator

The whole repository gets one reading, made of three credits. There is no denominator.

Each credit is earned once for the whole repository and is judged over all of its pipeline definitions together. The gate, the tests and the build may come from different pipelines. The tests and build credits count whether or not their pipeline is a gate. For example, a lint-only pipeline that runs on push, plus a pipeline that builds and tests but runs only on a schedule, scores 10.

Each credit looks in a different set of places. The table below is the only place on this page that says where each credit is seen. Pending re-definition gives the limits on each place.

| Credit | Seen in |
|---|---|
| Gate | the pipeline files |
| Tests run | the pipeline text, the scripts and build-tool task files it runs, workspace task configuration, and repository commands |
| Build runs | the pipeline text and workspace task configuration only |

Here "the pipeline text" means the pipeline files, the templates they include and the make recipes they run.

- **Gate:** at least one pipeline is started by a change, as "When a pipeline gates" defines it, and is written for a CI service that still operates.
  - **When a pipeline gates:** a pipeline that states its triggers is a gate when at least one of its triggers is not in this list:
    - started by hand;
    - on a schedule;
    - on a published release;
    - on a repository housekeeping event: issues, issue or discussion comments, discussions, labels, milestones, project boards, forks, stars or watches, wiki edits, or the repository being made public.

    Any other trigger makes the pipeline a gate. Examples are a push, a pull request, a branch or tag being created, a call from another workflow, or an external dispatch. A pipeline that does not state its triggers, and that its CI service runs on every push, is a gate.
  - **Shut-down services:** a pipeline written only for a CI service that has shut down is not a gate. For example, a repository whose only CI is a Travis configuration for travis-ci.org, which closed in 2021, has no gate.
- **Tests run:** a pipeline runs the project's test suite. It can run a test runner itself (for example `pytest`, `go test`, `npm test`, `npx jest`), or it can reach one through anything in the "Tests run" row above.
- **Tests indicated:** no run of the test suite is seen, but the pipeline indicates tests in one of two ways:
  - a pipeline job is handed whole to a workflow in another repository, so its steps cannot be read from this one;
  - the pipeline text refers to tests without running them (for example a `test:` key, or a `tests/` path).

  A test phase the pipeline switches off (for example `test: off`) indicates nothing.
- **Build runs:** a pipeline builds the product, for example by compiling, packaging or bundling it. It can build directly, or through the templates, make recipes or workspace task configuration it runs.

## Thresholds

- **Gate:** at least one pipeline in the repository meets the gate conditions above.
- **Tests run:** at least one run of a test suite is seen in the places the tests credit reads.
- **Tests indicated:** at least one indication as defined above. A delegated job always counts. In a JavaScript or TypeScript repository (defined under Pending re-definition), a reference to tests counts only when the repository declares a test command.
- **Build runs:** at least one build step is seen in the places the build credit reads.

## Score

The score is `gate + tests + build`, kept within 0-10.

| Credit | Value |
|---|---|
| Gate present | 5.0 (otherwise 0) |
| Tests run | 3.0 |
| Tests indicated, no run seen | 1.5 |
| No tests | 0 |
| Build runs | 2.0 (otherwise 0) |

The tests and build credits count even when there is no gate. For example, a repository whose only pipeline builds and tests, but runs only on a schedule or only on a shut-down service, scores 5.0. A repository with no pipeline definition scores 0.

## Not measured when

- **Template or teaching code:** the repository has no gate and is one of these:
  - a scaffolding template;
  - a project that declares itself an educational or proof-of-concept artifact (a kata, sample, demo, tutorial, exercise or prototype).

  Such a repository is scored as usual when it does have a gate.
- **Unreadable checkout:** the repository's files cannot be read.

## What the result is not

- **Not a merge rule:** the score does not show that a failing pipeline blocks a merge, because branch protection lives in the hosting service, not in the repository. It does not check that the pipeline passes either.
- **Not proof that the gating pipeline tests:** the gate, tests and build credits may come from different pipelines. A full score does not mean every change is built and tested before it lands.
- **Not test quality:** a pipeline that runs a trivial suite scores the same as one that runs a thorough suite.
- **Not proof that the pipeline runs:** a pipeline written for a live service may still be switched off in that service.
- **Not a full pipeline review:** lint, security, release or deployment steps add nothing.

## Pending re-definition

These are parameters of the existing reading's model. Today's score depends on them, and a later decision under decision 0013 will replace each with a threshold on the property.

- **Where a build is seen:** today, a build that shows only in a script or a build-tool task file the pipeline runs does not earn the build credit. Take a gating pipeline whose pipeline text holds nothing that builds, where the build and tests sit only inside a script it calls (for example `./ci.sh`). It scores 8.0 today.
- **Pipeline files:** each pipeline definition file is read whole, whatever its size. Pipeline files are read until their combined text reaches 64 Mi characters (67,108,864). The file that crosses that point is still read whole, and files after it are not read.
- **JavaScript or TypeScript repository:** a repository that meets both conditions:
  - its root holds a package manifest (`package.json`) that can be read;
  - its pipeline text names no other language's build or package tool (for example `dotnet`, Gradle, Maven, sbt, Cargo, `go build`, Mix, rebar3, Flutter, Dart, `swift build`, Xcode, Poetry, `pip install`, `python -m`, Composer or `bundle exec`).

  A root manifest larger than 1 MiB (1,048,576 bytes) is not read, so the repository is not one.
- **Declared test command (JavaScript or TypeScript repositories only):** in such a repository, a reference to tests earns 1.5 only when the repository declares a test command. Examples are a package script that runs tests, a `test` target or task in a project or root task file, or a root makefile target named `test`. A placeholder script that runs no tests declares nothing. Other repositories need no declared command.
  - **Packages read:** at most 400 packages are read for a declared test command.
  - **When the root declares workspaces**, only the declared workspace packages are read, minus those the declaration excludes. A pattern that matches folders at any depth is followed at most four folder levels below the point where it starts.
  - **When the root declares no workspaces**, only packages at most two folders below the root are read. Packages that are examples, samples, test fixtures, tests, documentation or templates are left out.
  - **Never read:** packages inside installed dependencies, build output, coverage output, vendored code or hidden folders.
  - **Size limit:** a file larger than 1 MiB (1,048,576 bytes) is not read and declares no test command.
- **Included pipeline templates:** at most 25 files are read, each at most 512 KiB (524,288 bytes), one level deep. A template that includes further templates is not followed.
- **Make targets the pipeline runs:** the recipes of at most 25 targets are read, counting each target's direct prerequisites. They come from the repository's root makefile (at most 512 KiB), one level deep. A `make` call inside a recipe is not followed.
- **Scripts and build-tool task files (full tests credit only):** at most 24 entries are followed, and each file read is at most 256 KiB (262,144 bytes). A larger file is not read. The reach is two steps at most:
  - the scripts and build-tool task files the pipeline text names (one step);
  - the task file of a build tool that such a script starts, for the target the pipeline line names (for example a `build.sh` that starts a Cake or NUKE build). This second step uses the same limits.

  A build project written in code counts as one entry, and at most 24 of its source files are read. Only what runs for the target the pipeline asks for counts.
- **Workspace task configuration:** the per-project task files of a workspace task runner the pipeline starts are read, one step from the pipeline. There is no limit on how many files. They are read until their combined text reaches 64 Mi characters (67,108,864). The file that crosses that point is still read whole, and files after it are not read. These files count toward the build credit and the full tests credit.
