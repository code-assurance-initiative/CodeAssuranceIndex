# X31: Test-only surface in a production module

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property

Whether an Erlang production module publishes functions that exist only for its tests: Erlang has no visibility below `-export`, so a test helper exported unconditionally becomes part of the module's contract for every caller in the system, instead of being exported inside an `-ifdef(TEST)` section that keeps it out of the shipped module.

## Applies to

Erlang.

## Population

- Erlang modules that are production code as [production-code.md](../production-code.md) defines it.
- This dimension also leaves out examples, samples and demonstrations. They ship in no release, so their exports widen no production contract.
- The module is read as it ships, which means compiled with no test or property-test flag defined. An export inside a section that only compiles when such a flag is defined (for example `-ifdef(TEST).` or `-ifdef(EQC).` around an `-export`) is not part of the shipped module and is never counted. That idiom is the remedy this dimension recommends.

## Unit and denominator

**Unit:** an exported function (name and arity) of a production module that is exported unconditionally and is test-only. It is test-only when both of these hold:

1. **It is marked for tests**, in either of two ways:
   - **Declared:** the comment attached to its `-export` attribute says that the exports are for testing. The attached comment is the comment lines directly above the attribute, with no blank line or code between them and the attribute, plus any comment on the attribute's own line. The declaration covers every function in that one attribute. It does not cover other `-export` attributes.
   - **Named:** the function's name carries a test marker at a name-segment boundary (see Thresholds).
2. **No production code reaches it.** Production code reaches a function, at any arity of that name, in any of these ways:
   - production code in another module calls it or imports it;
   - any production code, the module itself included, refers to it as a function value (for example `fun test/2` in its own routing or command table);
   - any production code, the module itself included, names the module and the function together so it can be called later (for example as a module, function and argument list handed to a timer, or in a registration tuple, record or map);
   - production code calls that function name through a variable module;
   - an in-repo behaviour that the module implements declares the function as a callback.

   Only a direct call from a module to its own export does not count as reach. A test function inside a production module (one whose name carries a test marker) is test code, and what it refers to is not production reach.

All arities of one exported name form one contract. If production code reaches one arity, no arity of that name is counted.

**Denominator:** the repository's production Erlang modules. The result is the number of test-only exports, plus the number of modules, out of all production modules, that hold at least one.

## Thresholds

- **Declaring words:** a comment declares that its exports are for testing when it contains, as a whole word and in any letter case, `test`, `tests`, `testing`, `testcase` or `testcases`, or the name of a test-suite module (a name ending in `_tests` or `_SUITE`). A word is a run of letters, digits and underscores, so `eunit_listener` and `common_test` are single words and do not declare anything. `tested` does not count, and neither does the name of a test framework.
- **Name markers:** the name begins with `test_`, ends with `_test` or `_test_`, or is exactly `test` or `tests`. A marker inside an ordinary word does not count (for example `latest`, `attest` or `contest_winner`).
- **Callers must be visible for a name-only mark:** a function that is named but not declared is counted only if the module's callers are visible. They are not visible when the module exports 20 or more distinct names and production code reaches at most 1 in 20 (5 %) of them. A declared function is counted whether or not its module's callers are visible.

## Score

No score curve is defined: the one existing engine reports findings only, with no 0-10 reading.

## Not measured when

The repository has no production Erlang modules. In that case there is no result, not a clean 0.

## What the result is not

- It does not list every export that only tests use. A test helper whose author neither declared it for tests nor named it for them is not counted.
- It does not prove that a test calls the function. It only says that the function is marked for tests and that no production code reaches it.
- It does not judge any export that production code reaches. If a "for tests" comment sits over such an export, the comment is out of date, but the export is not test-only surface.
- Calls from the test tree do not count as reach: a test calling its helper is exactly what this dimension reports.

## Pending re-definition

These are parameters of the existing reading's model. The current findings depend on them, and a later decision under decision 0013 will replace each one with a threshold on the property.

- **Status:** the catalog does not declare it advisory, yet no score curve exists; a decision either declares it advisory or sets its curve.
- **Caller visibility:** a module with 20 or more distinct exported names, of which production code reaches at most 1 in 20, is treated as one whose callers are not visible. In such a module, name-only marks are not counted.
- **Declaring vocabulary:** the words `test`, `tests`, `testing`, `testcase` and `testcases`, plus test-suite module names ending in `_tests` or `_SUITE`.
- **Name markers:** the prefix `test_`, the suffixes `_test` and `_test_`, and the whole names `test` and `tests`.
