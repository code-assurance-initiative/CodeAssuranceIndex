# D42: Runtime Threat Enforcement

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether the Kubernetes deployment commits runtime threat controls: a threat-detection engine that watches running workloads and alerts on suspicious behaviour, and/or an admission-control policy that rejects non-compliant workloads when they are deployed (for example Falco or Tetragon for detection; Kyverno, OPA Gatekeeper or Pod Security admission for admission control). Presence of committed policy, not a runtime guarantee.

## Applies to
Kubernetes deployment manifests written in YAML (`.yaml`, `.yml`). This includes plain manifests, chart templates (for example Helm templates) and overlay patches (for example kustomize patches). The dimension does not depend on the language the product is written in.

## Population
The repository's committed Kubernetes manifests, read together as one set for the whole repository. The dimension does not score per service or per file.

YAML is not production code as [production-code.md](../production-code.md) defines it, so this dimension reads its own file kind. It leaves out manifests in the same categories that [production-code.md](../production-code.md) leaves out:

- tests and test support, including expected-output files that tests compare against
- evaluation inputs
- vendored code, for example a third-party chart copied in
- build output and tool state, for example dependency caches

This dimension also leaves out manifests that [production-code.md](../production-code.md) would keep:

- **Examples, samples, demonstrations and benchmarks:** a sample workload is not one the project runs.
- **Documentation:** for example a manifest inside a documentation folder.

Comment lines in a manifest are not content: they name nothing and set nothing.

## Unit and denominator
The unit is a **control**. There are two controls, and the denominator is 2.

1. **Runtime threat detection:** the repository commits a threat-detection engine for running workloads. This can be the engine's deployment or a detection policy for it, for example a Falco installation or rules, or a Tetragon tracing policy.
2. **Admission control that refuses:** the repository commits at least one admission mechanism configured in a mode that rejects a non-compliant workload. Any one of these counts:
   - **Pod Security admission:** a namespace's `enforce` level is set to anything other than `privileged`. A level filled in by a chart template counts as set and is not read as `privileged`.
   - **Pod Security admission, cluster-wide:** the API server's Pod Security admission configuration sets a default `enforce` level other than `privileged`.
   - **Kyverno:** a `Policy` or `ClusterPolicy` with a failure action of `Enforce`, or a policy that has no validate rule (for example a mutate or generate policy).
   - **Gatekeeper:** a constraint whose enforcement action is `deny`, or that declares no action (`deny` is the default).
   - **Validating admission policy:** a binding whose validation actions include `Deny`, or that declares no actions.
   - **Engine only:** for Kyverno, Gatekeeper or validating admission policy, the repository commits the engine or its templates but none of the configuration that sets a mode (no policies, no constraints, no bindings). The mode is then not in the repository, so the mechanism counts.

Within each family, once the repository commits the configuration that sets a mode, the family counts only if at least one of those settings refuses. If every committed setting only admits, the family does not count. Admitting settings include Pod Security labels set to `warn` or `audit` only, `enforce: privileged`, Kyverno `Audit`, Gatekeeper `dryrun` or `warn`, and a binding without `Deny`.

A control is present or absent. Several detection engines or several refusing policies still count as one control.

## Thresholds
- A control counts when one committed instance exists, as defined under Unit.
- Pod Security levels that refuse: any set level except `privileged` (for example `baseline` or `restricted`).
- An unset Kyverno failure action means `Audit`, which does not refuse.
- An unset Gatekeeper enforcement action means `deny`, which refuses.

## Score
`score = 6.0 + 4.0 × present / 2`, kept between 6.0 and 10. Here `present` is the number of controls present (0, 1 or 2).

| Controls present | Score |
|---|---|
| 0 | 6.0 |
| 1 | 8.0 |
| 2 | 10.0 |

The two controls weigh the same. The curve only rewards: having no runtime enforcement gives the neutral floor of 6.0, never a lower score.

## Not measured when
The dimension is not applicable, and gives no score, when either of these is true:

- **No Kubernetes workloads:** the population has no resource that runs containers from a pod template. Workloads include, for example, a Deployment, Pod, DaemonSet, StatefulSet, ReplicaSet, Job, CronJob or Rollout, and any other kind that carries a pod template with its containers.
- **Workloads but no governance:** the repository ships workloads but no cluster or admission governance. Governance means any of these:
  - a custom resource definition
  - an admission webhook configuration
  - a Pod Security policy
  - a Kyverno `ClusterPolicy`
  - a Gatekeeper constraint template
  - a validating or mutating admission policy or binding
  - any Kyverno, Gatekeeper, Falco or Tetragon configuration
  - a Pod Security admission label in any mode
  - an API server Pod Security admission configuration

  An application repository or chart that only ships workloads leaves these controls to whoever operates the cluster.

## What the result is not
- **Not proof the controls run:** it is not proof that a detection engine is running or that admission control is blocking anything in a live cluster. It reads committed configuration only.
- **Blind to controls installed elsewhere:** controls installed cluster-wide outside the repository (for example as a platform add-on) earn no credit.
- **Not a measure of policy strength:** one refusing rule earns the same credit as a complete policy set.
- **Not adjusted for who owns the cluster:** a repository that governs only its own namespace can reach 8.0 at most unless it also commits threat detection.
- **Does not penalise missing baseline settings:** baseline container misconfigurations, such as running as root or privileged containers, are not penalised here.
