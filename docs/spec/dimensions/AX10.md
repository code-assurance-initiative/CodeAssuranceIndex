# AX10: Code composition

**Lens:** architecture · **Scored:** yes

## Property
How the code divides, by size, among five roles, each piece of code having one: domain (the code that models the business and holds its rules), application (the code that carries out use cases by directing the domain), infrastructure (the code that connects to the outside world, for example databases, networks, files and frameworks), test (the code that tests other code) and generated (code produced by a tool rather than written by hand). In domain-driven design terms, a small domain share beside a large infrastructure share suggests an anemic domain model, one whose types hold data while the business rules live elsewhere. A split by size, not proof of where the behaviour lives.

## Applies to
Code in any general-purpose programming language on the production-lines list in
[production-code.md](../production-code.md) (list version 1). This includes single-file components (for example Vue or
Svelte), counted whole.

Web markup (HTML) and styles (CSS) are not read by this dimension. Neither are the other files that [production-code.md](../production-code.md)
does not count as code, for example SQL, shell scripts and data files.

## Population
The files read are of three kinds:

- **Production code** as [production-code.md](../production-code.md) defines it, in the languages above. Only these files make up the score.
- **Tests and test support**, as [production-code.md](../production-code.md) describes them. They count only in the published test share.
- **Generated code**, as [production-code.md](../production-code.md) describes it. It counts only in the published generated share.

Everything else that [production-code.md](../production-code.md) excludes is not read. For example, vendored code, build output, data files,
build scripts and tool configuration files are left out. The authors' own examples, samples and tools are production
code here, as they are everywhere else.

## Unit and denominator
**Unit:** a line of a file that is not blank. Comment lines count. This differs from production lines in
[production-code.md](../production-code.md), which leave out lines that hold only a comment.

**Role:** each file has exactly one role, the main thing the file is for. All of a file's lines count under that role:

- **Domain:** the file models the business and holds its rules, for example entities, value objects, domain services
  and domain events.
- **Infrastructure:** the file connects to the outside world, for example data access, network clients, file access,
  messaging and framework wiring.
- **Application:** any production file that is neither domain nor infrastructure. This includes use-case code and
  any production file whose role is unclear. So the application share means "application or unclassified".
- **Test:** tests and test support.
- **Generated:** generated code.

**Denominator of the score:** production lines in this sense, meaning domain + application + infrastructure lines.
Test and generated lines are not in it.

**Published shares:** each of the five roles as a percentage of all lines read, rounded to whole percent. These shares
are shown but do not enter the score.

## Thresholds
- **Score floor:** 4.0 (see Score and Pending re-definition).

There is no other threshold.

## Score
Let D, A and I be the domain, application and infrastructure lines, and P = D + A + I.

```
share = (D + A) / P                 business-logic share of production lines
score = max(10 × share, 4.0)        rounded to 2 decimals
```

The share can also be written as 1 minus the infrastructure share of production lines. Some examples:

| Infrastructure share of P | Score |
|---|---|
| 0 % | 10.00 |
| 30 % | 7.00 |
| 60 % or more | 4.00 |

## Not measured when
- No line is read at all, meaning the repository has no code in the languages above.
- Every line read is test or generated code, so P = 0. A share over no production lines is undefined. It is never
  published as 0.

## What the result is not
- It is not a judgement of design quality. An infrastructure-heavy product, for example a gateway, a data pipeline or
  a driver, is legitimately low.
- It is not a measure of business value or behaviour. It splits lines, not logic or importance.
- The application share is not a measured application layer. It also holds every production file whose role is
  unclear.
- It is not a located finding. It names no file as a defect.

## Pending re-definition
These are parameters of the existing reading's model. Today's score depends on them, and a later decision under
decision 0013 will replace each with a threshold on the property.

- **Score floor of 4.0:** no repository scores below 4.0, however small its business-logic share. The floor is the
  existing lens model's critical gate. It is there so that this signal alone does not gate the architecture lens.
- **One role per file:** a whole file's lines count under one role, even when parts of the file serve different roles.
