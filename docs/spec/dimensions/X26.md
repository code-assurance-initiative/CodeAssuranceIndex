# X26: Unsynchronised callback handoff

**Lens:** codeHealth · **Scored:** yes in the standard (the catalog does not declare it advisory); the one existing engine reports it advisory, so no published score includes it

## Property

Whether a value handed from a callback (for example an event handler) to the code waiting on it is passed through a structure made for concurrent use, under a lock, or otherwise without the callback and the outside code touching the same collection at overlapping times. A collection not made for concurrent use (for example a plain queue, list or dictionary) that the callback changes and that is also accessed outside the callback while the callback can still run is used by both at the same time. A semaphore, completion object or other wait handle beside it orders what the callback wrote before raising it, but does not protect an outside access that a run of the callback can overlap, including one made before the code waits for the run in progress; an outside access that no run of the callback can overlap (for example after the waiting code has observed the callback's final signal, when the callback no longer touches the collection after signalling) is not this.

## Applies to

The dimension applies to any language in which a callback can touch a collection at the same time as other code that reaches that collection. For example: C#, Visual Basic .NET, Java, Kotlin, Scala, Go, Swift, Python, Ruby, Rust, and TypeScript and JavaScript (only through memory shared with a worker).

It does not apply to a language or file kind in which no collection can be touched by two flows at overlapping times. For example: PHP, Elixir and Erlang, Dart, and HTML and CSS.

The languages differ in these ways:

- **Python and Ruby (MRI).** Each single operation on a built-in collection (one append, one item write, one length read) is documented as whole under concurrency. So the only outside access that counts is one that walks the collection (iterates it) while the callback can change it.
- **Go.** A goroutine is a callback.
- **Rust.** Safe code cannot share a collection this way. Only code that sets aside the language's sharing rules (`unsafe`) can.
- **TypeScript and JavaScript.** Code on one event loop runs on one thread. A callback can run between two of a function's `await` points but never during one access, so a collection used only on one event loop is never touched at overlapping times. The only collection two flows can touch at overlapping times is memory shared with a worker (for example a typed array over a `SharedArrayBuffer`). A plain write to that memory, rather than an atomic operation, is not made for concurrent use.
- **Dart.** Isolates share no collection, and within one isolate code runs on one event loop. No Dart collection can be touched at overlapping times.
- **All other languages.** Any outside access counts, read or write.

## Population

Production code as [production-code.md](../production-code.md) defines it. This dimension adds no exclusions of its own.

## Unit and denominator

- **A callback:** code that one function hands over to run on another flow of execution. For example: an event handler or listener it registers, a timer callback, a closure it dispatches to a queue or a thread, a goroutine it starts, or code a worker runs. A callback nested inside another callback belongs to the one that encloses it.
- **A handoff (the denominator):** any of these:
  - a callback that raises a synchronisation signal (for example a semaphore release, a completion object's result, an event set, a countdown signal or a latch count-down), where the function that registered the callback waits on that same signal outside every callback;
  - a callback that runs on another thread and writes a collection field of its type. This counts once for each pair of callback and collection field it writes;
  - a callback that writes memory shared with another thread. This counts once for each pair of callback and shared memory it writes. It needs no signal and no wait.

  A handoff counts whatever kind of collection it carries. A handoff through a collection made for concurrent use (for example a concurrent queue, a blocking queue or a channel) is in the denominator and is never a finding.
- **A finding (the numerator):** one pair of a handoff, of any of the three kinds, and a collection where all of these hold:
  - The collection is not made for concurrent use, meaning its own documentation withholds the guarantee for a concurrent writer. For example: .NET's `Queue`, `Stack`, `List`, `Dictionary`, `HashSet`, `SortedDictionary`, `SortedList`, `SortedSet` and `LinkedList`; Java's `ArrayList`, `LinkedList`, `ArrayDeque`, `PriorityQueue`, `HashMap`, `LinkedHashMap`, `TreeMap`, `HashSet`, `LinkedHashSet` and `TreeSet`; and memory shared with another thread when it is written without atomic operations.
  - The callback changes the collection: it adds, removes, inserts, clears, enqueues, dequeues, pushes, pops or writes an element. A read alone inside the callback is not a finding.
  - Another access that a run of the callback can overlap touches the collection, and no single lock is held over both accesses. That other access may be code outside the callback. For a field, that means a member any caller can reach. For memory shared with another thread, it means the other thread's access. It may also be a write by another run of the same callback, or by another callback the same function starts, when no wait orders the two.

An access can overlap a run of the callback whenever the callback can still run on another flow at that point. Any such access counts, including one after a wait when the callback can fire again. Some examples:

- An access after the callback is registered and before the wait on its signal counts.
- An access in a loop that waits on the signal on every pass counts, because each wait orders only the one write it pairs with.
- An access after one wait, when the callback can fire again, counts.
- A callback started on every pass of a loop, with no wait before the next pass, overlaps the callbacks of the passes around it. Two callbacks started with no wait between them overlap each other.

These accesses cannot overlap a run of the callback:

- an access before the callback is registered;
- an access after the waiting code has seen the callback's final signal, when the callback no longer touches the collection after that signal;
- an access after the callback is removed and no run of it is in progress;
- an access in the same loop pass as a one-shot callback registered in that pass, made after that pass has waited on the callback's signal.

## Thresholds

- A pair of handoff and collection is a finding when all the conditions above hold. The unit has no other threshold.
- The score curve has two thresholds of its own: a finding density of 10 % and a denominator of 200 (see Score).

## Score

Let `v` be the number of findings and `N` the number of handoffs.

- If `v = 0`, the score is **10**.
- Otherwise, let `P = max(N, v + 1)` and `d = v / P`. Then:
  - `isolation = max(0, 1 − d / 0.10)`
  - `headroom = min(1, max(0, log10(P) / log10(200)))`
  - `ceiling = 6 + 2 × isolation × headroom`
  - `score = 1 + (1 − d) × (ceiling − 1)`, held between 1 and `ceiling` and rounded to two decimals.

So any finding caps the score at 8. The cap falls to 6 once findings reach 10 % of the denominator, or when the denominator is 1. As the density rises, the score falls towards 1.

## Not measured when

- **No handoff and no finding.** If the code read holds neither, the dimension is not applicable. That is not a 10.
- **No language it applies to.** If every production language in the repository is one where the dimension does not apply (see Applies to), the dimension is not applicable.
- **Its languages are not read.** If the engine reads none of the repository's languages where the dimension applies, the dimension is not measured.

## What the result is not

- It is not proof that the code is free of races. It covers only collections handed from a callback to other code that can touch them at the same time.
- It does not judge the order in which code on one event loop sees a collection. A function that reads, after an `await`, a collection a listener is still filling may read it too early, but the two never touch it at the same time.
- It does not judge the value handed over. For example, a buffer that a library reuses across callbacks, which the callback passes on by reference, is out of scope.
- It does not count reads inside the callback, because collections not made for concurrent use still allow concurrent readers.
- It does not say that a signal beside the collection is wrong. The signal still orders the handoff; it just does not protect the collection.
- No published score includes it today, because the one existing engine reports it advisory.
