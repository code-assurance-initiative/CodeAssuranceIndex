# C3: Audit Trail

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether changes to sensitive data are recorded (who, what, when) for compliance + incident response.

## Applies to
This applies to any language in which an application stores data. The property is the same in every language. Only the way the mechanisms below are written differs. Examples are an ORM lifecycle hook, a database trigger, a change-history library declared on a model, or an event store that every change is appended to.

## Population
- The population is production code as [production-code.md](../production-code.md) defines it, read as one whole repository. The dimension gives one result per repository, not one per file.
- **Sensitive data** is personal data that the repository stores.
  - Data counts as stored when it is declared on a persisted data model, for example an entity, a schema, a table, a migration column, or a model that an ORM maps.
  - Data counts as personal when the model has a field that names a person's personal data or a stored credential. Examples of such fields are email, first name, date of birth, phone number, a government identifier or financial details. Data also counts as personal when the repository keeps user accounts, for example through an identity framework's user model.
  - A postal code on its own names an area, not a person. It does not make data personal.
- An audit mechanism counts only when it is in production code as [production-code.md](../production-code.md) defines it.

## Unit and denominator
The unit is the repository's audit trail. It is read as four separate pieces of evidence. Each piece is either present or absent.

1. **Audit marker:** the code declares that its data is audited. Examples are an "auditable" interface, base class, mixin or concern on an entity, or a call that registers auditing. A switch that only turns the trail on or off (for example `isAuditLogEnabled`) is not a marker.
2. **Write-side hook:** one code path that every change to stored data goes through and that records the change as it is made. Examples:
   - an interceptor on the ORM's save, or an override of it
   - an ORM lifecycle hook or subscriber whose code writes audit or change-history records
   - a database trigger that records changes
   - a change-history library declared on the models
   - an event store that every change is appended to (event sourcing)

   An ordinary lifecycle hook that records nothing, for example one that only publishes a notification, is not a write-side hook.
3. **Audit store:** a dedicated type, table, model or read-model that holds the record of who changed what. Examples are an audit log, audit trail, audit entry or audit projection, or the version table of a change-history library. A raw event stream on its own is not an audit store.
4. **Per-entity coverage:** the entities that need a trail opt into it one by one. Examples are an `[Audited]` or `@Audited` annotation, or a change-history library registered on each model. In an event-sourced system, coverage is present when the appended events record who made each change. The actor can be recorded on the event or on the session that appends it, for example as a user id or a "changed by" field. An event stream that names no actor gives no coverage.

**Audit evidence** is any one of these: a marker, a write-side hook that is not an event store, an audit store, or a per-entity opt-in. An event store, and the coverage that comes from actors on its events, is not audit evidence on its own. It adds points only when some other audit evidence is present.

There is no denominator. The reading is presence anywhere in the repository.

## Thresholds
- A piece of evidence counts when it occurs at least once in production code.
- The dimension is scored only when both of these hold:
  - the repository stores personal data (see Population)
  - at least one piece of audit evidence is present (see Unit and denominator)

## Score
When audit evidence is present, the score starts at 5.0. A marker alone is enough. Each further piece adds points:

| Evidence present | Adds |
|---|---|
| Write-side hook (including an event store) | +2.5 |
| Audit store | +2.5 |
| Per-entity coverage (including an event store whose events record the actor) | +1.5 |

The score is capped at 10.0.

These are the possible scores:

| Evidence | Score |
|---|---|
| Marker only | 5.0 |
| Coverage only | 6.5 |
| Write-side hook only, or audit store only | 7.5 |
| Write-side hook and coverage, or audit store and coverage | 9.0 |
| Write-side hook and audit store, with or without coverage | 10.0 |

An event store fills the write-side hook, and when its events record the actor it also fills coverage. It does this only when other audit evidence opens the gate. For example, a marker plus an event store whose events record the actor scores 9.0.

## Not measured when
- **No personal data:** the repository stores no personal data (see Population). The dimension does not apply.
- **Not evidenced:** the repository stores personal data and has no audit evidence. A repository whose only evidence is an event store is also not evidenced, even when its events record who made each change. The code may lack a trail because the trail lives outside the repository, so absence does not prove there is none. The result is not measured. It is not scored 0.
- **Cannot be established:** the repository writes to a data store but declares no persisted model, so it is unknown whether it stores personal data. For example, it may write through raw queries or a hosted backend.

## What the result is not
- It does not check that the trail works, that it cannot be changed, or that it records who, what and when for each change. It reads only whether the mechanisms are present.
- It does not check that the mechanism covers the entities that hold personal data. Evidence anywhere in the repository counts for all of them.
- It does not credit audit trails kept outside the repository, for example in the database, the infrastructure or a sidecar service.
- It does not judge access logging (who read the data). It covers only changes.
- It is not a legal or compliance certification.
