# P6: Release Hygiene

**Lens:** productionReadiness · **Scored:** yes

## Property
Whether releases are traceable — a maintained changelog and explicit version stamping.

## Applies to
Any language. The dimension reads what a repository says about its releases: changelogs and release notes, build and package manifests, version declarations in source (for example an assembly version attribute or a version file), versioning tool configuration, release pipeline definitions and the repository's release tags. It does not judge the code itself.

## Population
The whole repository counts as one unit. The dimension does not use production code as [production-code.md](../production-code.md) defines it, and it does not read the repository's people.

- **In scope:** the repository's own release records, and the product's own manifests, version declarations, versioning configuration and release pipeline.
- **Out of scope:** the manifest or changelog of a vendored dependency, of a bundled example or sample, or of a dependency unpacked into the tree. These files do not speak for the repository's releases.

## Unit and denominator
The unit is the repository. Four facts are read, and each one is true or false. There is no denominator.

1. **Release traceability.** Any one of these is enough:
   - **Version stamp:** the product declares its version where its build or packaging reads it. For example: a package, build or application manifest; a project's version property; an assembly version attribute; a `VERSION` file; or a top-level source file named as the version file that holds a version.
   - **Computed version:** a versioning tool works out the version from the repository's history at build time. The tool is configured in the project, in a configuration file in the tree, or in the release pipeline (for example GitVersion).
   - **Tag-derived version:** a release pipeline takes the published version from the release tag.
   - **Release tags:** the repository has at least one release tag (see Thresholds).
2. **Changelog present.** Either of these is enough:
   - **A release log in the tree:** a changelog, history, releases or release-notes file. If there is none, a release log kept elsewhere counts when it has at least 3 version sections. For example, this can be a breaking-changes document, a package manifest's release notes, or a release section of the readme.
   - **Generated release notes:** the repository declares, in configuration or as a pipeline step, that it generates notes for each release. For example, a release-notes generator's configuration, or a pipeline step that writes the notes when a release is tagged.
3. **Changelog maintained.** True when the changelog is both present and current:
   - **Present:** generated notes; or a release log with at least 3 versioned entries; or a short pointer file that links to the release or tags page where the notes are published.
   - **Current:** the log in the tree is not behind the releases (see Thresholds). Generated notes and pointer files always count as current.
4. **Broken version hand-off.** A release pipeline step publishes a version from a variable that nothing sets. The publisher then gets an empty version, or the step stops.

A release log's **versioned entries** are the largest of three counts:

- the distinct `x.y.z` versions its text names, not counting link targets or URLs;
- its section headings that name a version or a version series (for example `## [1.2.0]` or `## 8.0.x`);
- its distinct section headings that name a date (a year with a day or month number).

## Thresholds
- **Maintained log:** 3 or more versioned entries.
- **Release tag:** a tag shaped like a version. That is an optional `v`, then `major.minor`, then an optional `.patch`, then an optional pre-release or build suffix. A package-scoped tag also counts (for example `pkg@1.2.3` or `module/v1.2.3`). A date tag also counts: eight digits `YYYYMMDD` with an optional leading `v`, where the year is 1900-2099, the month 01-12 and the day 01-31. Floating tags such as `latest` or `nightly` do not count.
- **Default version values:** a manifest version that a project-creation tool writes by default is not a stamp. These values are `0.0.0`, `0.0.1`, `0.1.0` and `1.0.0`. A placeholder that is not a number is not a stamp either.
- **Unpublished packages:** a package manifest that declares the package is never published does not stamp a release version.
- **Behind the releases:** the newest version heading in the release log is behind when either of these holds:
  - A plain release tag (not package-scoped) names a newer version. Two kinds of tag are left out of this comparison: a pre-release tag while the log keeps an Unreleased section, and a tag above the version the product's manifest stamps.
  - The product's manifest stamps a version more than one release past the newest heading. The next patch, the next minor or the next major counts as one release. Anything further counts as behind.

## Score
```
score = 5 × traceability + 3 × changelogPresent + 2 × changelogMaintained − 2 × brokenVersionHandOff
```
Each term is 1 when its fact is true and 0 when it is false. The result is clamped to 0-10. A score is given only when traceability or a changelog is present, so the possible scores are 1, 3, 5, 6, 8 and 10.

## Not measured when
The repository has no changelog in any of the forms above, no version stamp, no computed or tag-derived version and no release tag. The result is then "not evidenced", not a score of 0. Release tags cannot be read when there is no version control history.

## What the result is not
- It does not judge the quality of a changelog's entries or how often the project releases.
- It does not see versioning or release notes that exist only outside the repository, for example a hosting platform's release page that nothing in the tree points to or generates.
- It does not check that a stamped version matches what was actually published.
