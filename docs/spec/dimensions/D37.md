# D37: Vulnerability-disclosure Policy

**Lens:** securityCompliance · **Scored:** yes

## Property
Whether the repository publishes a coordinated-vulnerability-disclosure policy (SECURITY.md or security.txt) with a reporting contact, so finders know how to report a vulnerability. Presence of a policy file with a contact, not whether the policy is adequate or honoured.

## Applies to
Any repository, in any language. The dimension reads one kind of file: a disclosure policy. That is either a security policy in prose or plain text, or a `security.txt` file.

## Population
This dimension does not read production code. Its population is the repository's disclosure policy files at the analysed commit. A disclosure policy file is one of these:

- **A security policy:** a file named `SECURITY` with one of these extensions: `.md`, `.markdown`, `.mdown`, `.mkd`, `.rst`, `.txt`, or no extension. It must be in one of these places:
  - the repository root;
  - a hosting platform's metadata folder at the root: `.github`, `.forgejo`, `.gitea` or `.gitlab`;
  - a `docs` or `security` folder at the root.
- **A `security.txt` file:** in the `.well-known` folder at the root, or at the repository root.

Policy files count wherever they sit, so the hidden-folder rule in [production-code.md](../production-code.md) does not apply to them. A policy kept outside the repository (for example on a website or a bug-bounty platform) is outside the population.

## Unit and denominator
The unit is the repository's disclosure policy: the one policy file that is judged. There is no denominator. The result is one finding about the whole repository.

When several policy files are present, only the first readable one in this order is judged. The other files do not change the score.

1. `SECURITY` at the root, then in `.github`, `.forgejo`, `.gitea`, `.gitlab`, `docs` and `security`, in that order. In each place the extensions are tried in this order: `.md`, `.markdown`, `.mdown`, `.mkd`, `.rst`, `.txt`, no extension.
2. `.well-known/security.txt`.
3. `security.txt` at the root.

A file that is present but cannot be read is skipped, and the next file in the order is tried.

A **private reporting contact** is a channel that lets a finder send a report without making it public. Any of these counts:

- an email address or a `mailto:` link. A spelling that hides the address from scrapers also counts, for example `name [at] example.com`, `name[@]example.com`, `name (at) example [dot] com`, `name @ example com` or `name AT example.com`.
- a web address where a report can be sent, for example a form, a security contact page or a platform's private advisory page.
- an instruction to use the hosting platform's private vulnerability reporting, for example "use Report a vulnerability in the Security tab".

These are **not** a private reporting contact:

- a link to the project's public issues, pull requests, merge requests or discussions;
- an instruction to report through any of those public channels.

## Thresholds
- The judged policy file has a contact when it names at least one private reporting contact.
- A judged policy file whose only reporting route is a public channel has no contact.

## Score
| Judged policy file | Score |
|---|---|
| Names at least one private reporting contact | 10 |
| Names no private reporting contact (a stub, or public channels only) | 4 |

No other scores are possible. When the repository has no policy file, it is not scored (see below).

A policy may have a supported-versions section that lists only versions older than the repository's newest release. That is reported as a finding and does not change the score.

## Not measured when
- **No policy file:** the population is empty, and the dimension is not applicable. A policy may properly be published outside the repository, so a missing file means there is no evidence either way. It does not count as a failure.
- **No policy file can be read:** policy files are present but none of them could be read. Whether the repository names a contact is then unknown.

## What the result is not
- It does not judge whether the policy's response times, scope or safe-harbour terms are adequate. Apart from the out-of-date supported-versions finding, which does not change the score, it does not check the supported versions.
- It is not evidence that the project honours the policy or answers reports.
- It does not check that the contact works (for example that the mailbox exists or the form is turned on).
- It does not read policy files after the judged one. A contact in a later file does not raise the score.
- A repository with no policy file is not scored as having no policy. Its policy may be published elsewhere.
- It says nothing about whether the code has vulnerabilities.
